# github-events

GitHub's runs and releases, pushed into equin — no polling. Design:
[`research/2026-11-18-global-github-release-events.md`](../../../../research/2026-11-18-global-github-release-events.md).

## Watches — an open set

The plugin that owns a repo says what to follow, in its own `server/`:

```ts
GitHubEvents.Watch({
  repo: SOURCE_REPO,
  workflow: "installer-release.yml",   // the file under .github/workflows/
  releases: true,                      // follow the repo's Releases too
  headIsRunName: true,                 // the workflow's run-name is its ref (manual runs)
  remedy: ({ repo, head }) => [ "…re-publish command…" ], // extra lines for the failure task
});
```

Contributors today: `installer/release-assets` (the product repo's release
workflow and Releases), `database/client-tools` and `database/pgbouncer` (the
daily Build and Publish of the embedded packages). Everything here reads them
through `githubWatches()` / `watchedRepos()` / `watchFor()` /
`releasesWatched()` — never by name. An event of anything unwatched is dropped.

## Transport (`machine/`)

- **Who runs it.** Main's backend on the checkout that publishes (no upstream:
  `resolveUpstreamRemote` → `is-publisher`), started in `onReady` — never in a
  worktree, a clone, or an exec child. Everywhere else the status is `off`.
- **One forwarder per watched repo** (`github-events.forwarder`, a
  `defineDaemon` with backoff): `gh webhook forward --repo=<r>
  --events=workflow_run,workflow_job,release --url=<main's delivery URL>
  --secret=<random per start>`. Per repo, not per org: org hooks need the
  `admin:org_hook` scope; repo hooks work with `repo` + `workflow`.
- **The extension binary itself runs**, through a `/bin/sh -c` that first
  deletes any forwarder hook (`config.url` =
  `https://webhook-forwarder.github.com/hook`) a hard kill left on the repo,
  then `exec`s the extension. A repo holds one forwarder hook (a second start
  fails `422 Hook already exists`); a SIGTERM to the extension deletes its own,
  a SIGTERM to the `gh` wrapper would orphan it.
- **Not set up** (no `gh` on the PATH, or no `cli/gh-webhook` extension under
  `~/.local/share/gh/extensions/`) is a state the health row shows with its
  fix (`gh extension install cli/gh-webhook`), not an error. The extension is
  not an `infra/deps` dependency: deps has no installer kind for a gh
  extension (it would have to live where gh looks for it, under gh's own data
  dir, and use gh's auth).
- **The delivery URL** is `namespaceUrl(main, endpointPath(…),
  servedGatewayPort())` — never a spelled port.

## Deliveries

`POST /api/github-events/deliveries` is `access: { public }`: the gateway
stamps a forwarded request a visitor (`x-forwarded-*`). Its authentication is
`X-Hub-Signature-256`, checked over the raw bytes, constant-time, against each
running forwarder's current secret — the one that verifies names the repo
(and the payload must agree). Nothing is parsed before that; a bad signature is
a 401.

- `ping` (on connect): the forwarder is `connected`, and one **catch-up** runs:
  each watched workflow's 10 newest runs and, for a releases watch, the 5
  newest releases (`gh api`), through the same upserts. Once per connect,
  never on a timer.
- `workflow_run` of a watched workflow: upsert into `github_runs` (key
  `<repo>#<run id>#<attempt>`; an older `updated_at` never overwrites a newer
  one). When it completes: file its failure, and re-read the repo's releases
  (an asset upload sends no `release` event).
- `workflow_job` that failed: merged into its run's `failedJobs` (with the
  failed step names), if the run is stored.
- `release` of a releases-watched repo: upsert (or delete) `github_releases`.

## Report kind `github-run-failed`

Filed in-process (`recordReport`, source `server-github-events`) when a watched
run attempt completes with `failure` / `timed_out` and its event is not
`pull_request` — once per attempt: `reported_at` is claimed before recording
and given back if recording throws. A catch-up files only the newest run of
each head. A run with no failed job delivered reads its jobs from GitHub first.
Fingerprint `repo + workflow + head`, so a re-run of the same tag, or the same
cron failing again on main, lands on one row. No `code` staleness: this is
GitHub's state, and a later green run does not close the report.

## Readers

- `github-events.runs` / `github-events.releases` — live windows over the
  tables.
- `github-events.status` — `off` / `not-set-up { reason, fix }` / `on` with
  each forwarder's `connecting | connected | reconnecting | failed`; the
  **GitHub events** health row.
- `newestRunOf` / `releaseOf` / `forwarderStatusOf` (machine) — what the
  publisher's releases row (`upstream`) reads of the newest tag.

## Plugin reference

- Description: GitHub events in the browser: the health report's GitHub events row (on the publisher's main only — absent elsewhere): connected once GitHub pinged every watched repo's forwarder, pulsing while one connects, attention while one reconnects or gave up (naming why) or while forwarding is not set up (with the command that sets it up); and the github-run-failed report kind's Debug → Reports summary line. GitHub events, every host's half: the GitHubEvents.Watch contribution (repo, workflow file, releases?, remedy? — an open set each repo's owner contributes, read through githubWatches / watchedRepos / watchFor), the github_runs table (one row per run attempt of a watched workflow: status, conclusion, head, failed jobs and steps, reported_at) and github_releases (one per release of a watched repo: draft, asset names), served as the github-events.runs / github-events.releases live windows and swept after 180 days / 2 years, and the github-run-failed report kind (fingerprint repo + workflow + head; its task names the failed jobs and steps, the run, `gh run view <id> --log-failed`, and the watch's own remedy).
