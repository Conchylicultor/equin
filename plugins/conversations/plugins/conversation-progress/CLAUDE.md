# conversation-progress

Four-phase progress (research → design → implementation → pushed) per
conversation. `server/` is portable: the extension table, the live
read, and the `pushLanded` → pushed job, so a browser host serves the row from
its own DB. The git heuristic needs the worktree and lives in `machine/`.

## The phase follows the worktree's changes, not its turns

The phase is a function of which files the branch changed: none = research,
only `research/**` = design, any other = implementation. Reading that whole
set (`git diff <merge-base>` + an untracked listing) lstats every tracked file
and readdirs the tree — ~50k vnodes, cold whenever the machine's vnode cache
has moved on. So it is NOT read per turn:

- `classifyProgressJob` (on `conversationTurnCompleted`) only calls
  `followConversation`. The first call for a conversation (per process) opens
  a checkout watch on its worktree (`infra/git/checkout-watch`, ignored paths
  already dropped) and then classifies the whole tree once — the baseline,
  after the watch is live so nothing lands unheard between the two. Every
  later turn is a map lookup.
- Each watch batch is checked against git for **its own paths only**
  (`changedAmong`: `diff` + `ls-files --others` limited to those literal
  pathspecs), so a change costs reads of the files it touched. A batch whose
  paths could not move the phase (research files while already in design)
  costs no git at all. A watch that lost events re-reads the whole tree.
- A conversation stops being followed once it reaches implementation (pushed is
  `markProgressPushedJob`'s), when it closes (`CloseTeardown`), or when a batch
  finds it done or moved. One that ends without a close (gone) keeps its watch
  until its worktree next changes or the process restarts. A restart forgets
  everything: each conversation's next turn re-follows it.
- A workspace with no git base (scratch, or no `main`) is research, with no
  watch.
