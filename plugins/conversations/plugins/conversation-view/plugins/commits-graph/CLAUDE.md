# commits-graph

Toolbar chip showing how many commits the conversation's worktree branch is ahead of (and behind) `main`. Clicking opens a side pane that draws the chain of commits between the merge-base and HEAD as a single colored rail (VSCode-Git-Graph style, single-branch scope).

## The standing belongs to `tasks/attempt-work`

This plugin does not own "where does this attempt stand relative to `main`?" — the server-side exit-drop guard needs the same fact, so it lives in [`tasks/attempt-work`](../../../../../tasks/plugins/attempt-work/CLAUDE.md). Here:

- The **chip** subscribes the `attemptWork` live value and nothing else. `↑ahead ↓behind` come from `pending`'s `measured` arm; the push count is `landedPushes || ledgerPushes` (git-measured, with the ledger as corroboration — a `pushes` row proves a push happened, its absence proves nothing, and pre-trailer-era commits are visible only to the ledger).
- The **pane** owns only the commit *rows*, behind the `commitsGraph` live value (`commits-graph.graph`, params `{ attemptId }`, db arm). It **follows** the attempt's row (`attemptWorkspaces { ids }`: its checkout and start) and its conversation set (`attemptConversationIds { where }`) — not attempt-work's value, whose wire payload drops the landed shas — so a write reaches only the attempts whose rows it moves. Its landed shas come from attempt-work's landed memo, `landedShasFrom(attemptId, { createdAt, convIds })`, over those rows — the same trailer grep the chip's count reads; the pending-side git helpers (`readBranch`, `readMergeBase`, `probeHeadMain`) are imported from `attempt-work/server`, not re-implemented.

**The landed set is git-measured** — `main`'s commits carrying this attempt's conversation trailers — never read off the `pushes` ledger, which lags behind a background ingest job (`research/2026-08-17-global-attempt-work-git-derived-standing.md`). Two consequences worth keeping: the graph value recomputes on `refHeadServed` **alone** (a commit joins the landed set only by landing on `main`, so a ref advance is the complete refresh signal), and `graphEtag` folds in `(headSha, mainSha)` plus the conversation set and the checkout path — an adopted conversation moves the landed set with no ref moving, and without its ids the ETag would certify a stale graph (a 304). `recomputeOn: [refHeadServed]` recomputes every subscribed attempt, so a ref advance fans out only to the panes on screen; the `whileSubscribed` stop evicts the attempt's landed set (by attempt id: a moved row never restarts it), and the `whileFollowing` stop the git memo of the checkout its start was handed (a re-pointed `worktree_path` drops the old one).

## Unresolved payloads (worktree gone)

The graph payload is wrapped in `Resolvable`: the resolved arm carries the measured graph, the unresolved arm a `reason`. An attempt outlives its worktree, so "no worktree" and "worktree reaped mid-compute" are the SAME determinate state, collapsed onto `unresolved("worktree unavailable")` by `onWorktree` (`machine/internal/resources.ts`), as is a gone attempt row (no followed `attempt` row). Loader value and `revalidate` ETag come from the same `onWorktree` branch over the same followed rows, so they can never disagree (`research/2026-07-09-global-etag-value-coproduction.md`). Every *other* git failure throws.

The pane is deliberately stricter than the chip: `attempt-work` can still measure a reaped attempt through its surviving branch ref, but the pane needs a checkout to run its commit logs in.

The chip renders a muted `—` (reason as tooltip) both for an unresolved payload and for `pending.kind === "no-branch"`; the pane renders a `Placeholder` with the reason.
