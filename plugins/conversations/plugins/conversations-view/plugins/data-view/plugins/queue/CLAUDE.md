# queue

## Sections

The rows are grouped by the synthetic `section` field (`web/components/queue-sections.ts`,
`queueSectionField(sections)`): Pinned, the user's own sections (rank order,
`alwaysGroup` — drawn empty too), Queue, then the read-time ones (Working,
Lost, Unranked, Failed to start, Disconnected, Done). The user's sections
(`queueSections`) are read in the same all-or-nothing gate as the rows
(`useQueueRows`), so a row filed into a section never paints before it.

Only the **filed** sections — Pinned, a user section, Queue — hold ranked rows
and take a row from another (`manualOrder.reseatInto = takesFiledRows`); a
read-time section is neither a drag source nor a target. Every way of moving a
group is a section write (`queue-section-controls.tsx`, one value shared with the
item actions through `QueueSectionsContext`):

- drag within a section → `reorder`; into another filed section → `reorder`
  with `section` (beside the drop neighbour — one global rank space), or `file`
  when dropped on a collapsed or empty section's header / empty band (rank
  kept — an expanded section showing rows is entered through its rows);
- drag onto the floating "New section" target (`onReseatNew`), the row's
  **Move to → New section…**, or a header's "+" → `sections/create` (with the
  conversation, after a section, or last), then its name field opens
  (`groupEdit.renaming`);
- header: double-click to rename, drag to reorder among user sections
  (`groupEdit`), ⋯ → Rename / Move up / Move down / Delete (its members go
  back to the Queue);
- Pin / Unpin is `file` into Pinned / the Queue.

A section holds waiting groups only: a running group shows under Working
whatever it is filed into, and returns there when it stops. So does a waiting
supervisor whose managed tasks (at any depth) are running
(`supervisingTaskIds` in `queue-attach.ts`, over the same manager relation as
`QUEUE_ATTACH`), unless it waits on the user itself (a question, a stuck
turn) — it waits on its agents, not on you; its dot stays amber.
