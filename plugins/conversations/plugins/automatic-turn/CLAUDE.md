# automatic-turn

Whether the app may type an **automatic** turn — one no person typed: a watch's
event batch, a self-compaction — into a conversation now. Every automatic
sender asks the same question, so two senders woken by the same status change
cannot type into each other's turn.

```ts
automaticTurnReadiness(conversationId, { own?, exec? })
  // → ready | not-found | held: busy | waiting-for | pending-turn (by)
PendingTurn({ id, pending: (conversationId, exec) => … })
```

- **busy** — `starting` / `working` (`isAgentBusy`): a turn typed into a busy
  CLI is folded into the running turn at its next tool boundary, as plain text.
- **waiting-for** — `waitingFor` set (a held question): a turn would answer it.
- **pending-turn** — some *other* plugin's `PendingTurn` says a turn of its own
  is waiting for this conversation. It goes first: typed after ours it would
  reach a busy CLI (a `/compact` would then never run as a command). A sender
  that is itself a contributor passes its entry as `own`, so its own pending
  turn does not hold it.

**Re-running a hold is push-based**, through `conversation.statusChanged`
(tasks-core), which fires on every change that can end one: the agent leaving
a busy status, its `waitingFor` clearing (the status unchanged — the payload
carries `waitingFor` / `previousWaitingFor`), and the end of another plugin's
pending turn (that turn makes the agent busy, then idle). A held sender
subscribes to it and asks again.

User turns do not ask: what a person types is their call (`submitTurn` withdraws
a waiting question for it). This plugin names no sender and no contributor.
