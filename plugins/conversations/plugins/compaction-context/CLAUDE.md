# compaction-context

Hands an agent back, right after its context is compacted, what plugins had put
in it through tool results and the summary dropped.

**The problem.** A plugin that delivers something to an agent through a tool
result, and records that it did, is wrong after a compaction: the summary folds
the result away, the record still says "delivered", and nothing hands it over
again. Page instructions were the case that surfaced it — an agent stopped
following a page's instructions after its conversation compacted, and the write
gate, believing them received, never re-sent them.

**The mechanism.**

- Every app-launched agent carries a `SessionStart` hook on the `compact` source
  (agent-launch's `agentLaunchPolicy()`; entry built by `compactionHookEntry()`,
  `core/hook.ts`). It runs `bin/compaction-context.ts`. `compactionHookEntry()`
  lives in the `machine/` half — it checks the script on disk — so the
  `server/` half (the contribution and the endpoint) stays portable: a browser
  host can boot a contributor such as `page/annotations/agent-access`.
- The script POSTs `/api/conversations/:id/compaction-context` on the backend the
  agent dials (`EQUIN_PARENT_URL`), retrying a backend mid-restart for
  40 s, and prints the answer as SessionStart's `additionalContext` — nothing
  when it is empty. A refusal or a backend gone for good is a non-blocking hook
  error (exit 1, stderr): the session goes on without it.
- The endpoint runs every **`CompactionContext`** contribution's `restore` and
  joins their parts. A contribution reconciles its own record (what the agent
  no longer holds) and returns the text to hand back, `""` for none; one that
  throws fails the request, loudly.

```ts
CompactionContext({ id: "page-instructions", size: "whole", restore: (conversationId) => … })
CompactionContext({ id: "task-tree", size: "fit", restore: (conversationId, budget) => … })
```

This plugin names no contributor; a plugin that delivers through tool results
adds itself.

## The CLI caps a hook's output — so parts declare how they may be sized

Claude Code puts at most **10,000 characters** (JavaScript string length — not
bytes, not tokens) of one hook output in the agent's context. Past that it
saves the output to a file and the agent gets a ~2 KB preview. That is how this
broke on 2026-11-09: 5.6 KB of page instructions followed by a 30 KB task tree,
and the agent saw half of the first instruction — while the instructions were
recorded as received, so the write gate never sent them again.

- **`whole` parts are never cut** (page instructions). They go first, in
  registration order.
- **`fit` parts are given the room left** under `COMPACTION_CONTEXT_BUDGET`
  (the cap minus a margin) and must return text no longer than it —
  `fitToBudget` cuts at a line and adds a footer pointing at the tool that
  reads the rest (`task_tree`). A longer answer fails the request.
- **The cap is a copy** (`HOOK_OUTPUT_CAP`, core/budget.ts — the `HCe`
  threshold in Claude Code 2.1.319). The CLI may change it in any release, so
  nothing trusts it: the endpoint records what it answered
  (`compaction_context_sends`) and
  [`delivery-check`](plugins/delivery-check/CLAUDE.md) reads back from the
  transcript whether the agent got exactly that. When it did not — whole parts
  over the cap, or a CLI that lowered it — it files `compaction-context-cut`
  and sends the whole context as a turn.

**Bounds.**

- Only sessions launched (or resumed) since the hook existed carry it.
- A compaction while the backend is down for more than 40 s restores nothing,
  and the contributors' records stay as they were.
- `/clear` is not handled: the matcher is `compact` only.
- If the fallback turn cannot be delivered (the conversation stopped), the
  report says so; the contributors' records still say "received".
