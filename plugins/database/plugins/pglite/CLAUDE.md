# pglite

The PGlite database driver: a `DatabaseDriver` (`database/server`'s host
service) over Postgres compiled to WASM, running in this process — for a host
without the computer's Postgres cluster. The desktop never boots it: it is a
host provider, which no composition bundles (`plugin-meta/closure`'s
`hostProviders`), and its own `pgDriver`
(`database#machine`) is the desktop's provider. A composition that runs without
the computer names it to take it back.

- **Where its data lives is the host's storage**
  (`createPgliteDriver({ storage })`, the provider passing
  `browser-server/host-storage`'s `hostStorage`): in memory, or — a
  persistent storage — its `idb://` dir, opened with `relaxedDurability` and
  adopted by the storage, which flushes it (`syncToFs`) before it records
  anything durable and closes it before a wipe or a handoff. No `storage`: in
  memory (a test). `server/internal/stored-data.test.ts` reopens an on-disk
  database (`nodefs`) and applies the next version's migrations over it — a
  phased group with claimed data — keeping its rows.
- **A snapshot's database** (`storage.databaseStart: { from: "snapshot",
  dataDir, shiftMs }`): opened with `loadDataDir`, then — in `ready()`, before
  anything reads it — every `timestamp` / `timestamptz` column of every public
  base table is moved by `shiftMs`, in one transaction with
  `session_replication_role = replica` (no trigger: the rows did not change,
  the clock did). `dump()` (what the storage adopts) is `dumpDataDir("gzip")`.
  Pinned by `server/internal/snapshot-load.test.ts`. In memory, PGlite takes
  its options as its ONLY argument: `new PGlite(undefined, options)` drops them.
- **Scripts go through `exec`.** node-postgres runs a parameterless query over
  the simple protocol, which accepts several statements (a migration file, a
  view rebuild); PGlite's `query` is extended-protocol, one statement only. The
  driver routes a parameterless, non-array-mode query through PGlite's `exec`
  and answers with the last statement's result — decided up front, because
  inside a transaction a failed attempt would abort it.
- **`bootDdl` adds no bound**: one connection, nothing else holding locks.
- **`listen` uses the root client's `onNotification`** (channel and payload,
  one queue, so a transaction's `live_state` NOTIFYs arrive before its
  `live_state_end`), filtered to the session's channels, after one `LISTEN a;
  LISTEN b` through `exec`. It never reports `lost` (no socket), and `close`
  issues no UNLISTEN — another session may share the channels. This is the
  change feed's session on a browser host. What the feed leans on — statement
  triggers with transition tables, `pg_current_xact_id()`, the deferred end
  marker firing at commit, delivery only after commit and in order, nothing for
  a rollback, `tgargs` as a `Uint8Array` — is pinned on this build by
  `server/internal/notifications.test.ts`, which runs the real `rebuildTriggers`.

Proven by `tasks/task-category`'s portable boot test, which boots that plugin's
whole server closure on this driver.
