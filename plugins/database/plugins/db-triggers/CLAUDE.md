# db-triggers

An invariant a plugin needs **the database** to keep — one write must always
come with another, or a commit must never leave some state — declared as data
and installed by the boot schema layer, so it holds for every writer: a
mutation that forgets, a seed, raw SQL, a backend still running older code.

```ts
export const clusterTriggers = defineDbTriggers({
  id: "tasks.cluster",
  functions: [{ name: "tasks_union_clusters", args: "text, text", ddl: `CREATE OR REPLACE FUNCTION tasks_union_clusters(…` }],
  triggers: [{ name: "…", table: "task_dependencies", ddl: `CREATE OR REPLACE TRIGGER … ON task_dependencies …` }],
});
// server definition: contributions: [DbTrigger(clusterTriggers)]
```

- **`defineDbTriggers`** asserts at module eval that each DDL creates exactly
  the function / trigger it is named (and the trigger is `ON` its table): the
  installer's catalog check reads those names.
- **Installed by the schema layer** (`migrations/server`'s `applySchemaLayer`,
  after the derived-`updatedAt` triggers, before the rollups), in its one
  transaction: each trigger's COMMENT is its set's stamp (`<id>:<sha256 of
  every DDL>`), so a
  current set is a catalog-only no-op; a stale one reinstalls whole under an
  advisory lock (`CREATE OR REPLACE TRIGGER`: SHARE ROW EXCLUSIVE, never
  ACCESS EXCLUSIVE); then every set is asserted current, or boot fails.
- **Plain, immediate triggers only.** No CONSTRAINT trigger: Postgres cannot
  replace one in place, and the change feed refuses a DEFERRED trigger on any
  table it routes (a write it makes would notify after the transaction's end
  marker). A check runs at the end of its statement instead.
- **Removing** a trigger from a set drops it on the next install (found by
  the set id in its stamp). A removed function stays — nothing calls it once
  its trigger is gone.
- **Forks keep their data**: pg_dump writes triggers in post-data, so a dump /
  restore loads the rows before any trigger exists.
- **In a test**, `installDbTriggers(db, [set])` on a throwaway database
  (after `runMigrations`).

Older hand-rolled installers with the same protocol: `derived-updated-at`
(compiled per table) and `infra/jobs`' superseded trigger (graphile's schema,
installed with the queue schema).
