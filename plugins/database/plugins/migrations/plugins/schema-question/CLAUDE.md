# schema-question

`askSchemaFiles`: what loading the drizzle schema files yields, as a plugin
record — the shape every schema check uses instead of a subprocess of its own.

A check that needs what LOADING the schema files yields — the tables they
export, a registry their module eval fills — asks a **schema question**: a
module whose default export is `{ answer(file, exports, input) } satisfies
SchemaQuestion<A, I>`, and one `askSchemaFiles(repo, { name, module, input? })`
call (`core/internal/schema-question.ts`). The probe host
(`scripts/schema-question-host.ts`, import-free) loads the files drizzle-kit's
way — `require()` each under `bun --bun`, from the migrations plugin's dir, drizzle-kit's
environment, in path order — then loads each question module and asks it about
each file that loaded; a file whose load threw answers with its error.

- **One record per question, keyed by the whole set** (`plugin-records`'
  `closureRecord`): the host and the question module as CODE (by URL, read
  and run from the checkout they live in, never from the set asked about),
  every schema file of the set as DATA (each over its import closure), the
  inputs and the npm code. Asked about another checkout's set, a question's
  imports are its own checkout's, so a registry it reads is not the one that
  set's schema files filled — one instance per module holds only over the
  question's own checkout (every caller today). Over
  400 main commits, 64% reach no schema file's closure — a lookup.
- **Why not one record per file** (tried, and wrong): the files load in ONE
  process, as under drizzle-kit, so their module eval shares registries — two
  tables declaring one derived `updatedAt` differently make the SECOND file to
  load throw. A file's answer is a function of the whole set loaded with it; a
  per-file key kept a failure caused by another file after that file was fixed,
  and missed a new conflict when only the edited file reloaded. The test
  "fixing one schema file re-answers another whose load it broke" pins this.
  Loading each file in a process of its own would be sound per file, but costs
  a bun start and ~475 shared modules per file (145 processes cold), and would
  no longer see the conflicts drizzle-kit hits.
- **The misses of every question share a load**: a keyed coalescer per
  (checkout, file set) starts the first miss's process at once and folds every
  miss arriving while it runs into one trailing process — at most two loads per
  burst, whatever the number of schema checks. Asks over different file sets
  never share a process (each answer is keyed by exactly the set loaded with it).
- **The host answers per ask**: a question that throws fails its own ask
  (`probe-failed`), never another check's; a crash of the host fails them all.
- **What escapes the key**, as for every record: a schema module that reads a
  file or the environment at load (`--verify-records` catches it); and an edit
  made on disk between the pass taking its file set and the host loading the
  files — the answer is computed from the newer bytes and stored under the
  older key (the race every record computed from a live checkout has; the
  sql-writes probe record had it before this).

Adopters: `schema-files-loadable`, `derived-updated-at:declared`,
`ids:pk-declared`, `sql-writes:fit`. Measurements:
`research/2026-11-12-global-plugin-records-store-layout.md`, last section.

**Why a sub-plugin, not `migrations/core`**: it imports the plugin-record
store, which is build tooling. `migrations/core` is imported by the browser
hosts' server graph (`framework/browser-server/bun-host`): while this lived in
that barrel, the build's browser-host codegen refused the demo composition
(its home app no longer bundled), and moving it here cleared that.

Tests: `core/internal/schema-question.test.ts` — a throwaway checkout whose
answer must move with an edit to a schema file, a module one imports, another
schema file whose load broke it, an input and the question module, and stay a
record after an edit outside every schema file's closure.
