# scoped-out-dispatch

The report kind for **a dispatch slot that fell back inside a `<PluginScope>`
though the page serves its key** — a contribution on the page matches, and
the scope dropped it without its composition negating that plugin by name.
In /demo this is how a negative's cascade hid ~20 transcript renderers for
months: each Read / Edit / Bash card rendered the generic tool card, and
nothing said so.

`.Dispatch` (`primitives/slot-render`) asks, on a fallback,
`useScopedOutContributions(slot)` (web-sdk: what the innermost scope left out,
minus the composition's `negated` plugins) for a match, and emits a
`ScopedOutDispatchFault` into `scopedOutDispatchSink` once per (slot, key,
plugin, scope) per page. `ScopedOutDispatchCollector` (mounted via
`Core.Root`, on the page outside every scope) files it as
`report({ kind: "scoped-out-dispatch", … })` over the page's telemetry route.
The fallback still renders.

Fingerprint: scope + slot + plugin — the defect is the plugin missing from the
scope, so every key it would have served is one report.

The static twin is `composition-closure`'s cascade-loss rule
(`Composition.cascadeLosses`): a negative may not take a plugin a positive
asked for without naming it. This report catches what that cannot see — a
plugin nothing asked for whose renderer the scope's data still needs.

The runtime rule is the stricter of the two on purpose: only the plugins a
composition negates by name are exempt, so a plugin a cascade removed without
anyone asking (which the static rule accepts when no positive asked for it, or
under a root `**`) is still reported here once its key falls back.
