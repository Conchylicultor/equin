# check-thread-stall

The report a `./equin check` run files when its shared JS thread stalls
past the "Check pass speed" track's targets. The stall watch itself lives in
the check runner (`plugins/framework/plugins/tooling/plugins/checks`, section
"The check thread is shared, and a run reports when it stalls"). This plugin
owns the kind: its payload, fingerprint, task and summary line.

## Two triggers, one kind

| trigger | files when | fingerprint | one row per |
| --- | --- | --- | --- |
| `stall` | one stall's `held.heldMs ≥ STALL_REPORT_MS` (2 s) | `check-thread-stall:<top owner>` | owner (`check <plugin>`, `shared <fn @ path>`, `import`, `native <leaf>`) |
| `total` | a run's `held.heldMs ≥ TOTAL_REPORT_MS` (20 s) | `check-thread-stall:total` | — |

**Held, not late.** A tick fires late when code holds the thread AND when the
OS does not schedule it (a build's check pass runs at background priority).
Only the first is code's doing, so the runner splits each stall into held (the
main thread's own CPU time plus its synchronous-I/O wait) and starved, and
files on held time. Without a thread CPU clock on the writer's platform
(`held.measured: false`, the run's `held: null`) it falls back to `lateMs` /
`stalledMs`. `held` is optional in the schema only so rows filed before the
split still parse.

The thresholds are the track's **targets**, not today's measurements, so both
fire on most full passes until the remaining stalls are fixed. After that, a
report is a new regression.

Warning variant, bell re-alerts at most every 6 h per row: a slow check is a
chronic cost, not an outage. The row keeps the latest example — worktree, run
id, transcript path, the top 3 owners with their stacks, the waiting-vs-working
split, held vs starved, and CPU.

## `check-pass-hung` — a pass its watchdog killed

The second kind here. A check pass whose main thread held its core
`HANG_HELD_MS` (5 min of its own CPU time) without running one timer is
killed by its hang watch (checks' section "A pass that hangs is killed by its
own watchdog thread"), which files this first. Its own kind, not a third
trigger: a stall is a slow pass (warning, chronic), a hang is a pass that
would never have finished — an **error**, the build or push on it failed.
One row (`check-pass-hung`), its count the recurrence; the payload names the
checks in flight, the newest one started, settled vs selected, held vs wall
time, and the main thread's native stack (macOS `sample`, the full capture's
path beside it).

## How it is filed

The check runner is a CLI process with no server, so it files through the
report outbox (`plugins/reports/plugins/outbox`). The payload's worktree lives
in `data`, not in the row's `worktree` column — main records every outbox
entry. The outbox's staleness rule drops a report when main has changed a file
on the stall's stacks since the writer's branch point.

`core/` is imported by the check runner (`checks/core/stall-report.ts`), so it
stays zod-only: no React, no server code.

## Plugin reference

- Description: Check-thread-stall and check-pass-hung report kinds' Debug → Reports summary views: one line naming how long the check thread stalled, its top owner and what it was mostly doing — or, for a hung pass, how long its thread held its core, what was in flight, and that it was killed. Both are filed by the check runner through the report outbox — no collector here. Check-thread-stall report kind: validates the check runner's thread-stall payloads (trigger stall = one stall whose code held the thread ≥ 2 s — held, not merely late: a starved thread files nothing —, fingerprinted by its top owner; trigger total = a run whose stalls add up to ≥ 20 s held, one row), filed through the report outbox, and renders a task naming the owner, its stacks, the held-vs-starved split and the run's transcript. Warning, re-arms every 6 h. Also the check-pass-hung kind: a pass whose main thread held its core 5 min without yielding, killed by its own watchdog thread — one row, an error, its task naming the checks in flight and the main thread's native stack.
