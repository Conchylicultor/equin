# crash

## What makes one crash one row

`crashFingerprint` hashes the first identity the occurrence actually carries:

1. **Its stack** — top 3 normalized frames, prefixed by the error type.
2. **A caller-declared `errorType`, no stack** — `PaneRestoreCorrupt`,
   `JobDeadline`, `LiveStateWedge:<disc>`, `PluginLoadError <path>`,
   `EndpointError <status> <route>` pass this ON PURPOSE so a family of varying
   messages collapses onto one row. Don't "improve" it by folding the message in.
3. **The message**, when there is neither (browser `window.onerror` with no
   `Error`, server call sites passing `stack: null`), with the per-occurrence
   tokens normalized away so a recurring failure still accumulates on one row.

Whatever the branch, a `scope` is prefixed: what a shared throw site failed
for. Filers derive it from the error with `packages/error-subject`'s
`crashFieldsOf` (a `SubjectError`'s subject, the cause's class code such as a
SQLSTATE, plus the caller's own — a job's name), never by copying `name` /
`stack` by hand (`error-subject/crash-fields-of`). That is what splits the one
migration runner's failures into one row per migration and error class.

`core/crash-kind.test.ts` pins branch 1 and 2 as literal hashes: they reproduce
the pre-2026-09 input byte for byte, so live report rows keep their identity.
Add a case there before changing any of this.

## A fetch with no answer needs a host that answers

An unhandled rejection that is a fetch with no HTTP answer at all (an
`EndpointNetworkError`, or a browser's bare fetch `TypeError` — "Failed to
fetch", "NetworkError when attempting to fetch resource.", "Load failed") is
filed only once the page's own host answers HTTP (`reachHost`, infra/health —
the signal the live-state wedge watchdog files on). Host answers → the network
is up and the request still failed (CORS, a blocked URL, a server that drops
it): filed — a page fetch's rejection names its URL and caller
(`FetchRequestError`, request-guard; the test reads its `browserMessage`). No answer either → the visitor's network (an offline laptop, a
phone's backgrounded tab), or the whole host: a console warning, no report.
`web/internal/fetch-no-answer.ts`.

## A page leaving is not a crash

When a document goes away (navigation, reload, closed tab, removed frame),
WebKit rejects every pending or held Web Lock promise (`navigator.locks.request`
/ `.query`) and pending `permissions.query` with `AbortError: Promise was
rejected because the browsing context is going away`. A lock held for the page's
lifetime is released that way, so every Safari page leaving produced one
unhandled, stackless rejection. The collector recognises that exact,
browser-owned DOMException and warns instead of filing; any other AbortError is
filed. `web/internal/context-teardown.ts`.

## A browser extension's error says so

A browser extension's page-world script throws into the page's window error
handler, and Firefox and WebKit attribute its frames to the document's own
URL (Dark Reader's stylesheet proxy:
`overrideProperty/<@https://equin.ai/demo:51:24`). So "on our origin" does
not prove a frame is ours. A window error or unhandled rejection therefore
carries `codeOrigin` (`core/code-origin.ts`, `stackCodeOrigin`):

- `page`: a frame is a script file the page loaded from its origin, or a
  function one of the document's inline `<script>`s names;
- `foreign`: every frame is provably elsewhere (another origin, an extension
  scheme, or the document at a function no inline script names);
- `unknown`: anything undecidable.

The verdict never mutes anything. A `foreign` crash is still filed; its task
title reads `[not our code]` and the website-visitor import keeps the
verdict as a typed field with a "Not our code" badge.

## The page shell's own report arrives through the collector

The shell's inline boot-failure script (`framework/web-core`'s `index.html`)
reports a boot file that failed to load. Before the app entry runs, it POSTs
`/api/reports` itself; once the entry has installed the page request guard a
raw POST is refused (and on the website there is no engine to POST to), so it
pushes the body onto `SHELL_REPORT_QUEUE_GLOBAL` instead. The collector takes
that queue when it mounts (`web/internal/shell-reports.ts`): it reports what is
queued, then every later push at once, through `report()` — the page's own
channel.
