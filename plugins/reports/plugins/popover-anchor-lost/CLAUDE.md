# popover-anchor-lost

The report kind for **an open popover whose anchor lost its box** — the anchor
(its trigger, or the caller's `anchor`) left the document, or something hid it
under `display: none`. Floating UI measures such an element as an empty rect
at the viewport's origin, so the panel used to jump to the screen's top-left
corner (the Wish popover did, with no reproduction).

ui-kit's `PopoverContent` positions through a steady anchor
(`ui-kit/web/components/steady-anchor.ts`): it measures the real element while
it has a box and keeps the last rect while it has none, so the panel stays
where it was. That cures the symptom only — the anchor vanishing under an open
popover is the bug of whoever hid it — so each loss is emitted, as ELEMENTS,
into `popoverAnchorLostSink`. This plugin **drains that sink**:
`PopoverAnchorLostCollector` (mounted via `Core.Root`) reads the popover, the
anchor and the nearest `display: none` element up from it through ui-context's
`collectMeta` (description, lineage, source line, owner) while they are still
the live nodes, and files `report({ kind: "popover-anchor-lost", … })`. The
dependency runs one way — ui-kit never imports `reports` or ui-context — the
same inversion viewport-escape and panel-overflow use.

Fingerprint: cause + popover lineage + anchor (source line, else description)
+ the hider (source line, else description). That tuple is the defect; one
emission per loss (re-armed when the anchor gets its box back).
