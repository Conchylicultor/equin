# list-catalog

An entry of a list (an app, a theme, a sidebar item) has two halves: its
**fact** — plain data — and the **code** behind it (a component, a callback),
written together by its plugin. The build runs every plugin's declarations
once and writes each web list entry's fact into the **catalog**; the code
stays in the plugin. Design: wiki "Design: a list entry without its plugin's
code" (stage 2).

- **One rule for what is data** — `factOf` (`core/fact.ts`): strings, finite
  numbers, booleans, null, arrays and plain objects of them are data; a
  function, a class (component), a React element, a zod schema, any class
  instance (Map, Date, a store) is code and is written as `{ "$code": true }`.
  A value that is neither (NaN, a hole in an array, a cycle) throws, naming
  where: an entry is never written wrong. The build (codegen's
  `list-catalog-gen.ts`, over the evaluated barrel records — a record's class
  instance revives with a non-plain prototype so it judges the same) and the
  page (web-sdk's `catalogMismatches`, over the live entries) run the same
  rule, so they cannot disagree on what is data.
- **The type twin** — `Fact<P>`: every field whose type is code does not
  exist on it, so reading code from a fact is a compile error. A field typed
  as a class the type cannot see as one is the one place the twin is weaker
  than the rule.
- **Where it lives** — the declared lists:
  `plugins/web-lists/core/web-lists.generated.ts` (read at load by
  `reorder/server`: the reorderable lists are a view of it); the entries:
  `server-core/core/web-list-entries.generated.json` (JSON: data, which no
  check reading source text judges). Both are the main composition's,
  each entry tagged with its plugin. The server loads the entries at boot
  (server-core's `installWebListEntries`, read by `webListFacts(listId)`, kept
  to the composition's plugins); a page is shipped them kept to its
  composition (`catalogFor`), as `catalog.js` of its registry artifact behind
  `@composition-web-catalog` (web-artifacts' `page-catalog.ts`), read with
  `slot.useFacts()` (web-sdk). `list-catalog-in-sync` fails on drift.
- **What is left out** — a list whose slot is declared
  `defineSlot({ catalog: { omitted: "<why>" } })`, as a whole: today the
  settings lists (`ConfigV2.WebRegister`, `Automations.Config`), which have
  their own declared form (decision D11 of the design: jobs, endpoints, live
  values and settings stay out).
- **Measurement 2** of the design — how many direct readers of a web list
  touch a code field — is `scripts/measure-fact-readers.ts`.
