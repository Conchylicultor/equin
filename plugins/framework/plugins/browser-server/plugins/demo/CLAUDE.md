# demo

Demo packs: recorded answers to live declarations, served by a browser server
(`framework/browser-server`) through its own `s.serveValue` /
`s.serveCollection`, so the unchanged app reads them through `useLive`.
Design: `research/2026-10-14-global-demo-scope-and-pack.md` §1.

```ts
// a pack module — lazy: nothing runs until it is served
export default definePack(({ ago }) => [
  packValue(configValues, { path: "x/y.jsonc" }, { … }),   // one value tuple (a typed-query value: its question)
  packAll(taskTracks, [...rows]),                            // an `all` collection (+ its :rows)
  packRows(conversationsById, [...rows]),                    // :rows of any collection
  packWindow(conversationsGone, { where: { … } }, [...rows], { count: 12 }),
]);

// the scope
const server = createBrowserServer({ serve: servePack(pack), unserved: (k) => new DemoMissingError(k, {}) });
```

- **Typed against the declaration.** Each builder is generic over the
  `liveValue` / `liveCollection` it is handed (tsc checks params, value, rows
  and `count`). The collection builders take network/live's
  `External{All,Lookup,Window}Collection`, so a contributed, `exposes` or union
  collection is a tsc error (its rows fold Postgres columns — no external
  spelling); a `columnScope` one, which no type tells apart, and a paged or
  central value throw `DemoPackError` when recorded.
- **Parsed on load.** The builders run inside the pack's thunk, which
  `servePack(pack, { now? })` evaluates: every value and row is parsed with its
  declaration's schema (the parsed output is what is served), a window query
  through the collection's codec, and any failure throws `DemoPackError`
  (`key`, `tuple`). So does a tuple or an `all` recorded twice, one row id
  recorded with different fields, two declarations sharing a key, a `count`
  smaller than the rows listed (or on a collection not declared `count: true`),
  and a sortable field holding a value with no order text.
- **Exact tuples.** A value answers `canonicalJson(canonicalParams(params))`
  — the tuple the runtime hands its loader — or, for a typed-query value, its
  question's canonical `q`. A window entry is keyed by the window codec's
  canonical wire params minus `limit` (and page cuts): the loader re-encodes the
  decoded query it is handed, so `useLive(c, query)` reaches the entry whatever
  its `limit`. The entry's rows are the query's whole answer in any order: the
  pack sorts them by the query's order (code points, NULL last, the id
  breaking ties), answers a page's `(after, until]` cut from them and the
  first `q.limit`. `$key` text is derived generically for every sortable field
  (`keyText`): text as is, a `Date` as ISO, a number as its order-preserving
  float bits, a boolean by name. `:rows` answers any id subset from every row
  the declaration's entries list (absent ids omitted). A collection declared
  `count: true` answers `:count` at each window entry's `where` (default: the
  rows listed). `:groups` is never served (the browser server fails it as
  unserved). Anything unrecorded throws `DemoMissingError(key, params)`,
  which the client sees as `loader-failed`.
- **One serve call per declaration**, `changes: { fixed: { reason: "demo pack" } }`
  (`{ snapshot }` for a `load: "snapshot"` value).
- **`DemoScenario`** = `{ id, pack: () => import("./pack") }`.

## web/: the `Demo` slots

`Demo.Resource({ id, useServe })` (a plugin answering its own live keys in
every demo scope — `useServe: Hook<() => DemoServe>`) and
`Demo.Route({ route: [ep.route, implement(ep, h)] })`. Declared here, in a
leaf barrel, not in `demo/scope`: the scope imports UI (toast, loading) that
reaches config_v2, a contributor, so the slots there would be a cycle. Read by
`<DemoScope>` (`demo/scope`), which documents the contract.

Tests: `core/internal/pack.test.ts` — through a real `createBrowserServer`'s
HTTP read, with tuples spelled by the declarations' own codecs (the client's).
