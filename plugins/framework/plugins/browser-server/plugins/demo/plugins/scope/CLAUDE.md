# scope

`<DemoScope scenario>` renders its subtree against a browser server of its own
(`framework/browser-server`), so the unchanged app reads fake data through
`useLive` / `useFetchEndpoint` and nothing reaches the page's real server.
Design: `research/2026-10-14-global-demo-scope-and-pack.md` §2.

```tsx
<DemoScope scenario={{ id: "agent-manager", pack: () => import("./pack") }}>
  …the unchanged app…
</DemoScope>

// a plugin answering its own keys in every scope (web/index.ts contributions;
// `Demo` is declared by the leaf `demo/web`, so config_v2 contributes without
// depending on this scope — which reaches config_v2 through its UI imports)
Demo.Resource({ id: "config-v2", useServe: useConfigDemoServe })
Demo.Route({ route: [markViewed.route, implement(markViewed, () => ({ kind: "not-hibernated" }))] })
```

- **The pack** loads through `use()` under the scope's own `<Suspense>`
  (`<Loading/>` meanwhile), cached per scenario object. A failed import or a
  pack that does not parse (`DemoPackError`) throws to the error boundary.
- **`Demo.Resource`** — `useServe` is called once per scope mount, inside the
  scope's tree, one component per contribution (the `CollectFieldExtensions`
  fold, so every hook keeps a stable position). It returns the serve function
  the server calls when it is built; return a stable function and read
  changing inputs through a ref (a new identity rebuilds the server). To push
  a change, keep what `s.serveValue` / `s.serveCollection` returned and call
  its `notify()` (config_v2's contribution does, when a lazy plugin registers
  a descriptor).
- **`Demo.Route`** — `[ep.route, implement(ep, handler)]`, routed by the
  shared router (a duplicate route key throws).
- **One server per mount**, built in an effect once the pack has landed (so
  StrictMode's remount disposes the first) and disposed on unmount; one
  `browserServerTransport` per server; `<TransportProvider>` +
  `<NotificationsProvider>` around the children.
- **A key served twice** (pack and a contribution, or two contributions)
  throws naming both sources, before the runtime sees it.
- **Unserved keys** fail `loader-failed` (`DemoMissingError`), never as skew.
- **Unmatched `/api` requests** answer `unsupportedEndpointResponse`
  (`fetchEndpoint` throws `EndpointUnsupportedError`, reports nothing) and show
  "Not available in the demo" — at most one toast from a scope while the last
  is still up (sonner's default 4 s, a timestamp, no timer). Other paths 404.

Another plugin's test mounts the real scope from `web/testing` (`DemoScope`)
— unless that plugin is below the scope (config_v2): its in-scope test lives
here instead, `useConfigDemoServe` taken from `config_v2/web/testing`.

Tests (jsdom, the real `NotificationsClient`): `web/__tests__/demo-scope.test.tsx`,
`web/__tests__/config-v2.test.tsx`;
`conversations/plugins/hibernation/web/__tests__/demo-route.test.tsx`.

## Plugin reference

- Description: <DemoScope scenario>: renders its subtree against a browser server of its own, built once the scenario's pack loads — the pack's recorded answers, every Demo.Resource contribution's serves (a plugin answering its own live keys, e.g. config from code defaults) and every Demo.Route handler. Any other live key fails loader-failed; any other /api request is refused as unsupported with one deduped 'Not available in the demo' toast; a pack that fails to parse, or a key served twice, throws to the error boundary.
