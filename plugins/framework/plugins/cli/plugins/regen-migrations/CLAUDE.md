# regen-migrations

`./singularity regen-migrations [--name <slug>]` — throws away this branch's
own migrations and re-runs drizzle-kit generate against the rebased schema.

A branch-local migration is generated as a diff against the schema as it stood
when the branch started. A rebase moves that schema, so replaying the old diff
on top of it produces DDL for a state that no longer exists. Regenerating from
the merged schema is the only correct answer, which is why `push` calls this
right after its rebase.

It is the migration-generation stage of `./singularity build`, reached through
the same `generateMigration` pipeline (`plugins/migrations/cli`) with
`resetMigration: true`. The default slug is `merged_YYYYMMDD_HHMM` in UTC;
`--name` overrides it.

The regenerated `merged_*` file is phased like any schema migration, and since
the reset deleted every other branch-local schema migration, it **claims all of
the branch's data migrations**: the runner applies the push as one group —
expand, then those data migrations, then contract — so a backfill that reads a
column this branch adds, or one it drops, keeps working however far main moved.
See `database/migrations/CLAUDE.md` → **Phased schema migrations**.

The regenerated file **supersedes** the hashes the reset deleted (a
`-- singularity:supersedes` header) when it provably carries the same schema, so
the worktree that built those migrations adopts the merged file on its next
boot instead of re-running its DDL. When that cannot be proved, the command
warns that such a database needs `./singularity db fork --replace`. See
`database/migrations/CLAUDE.md` → **Supersession**.

Two refusals come before the regeneration, both because "reset and regenerate"
is destructive in exactly two ways:

- **A hand-edited branch-local migration.** Every migration's filename embeds a
  sha256 prefix of its own SQL, so content that no longer matches the name is
  proof someone edited it — and regenerating would discard those edits without
  a word. Data migrations (the snapshot-less ones) are exempt: their SQL is
  hand-written by design and their hash self-heals on every build.
- **A published migration changed in the working tree** — deleted, renamed,
  edited, or carrying a filename hash that is not its content's. Published
  migrations (on local `main` or any `<remote>/main`) are immutable by contract —
  deployed databases record their hashes in `__singularity_migrations` — so this
  is always an error. The rule is the migrations plugin's
  `findPublishedMigrationViolations`, the same function the
  `published-migrations-immutable` check runs. It is also what keeps the
  unconditional journal regeneration honest: the journal is derived from the
  `.sql` files on disk, so a deletion would otherwise just quietly lose its row.

"Branch-local" means *not published* (`publishedMigrationBasenames`), so in a
clone the user's own landed migrations and, after an upstream update,
upstream's are both left alone. Both refusals throw when there is no local
`main` to compare against.
