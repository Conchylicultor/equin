# release

`./singularity release --composition <name>` — turn a composition into an
artifact that runs on a host with no checkout, no `node_modules` and no Postgres
install.

`cli/index.ts` is the data-only declaration (loaded on every `./singularity`
invocation); `cli/run.ts` is everything else, reached through the declaration's
lazy `import()` — the staging pipeline, the Tauri wrap, the DMG packaging and
the self-extracting pack. It is the heaviest body in the CLI (`@resvg/resvg-js`
plus a dozen plugin server barrels), which is exactly why none of it is reachable
from the declaration.

## The hermetic child is a correctness boundary

Step 1 spawns a **fresh** `bun bin/index.ts build --hermetic --composition <n>`
process instead of calling the artifact phase in-process. That is not a
convenience — this module statically imports plugin barrels
(`symbolBody`, `runAssetMirrorPrewarm`, `propagateConfigToUser`,
`buildPluginTree`), and ESM imports evaluate before the action body runs, so by
the time `release` starts Bun's module cache has those barrels **frozen**. The
build's `setPreBarrelImportGuard` can then never fire, `generateConfigOrigins`
re-imports stale barrels, and `pruneOrphanedConfigFiles` deletes a
freshly-authored config override. A fresh process is what makes that impossible.
The invariant is enforced process-wide by `cli:codegen-manifests-not-frozen`.
The long docblock at the `[1/5]` step in `cli/run.ts` is the full statement —
read it before moving that spawn in-process.

The child installs the orphan guard, and its ppid is the `release` process. The
guard is therefore inert unless `release` itself dies — in which case the child
exiting, and dropping `.build.lock` with it, is exactly right.

## Every compile sees the composition's registries, not the committed ones

`bun build --compile` bundles everything an entrypoint reaches, npm included,
and some packages cannot be bundled (`playwright-core` requires an uninstalled
`chromium-bidi`). The committed `<dir>.generated.ts` registries list the whole
app, so an entrypoint reaching one bundles every plugin's contributions — the
launcher reaching the unfiltered `deps` registry is how Playwright broke the
2026-10-14 website release. So every compile resolves each committed registry
with a filtered sibling (`compositionRegistryRedirects`, codegen) to the
composition's own, through `registryRedirectPlugin` in
`shared/entrypoints.ts` — matched on the resolved file, applied to every
entrypoint, never wired per call site.

The `release:fixed-entrypoints-bundle` check bundles the launcher, pg-start,
pgbouncer-start and teardown with those registries empty, npm resolved, so what
no composition can shrink fails at build time rather than at deploy time.

## `--platform` help text restates the tag list

`PLATFORM_TAGS` lives in `@plugins/release/core`, whose barrel reaches zod, so a
declaration may not import it (`cli:command-declarations-light`). The `--platform`
help string spells the four tags literally; the closed list still validates the
flag at run time, from `PLATFORM_TAGS` itself, in `resolvePlatformTag`.
