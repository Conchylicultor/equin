# check-thread-safety

Every check in a pass runs on ONE JS thread, so check code never holds it with
per-file synchronous work (`checks/CLAUDE.md`, "The check thread is shared" and
"A check gets its files from `ctx.repo()`, and never blocks the thread").

- `no-blocking-check-work` — in a `check/` folder's code (tests exempt): no
  blocking fs / process call (`readFileSync`, `existsSync`, `statSync`,
  `readdirSync`, `realpathSync`, `openSync`/`readSync`, `spawnSync`,
  `execSync`, `scanSync`, …) made **per item** — inside a loop, or inside a
  function handed to a call (`files.map(f => …)`); one call costs one syscall,
  per file it is the stall. Read through `ctx.repo()` or `node:fs/promises`,
  spawn with `spawnCaptured`. And no direct `maskSource` / `createSourceFile`
  anywhere (a parse helper is called per file) —
  `await maskedSource(…)` / `await parsedTsSource(…)` (checks/core) yield the
  check thread's time slice first and keep the result for the run.

  It sees only the check's own files. Blocking work inside a core helper a
  check calls is still named by the thread watch's `check-thread-stall`
  reports. Existing violations are declared debt in each owning plugin's
  `exempt/index.ts`.
