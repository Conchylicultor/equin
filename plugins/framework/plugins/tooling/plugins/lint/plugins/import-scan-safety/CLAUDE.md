# import-scan-safety

Contributes the repo-wide `no-adhoc-import-scan` ESLint rule: a **global**
RegExp literal that scans for `import … from "…"` / `export … from "…"` / bare
`import "…"` statements is banned everywhere except the `findImports` primitive.

## Why

A hand-rolled import scanner that keeps string interiors
(`maskSource(src, { strings: false })` then regex) also matches an import
statement written INSIDE a string or template literal — a test fixture, a docs
snippet, a codegen template — reporting fixture data as a real import. Route
whole-file static-import scanning through
[`findImports`](../../../../../../../plugin-meta/plugins/parse-utils/CLAUDE.md)
(`@plugins/plugin-meta/plugins/parse-utils/core`): it masks comments/regex AND
strings fully, matches the import structure against the masked text, and reads
each specifier back from the original source by offset. For a construct outside
its scope (`require()`), mask fully with `maskSource(src)` and read the quote
span by offset. A global regex scanning for `import("…")` is flagged too:
`findImports(src, undefined, { dynamic: true })` adds every `import("…")`
(a lazy load or an inline type) with the same masking.

The rule only fires on **global** (`/g`) regexes — the whole-file-scan tell.
Single-statement, anchored parsers (e.g. a trailing `from "…"$` matcher over one
already-isolated statement) are not the footgun and are not flagged. The
exemption manifest (`exempt/index.ts`) contains only `find-imports.ts`, the one sanctioned home
for the scanner shape.

## `no-hand-import-resolution`

An `@plugins/…` specifier mapped onto the repo's `plugins/` directory —
`` `plugins/${spec.slice("@plugins/".length)}` ``, `"plugins/" + …`,
`join(root, "plugins", rel)` of the stripped spec (through a `const` too),
`spec.replace("@plugins/", "plugins/")` — is a hand-rolled import resolver.
Each one guessed extensions, index files and relative specifiers a little
differently, and re-parsed and re-resolved the tree on every pass beside the
plugin-records module graph, which already holds every module's resolved
imports as per-blob records. Read them off the graph (`fileSetImports`,
`fileSetRuntimeReach`, `fileSetClosure`, `fileSetBindings`, or a
`ModuleNode`'s `staticImports` / `dynamicImports`).

A RELATIVE specifier joined onto its importer's directory is the same
resolver: `join(dirname(importer), specifier)`, `posix.join(posix.dirname(f),
spec)`, `resolve(dir, spec)`, `` `${dir}/${specifier}` `` (a call ending in
`join` / `resolve` whose first argument is a `dirname` call or a name ending in
`dir`, or a template appending a name ending in `spec` / `specifier` to one) — flagged as `relativeResolution`.
Heuristic by name: a resolver spelled with neither shape still escapes it.

A specifier the graph has no edge for (an `import type`, a CSS `@import`, a
barrel named as data, a lint rule judging one file) is resolved by the
graph's own resolver, `plugin-records/specifier` (`specifierPath`,
`resolveSpecifier` against any file set, a subset included) — the one
sanctioned resolver.

A specifier read for its own TEXT is grammar, not resolution, and is not
flagged: a plugin id (`spec.slice("@plugins/".length).split("/")`), a barrel
folder, a specifier compared with a pattern. A plugin's DIRECTORY derived from
its barrel specifier is a sanctioned exemption (it names no module file).
