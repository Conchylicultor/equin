# import-closure

`importClosure(root, entry, { dynamicImports })` answers "what does this
entrypoint load?" for any file in the repo. It runs `Bun.build` on the entry and
returns:

- `modules` — every repo module the bundler parsed, i.e. what the Bun runtime
  evaluates (it does no tree-shaking);
- `live` — the subset that survives tree-shaking;
- `external` — every npm specifier reached, with its importers;
- `commandRuns` — the CLI `run` thunks cut under `"follow-except-command-runs"`;
- `importChain(module)` — the shortest chain from the entry to one module, for a
  failure message.

`importClosures(root, entries, { dynamicImports })` measures several
entrypoints in ONE build and returns only the union of their `modules`, with
`importChain(module)` from the first entrypoint reaching it — the same chain
that entrypoint's own `importClosure` names, and `children(module)` — the
modules it statically imports, the build's own edges (resolved lazily,
memoized, shared with the chains) — so a caller can walk the whole graph (the
server-portability derivation's reverse taint). Use it when only the union matters
(the browser-host derivation: 110 member barrels, one build each, was the whole
cost of the guard); `live` and `external` stay per-entrypoint readings.

The full contract lives in the docblocks of `core/import-closure.ts`.

A check that must keep some entrypoint light should measure it with this rather
than grep its imports: the bundler resolves `@plugins/*` exactly as the runtime
does, so the answer cannot drift from what actually loads.

## A check measures over its file set: `fileSetImportClosures`

`fileSetImportClosures(repo, entries, { dynamicImports })` answers what
`importClosures` answers — `modules`, `children`, `importChain`, `external`
(runtime builtins included) — from the plugin-records module graph
(`fileSetClosure`) instead of a `Bun.build`: each module's imports, and which
of its `import()` edges are command `run` thunks (`command-runs.scan.ts`), are
file records keyed by its blob. So a check pass after an edit reads and scans
the edited modules alone; a `Bun.build` re-parsed the whole closure on every
pass (the backend's boot closure, ~5.8k modules: 5–10 s and ~10 CPU-s per
check, per pass). Proven equal on the real tree — modules, edges, chains and
externals, both policies, the CLI bin's 42 cut command runs included
(research/2026-11-12-global-plugin-records-store-layout.md, last section).

**A check reads a closure with it.** `importClosure(s)` stay for what the
graph cannot answer — `live` (the tree-shaken subset) and `commandRuns` — and
for one-off scripts that compare the two
(`plugin-records/scripts/closure-equivalence.ts`). Checks still on a
`Bun.build` per pass: `cli:codegen-manifests-not-frozen` (`manifest-freeze`,
`live` and `commandRuns`), `cli/check`'s bootstrap and declaration checks, the
guards check and the sentinel check.

## Why it is its own plugin

It used to be a private file of `framework/cli/check`, which no other plugin can
import. It recognises a command's `run` thunk by the name of `framework/cli`'s
`defineCliCommand` — a literal in `command-runs.scan.ts` (importing the CLI's
`core` would put it in every scan record's key), held equal to the real name by
`scan-command-runs.test.ts` — so the CLI's `core` barrel must never import
this plugin back.
