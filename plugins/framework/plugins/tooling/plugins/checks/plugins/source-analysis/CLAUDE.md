# source-analysis

Reads code the way a check needs to: which uses a declaration has, what an
import names, what a `const` holds — from the TypeScript syntax tree and the
repo project's own module resolution, **fail-closed**. Design:
[`research/2026-11-12-global-check-source-analysis.md`](../../../../../../../../research/2026-11-12-global-check-source-analysis.md).

Inside a check, get it with `sourceAnalysis(ctx)` from `checks/core` (wired to
`ctx.repo()`, the run-shared `parsedTsSource`, and the root `tsconfig.json`).
How checks use it: `checks/CLAUDE.md` § "Reading code".

## Fail-closed is the contract

Every answer is a `Readout<T>` (`read` | `unreadable`) or a `Collected<T>`
(`found` + `unreadable`). An `Unreadable` names the file, line, source text and
how to write the code so it can be read. A reader never drops one:

- a check reports each as a violation (`formatUnreadable`);
- codegen refuses the whole answer (`failClosed` throws, naming every one).

Never add an API here that answers `undefined` / `[]` / "skip" for something
it could not read — that is the bug class this plugin exists to remove (the
icon scan that skipped `{ ...symbol("x") }` and shipped empty icons).

## Two layers

| Layer | File | Needs | For |
| --- | --- | --- | --- |
| per file, sync, pure | `core/file-uses.ts` | one parsed file + a `TargetResolver` | a cached per-file scan (codegen's `FileScan`, e.g. the icon manifest) |
| cross file, async | `core/analysis.ts` | `SourceAnalysisHost` (files, parse, compiler options) | checks: imports through barrels, identifier → declaration, every use of a target |

- `fileTargetUses(ts, file, resolver)` classifies EVERY reference to a target —
  `call` / `member-call` / `reexport` / `reexport-all` — or returns it as
  Unreadable (passed as a value, shadowed, namespace indexed or used whole,
  default-exported). `literalString` reads one argument.
- `SourceAnalysis.usesOf(targets, candidatesFor)` runs it over the repo: it
  finds every name a target is exported under (re-exports followed to a
  fixpoint), selects candidates through the caller's grep, and resolves each
  file's imports through every barrel. An import that resolves to no repo file
  is Unreadable (it might have named the target).
- `exportedBinding`, `bindingOf`, `initializerOf`: go-to-definition (scope
  aware: parameters, block declarations, hoisted `var`s, catch variables) and a
  `const`'s value — `let`/`var`/parameters/destructuring are Unreadable. A
  destructured export (`export const { f } = runtime`) is a declaration (its
  node the `BindingElement`, whose value `initializerOf` refuses); a name the
  file neither declares nor imports binds `global` (`bindingOf` only — the
  reader decides what a global means); a JSON module binds `external` (data,
  not code).
- `valueReferences(ts, root)`: every identifier under a node that reads a value
  binding (member names, keys, declarations and type positions left out) — what
  a reader feeds `bindingOf` to learn which declarations some code names
  (no-db-backed-notify's loader walk, network/live's registration checks).
- `boundConst(ts, file, expr)`: the `const` a call initializes, through
  parentheses, `as` / `satisfies` / `!` and either arm of a ternary;
  `declarationKey(d)` is a declaration's identity across a run.

## No type checker, by design

Module resolution is `ts.resolveModuleName` with the root `tsconfig.json`'s
options (`readRepoCompilerOptions` parses its `extends` chain with TypeScript
itself), over the run's file set — never a hand-written `@plugins/` rewrite.
No `ts.Program` is built: the repo program exists only inside type-check's
batched worker process, and building one on the check thread is minutes and
GBs. Binding questions do not need types; a check that genuinely needs a type
belongs in a typed lint rule (it runs inside type-check's program).
