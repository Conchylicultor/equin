# table-defs-in-schema-glob

Enforces that every concrete drizzle table definition lives in a file matched by
drizzle-kit's schema glob (`server/**/internal/tables.ts`, `tables-*.ts`,
`schema.ts`, or `schema-*.ts`). drizzle-kit discovers tables by filename glob, so
a `pgTable(...)` — or a table-factory call like `defineLink(...)` — in any other
server file is invisible to migration generation: drizzle treats the table as
dropped and emits a spurious `DROP TABLE` with no error. The glob-matched file
set is enumerated by `schemaGlobFiles()` from **`SCHEMA_GLOBS`**
(`plugins/database/plugins/migrations/core/internal/schema-glob-patterns.ts`) —
the one declaration `drizzle.config.ts` also builds its `schema:` array from, so
this check and migration generation provably scan the same file set (the
`database-migrations:drizzle-config-schema-globs` check proves it). Nothing is
parsed out of the config's text any more: that parse could silently yield a
subset, narrowing this check's domain while it kept reporting green. The set of
table factories lives in the `TABLE_FACTORIES` const in
`check/index.ts` — register a new server-defined factory there (both `name` and
`definedIn`) so the footgun can't be reintroduced silently.

## Imperative-table read handles are exempt

A public table created **imperatively** on boot (`CREATE TABLE IF NOT EXISTS`,
NOT through drizzle — e.g. a derived-tables materialized rollup like
`task_latest_conversation`) must live OUTSIDE the schema glob (drizzle-kit would
otherwise emit a spurious migration for it), yet a loader still wants a typed
`pgTable(...)` READ handle. The footgun this check guards against —
"silently vanishes from migration generation → spurious DROP" — does not apply,
because the table was never drizzle-managed in the first place.

So a `pgTable(<CONST>, ...)` whose **name argument is one of the allowlist's name
constants** is exempt. String-literal table names are never exempt — those go
through the schema glob. To add an imperative-table read handle: add its name
constant to the `IMPERATIVE_PUBLIC_TABLES` record, create the table imperatively,
and pass that constant to `pgTable(...)` in a non-glob file.

The name argument is read from the call's own argument span
(`strayPgTableCalls`: `markerCallSpans` over the fully masked file), never from
the line the call starts on — so the formatter wrapping
`pgTable(\n  MY_TABLE,\n  {…})`, a comment before the name, or the generic
`pgTable<…>(` form all exempt the handle like the one-line spelling.

The identifiers come from **`IMPERATIVE_PUBLIC_TABLE_CONSTS`**
(`@plugins/database/plugins/derived-views/core`) — the keys of the same
single-source allowlist record the `orphaned-db-tables` check reads the values of.
Nothing is parsed out of that module's text: this check used to regex the
identifiers out of the `IMPERATIVE_PUBLIC_TABLES` array literal, one of two
independently hand-rolled parsers of it (the other in
`imperative-create-table-allowlisted`) carrying the same truncation and
prose-hijack hazards as the `drizzle.config.ts` parse deleted alongside it. A
partial parse dropped exemptions and flagged legitimate read handles. The keys are
usable as identifiers because each entry is written **shorthand** (`{ MY_TABLE }`);
`imperative-create-table-allowlisted` proves that invariant by checking every key
names a barrel export holding that value. See
`research/2026-07-29-global-imperative-tables-declared-const-names.md`.
