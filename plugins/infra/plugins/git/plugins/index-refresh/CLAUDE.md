# index-refresh

A checkout's index is git's cache of what its files looked like. When it cannot
vouch for a file, every read re-checks that file by content — and **no git read of
ours may write the index back** (spawn's `GIT_OPTIONAL_LOCKS=0`), so the doubt
outlives the read that resolved it. Two kinds of doubt cost every read:

- **Racily-clean entries** — files whose mtime is not strictly older, in whole
  seconds (Apple git has no `USE_NSEC`), than the index file. A whole-tree write
  (checkout, rebase, switch) leaves thousands: 6,857 in one checkout made each
  `git diff <merge-base>` there 0.6 s warm and 8 s cold, for a branch with no change.
  `countRacyEntries` (core) counts them from the index bytes, no spawn.
- **An empty untracked cache** — every `git status` re-reads every directory.

`refreshCheckoutIndex` fixes both once: `git status` on a private copy, published by
`private-index`'s compare-and-swap under git's own `index.lock`.
`refreshIndexIfRacy` runs it only when the index holds racy entries (waiting out the
index's own second first, so the refresh does not leave them racy again).

Who calls it: `infra/worktree` when it sets a checkout up, and `checkout-watch` on
every checkout it watches — when the watch opens and whenever it hears the index
written — so a checkout being read never stays racy for more than a second or two.
`refreshCheckoutIndex` takes a required `tier` (`CheckoutTier`): `foreground` for a
launch's checkout (someone waits on it), `background` for every other refresh.
