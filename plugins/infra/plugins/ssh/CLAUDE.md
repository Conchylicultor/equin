# ssh

Hermetic OpenSSH client: every invocation dials with EXACTLY the key, host
and pin it is handed (`isolationOptions` in `server/internal/session.ts`,
written once). Read that file's header before touching the option block.

## One-shot vs long-lived

| The work | Use |
|---|---|
| One remote command / one file | `sshRun` / `sshUpload` — a session materialized and disposed per call |
| A long-lived `ssh` (a tunnel) | `materializeHermetic(target)` → handle, `sshTunnelArgv(handle, forwards)`, run the argv under `defineDaemon` |

- **`materializeHermetic(target, { budgetMs? })`** → `HermeticHandle`
  `{ dir, host, argv(program, extra, positionals), learnedHostKey(), dispose() }`.
  The caller owns the scratch dir (key 0600, `known_hosts`) until `dispose()`;
  `argv` throws after it. `extra` lands after the isolation block, and
  OpenSSH keeps the first value of an option, so it cannot override one.
  Without `budgetMs` (no deadline bounds a long-lived ssh), `ConnectTimeout`
  is the 15 s cap. `runHermetic` is this plus `spawnCaptured`.
- **`sshTunnelArgv(handle, [{ localSocket, remotePort }])`** — `-N`,
  `ExitOnForwardFailure=yes`, `ServerAliveInterval=15` /
  `ServerAliveCountMax=3` (a dead peer ends ssh in ~45 s),
  `StreamLocalBindUnlink=yes` (a respawn re-binds over a stale socket), one
  `-L <socket>:127.0.0.1:<port>` per forward. Throws on a socket path that is
  relative, contains `:`, or is ≥ 104 bytes (macOS `sun_path`) — put the
  sockets in `handle.dir` with short names (`d<n>.sock`).
- **Tunnel stderr** has its own vocabulary, `SshTunnelFailureKind` (core):
  the dial kinds plus `forwarding-refused` and `disconnected`, without
  `command-failed`. `classifyTunnelStderrLine(line)` reads a running
  tunnel's lines (a server that forbids forwarding says so per connection —
  `administratively prohibited` — while ssh keeps running);
  `classifyTunnelStderr(stderr)` reads why it ended; `tunnelFailureRetryable`
  says which kinds a respawn cannot fix (auth, host key, forwarding refused).
  A forward's TARGET refusing a connection (`open failed: connect failed`)
  is never a session failure and is skipped — the local client sees it as
  its own connection closing. `isForwardTargetRefusal(line)` recognises it:
  positive evidence the session is up while nothing listens behind it.

## Plugin reference

- Description: Hermetic SSH client primitive: sshRun (one remote command) and sshUpload (one file, over scp) open a session to (host, port, user) with EXACTLY the private key they are given — IdentitiesOnly + IdentityAgent=none + -F /dev/null keep the machine's own agent, config and multiplexed sessions out, so a connection test proves the key it was handed works — and return a discriminated result whose failures are classified from OpenSSH stderr (dns / unreachable / timeout / auth / host-key-mismatch / command-failed / unknown). Both are built from one shared hermetic invocation, so the isolation flags cannot drift between them. Host-key policy is pinned-or-learn with no 'off'; the key is materialized 0600 into a mkdtemp dir removed in finally. A long-lived ssh is built from the same block: materializeHermetic returns a caller-owned handle (the scratch dir with key and pinned known_hosts, its argv builder, dispose), sshTunnelArgv turns it into a forward-only ssh (-N, local Unix socket → remote loopback TCP port, ExitOnForwardFailure, 15 s keep-alives, StreamLocalBindUnlink; socket paths under macOS's 104-byte sun_path, asserted), and classifyTunnelStderr / classifyTunnelStderrLine read its stderr into its own vocabulary (adds forwarding-refused and disconnected; tunnelFailureRetryable in core says which a respawn can fix). An upload lands on a staging sibling and is renamed over its destination, so it can neither fail because the destination is being executed nor leave a truncated file where a working one was.
