# health

Watches this page's connection to its backends and says so.

- **Connection row** — the health report's `connection` row lives in the
  `connection-row` sub-plugin (`plugins/connection-row/CLAUDE.md`), so a
  composition can leave it out alone. `PUSH_STALL_MS` (`web/internal/push-stall.ts`,
  exported) is the stall threshold it and the wedge watchdog share.
- **`ReconnectWatcher`** — the toast when the server restarts.
- **`WedgeWatchdog`** — detects a live-state channel that stopped delivering,
  including a server stalled past the Connection row's threshold
  (`push-stall:<channel>`, one report per channel per episode), and one
  resource's push stuck (`push-stall-resource:<channel>:<key>`, one report per
  resource per episode — each stuck resource is its own bug), and a sub a
  server left unanswered on an open socket (`unanswered-sub:<server>:<key>`
  — per server, `worktree` / `central` / `in-browser`, and per its oldest
  key, so a fix of one key never reads as regressed by another, and a
  browser host's wedge never hides the page backend's under the cooldown).
  Its detail ends with where that server stands on the oldest sub
  (live-state's `describeUnansweredTrail`: read or not, queued for a read
  slot behind which holders, loading, answered and lost on the way back, or
  the server silent on the question).
  A `ws-connect-stalled` the socket owner publishes is judged on this page's
  VISIBLE time (`visible-deadline.ts`): the owner's deadline runs in the
  SharedWorker, which keeps running while the page is hidden or frozen, so
  its `firedLate` cannot see the page's suspension; a handshake that did not
  go unanswered for a full deadline of visible time files nothing (a socket
  still down once the page runs is socket-down's). Time before the page's
  watchdog existed counts as not visible: a worker outlives its pages, and a
  page opened mid-handshake cannot vouch for the seconds before it (a phone's
  background tab left one hanging while its radio woke; the page opened next
  filed it after watching 0.2 s of it).
  **A wedge needs a host that answers.** socket-down, connect-stalled and a
  page-backend unanswered-sub are filed only once `/api/health` gets an HTTP
  answer (any status — `reachHost` in `web/internal/client.ts`). No answer at all means
  the visitor's network (or the whole host) is down: not a live-state fault,
  and a report that could only be delivered after the link came back. Such a
  socket-down restarts its window instead (`socket-down-watch.ts`), so a
  socket still down once the host answers is reported one window later. An
  in-browser server's unanswered sub needs no network and is never gated.
- **`getHealth` / `waitForRestart`** — the `/api/health` client helpers.
  `/api/health` admits a deployed site's **visitor** (`access: { visitor }`):
  every page probes its own host through it, and owner-only it answered a
  visitor 403 — reachable, but blind to the boot instant, so a stall held by a
  server restart filed as a wedge of a running server.
