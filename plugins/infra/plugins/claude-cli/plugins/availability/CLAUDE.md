# claude-cli/availability

Can this machine run an agent right now? Every agent pane and every one-shot
`claude --print` runs on the user's own Claude Code, so the answer is whether
that CLI is **installed** and **signed in**. This plugin owns that answer inside
the running app; `framework/cli/plugins/doctor` asks the same thing at install
and build time.

## The status

`ClaudeCodeStatus` (core) — `ready` / `signed-out` / `missing` / `unreadable`.
`unreadable` means the check itself failed (timeout, crash, unexpected output):
it is rendered as "can't tell", never as a verdict.

The probe (`server/internal/probe.ts`) runs `claude --version` and
`claude auth status --json` (zod-parsed, read whatever the exit code) under
`pickHostEnv` — the same closed environment agent panes and `runClaudePrint`
use, so it answers for the account they would run as.

## Freshness — no polling

The answer is cached per backend (`server/internal/status.ts`) and pushed as
the `claude-code-status` value — the `claudeCodeStatus` `liveValue` (core),
served on the external arm as `claudeCodeStatusServed`
(`machine/internal/status-served.ts`), notified whenever a probe's answer
differs from the last one. There is no placeholder: until the first check
lands, readers see `pending`.

The value and the recheck endpoint are declared `needsMachine` ("Checking
Claude Code") and served from `machine/` — the probe is the computer's CLI —
while the gate API (`assertClaudeCodeReady`, `requireClaudeBin`, …) stays in
`server/`, which other plugins' server code imports. Under a host without the
computer (the demo's browser worker) every reader handles `unavailable`: the
health row is `unknown` with the sentence, Check again is disabled with it as
its tooltip, and `useClaudeCodeLaunchBlock()` adds no block (Launch is gated on
the launch endpoint's own availability). It is re-asked:

- on first read (lazy — nothing probes at boot);
- by the launch gate, when the last answer is not a `ready` younger than five
  minutes (a token can expire and nothing announces it);
- on `POST /api/claude-code/recheck` (the health row's Check again);
- when the user returns to the window while it is blocked (`RecheckOnReturn` —
  installing and signing in happen in a terminal);
- after evidence: `requireClaudeBin()` finding nothing, `claude --print`
  exiting non-zero.

`~/.claude.json` is deliberately not watched: every running agent rewrites it
constantly, and login state lives in the macOS Keychain anyway.

## What consumers use

- `assertClaudeCodeReady()` — the first thing every launch and resume path does,
  before anything is written. Throws `ClaudeCodeUnavailableError`, an
  `HttpError(409)` whose message carries the fix, so every endpoint answers with
  it without knowing about it. Resume paths use `checkClaudeCode()` and return
  the `claude-code-unavailable` resume-blocked reason instead.
- `requireClaudeBin()` — the ONLY way to get the executable to spawn. Looked up
  on every call (`resolveClaudeBin`, infra/paths: a few `stat`s), so an install
  after boot is seen; a missing CLI throws at the spawn site instead of becoming
  a bare `claude` that dies as `command not found` in a pane.
- `onClaudeCodeReady(fn)` — runs when the status turns `ready` after a block.
  The auto-start queue leaves tasks armed while blocked; tasks/server re-runs its
  armed-task reconcile on this.
- web: the health report's **Claude Code** row (critical while missing or
  signed out, expandable to the commands), `useClaudeCodeStatus()`, and
  `useClaudeCodeLaunchBlock()` — the reason a launch control disables itself,
  only for a KNOWN block (loading or unreadable leave it enabled; the server
  gate decides).

The fix commands (`CLAUDE_CODE_FIX`) are the same two lines doctor.sh prints;
`core/internal/status.test.ts` keeps them in step.
