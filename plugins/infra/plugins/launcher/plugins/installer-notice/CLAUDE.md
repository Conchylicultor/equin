# installer-notice

The rules every installer message keeps, and the shape that makes them hard to
break. "Installer" is everything a person meets while installing equin:
`install.sh`, `./equin start` (and the login services it adds), the
prerequisite doctor (`framework/cli/doctor`), and the installer window to come.
"Message" is anything that stops the install, asks for a permission, pauses it,
or leaves something out.

## The five rules (decided by the user, 2026-11-17)

1. **No internal names** — gateway, menu-bar helper, io-health monitor, crate,
   TCC, sandbox, build slot, launchd, PID, bundle… Say what the user gets:
   "an icon in your menu bar", "app shortcuts in your Applications folder",
   "equin's own database".
2. **Say what equin was trying to do, and why it helps the user.**
3. **Say why it was blocked, in the user's terms.**
4. **Say what the user can do now, and what happens if they skip or say no** —
   is it optional, what still works, how to add it later.
5. **Raw technical lines** (error output, permission ids, paths, labels, PIDs)
   **go in the log or the evidence area, never in the message itself.**

Target tone (the approved installer mockup, proto-1794832268-wlybzk): "macOS
blocked equin from adding its apps. With them, equin's apps open in their own
windows and get a menu-bar icon. To allow it, turn on Terminal in Privacy &
Security → App Management. It's optional: skip it and use equin in your
browser."

## The shape (`core`)

`InstallerNotice { title, doing, blocked, now[], ifSkipped, evidence[] }` — one
field per rule, so a message missing one does not compile. `ifSkipped` is
`{ optional: true, stillWorks, addLater }` or `{ optional: false, because }`.

- `defineNotice(n)` refuses (throws, naming each break) a notice whose
  user-facing fields carry an internal name (`INTERNAL_TERMS`), a path, a
  reverse-DNS label or a line break. A `backtick span` (a command to type) and
  a URL are the user's to copy and are not read. Build notices through it, so
  the test that builds one fails before a user reads it.
- `renderNotice(n)` prints the message, then the evidence apart under
  "Details (for a bug report)".
- `plainTextProblems(text)` is the same check for one string: login services
  run it on their `forUser` wording at declaration (`defineLoginService`).

Where TypeScript cannot reach (`install.sh`, `doctor.sh`), the same split is a
function signature: `fail <message> <details>` in `install.sh`,
`miss <what> <why> <details> <fix…>` in the doctor — the raw facts on their own
`details:` line.

Users today: `infra/launcher/login-services` (`appsBlockedNotice`, every
service's `forUser`) and `framework/cli/start`.
