# backend-hold

**Backend down before its data.** A namespace's backend serves against the
database named by the namespace. Dropping that database while the backend runs
(`DROP DATABASE … WITH (FORCE)`) cuts its sessions and leaves it serving against
nothing — it exits 1 and files a backend-exit report, or answers with errors —
and a request arriving mid-drop cold-starts a fresh backend onto the database
being destroyed (report-1794167098-q99s8d).

- `holdBackendDown(ns)` — `POST /gateway/worktrees/<ns>/stop?hold=1`
  (`gateway/CLAUDE.md`): the backend is stopped and traffic gets "held" instead
  of a cold start. Answers a `HeldBackend` only once the gateway confirms the
  hold (or there is nothing to hold: the gateway is down, or the namespace is not
  registered); otherwise throws `BackendHoldError` with nothing touched.
- `startBackend(held)` — a deploy start: cold-starts it on the replaced data and
  releases the hold. A teardown never calls it: removing the namespace's spec
  deregisters it, hold and all.

## The order has no other spelling

`HeldBackend` (`core/`) is a branded type only `holdBackendDown` builds, and
`database/admin`'s `dropDatabase` / `recreateDatabase` take one for a
namespace's database. Every other drop must say `{ unserved, reason }` — a
fork temp, a test's throwaway — so dropping a served database without holding
its backend is a written, reviewable lie rather than a forgotten step.

Callers: composition reset (`build/serve-composition`), namespace reclaim
(`infra/worktree/reclaim`), checkout reap (`debug/worktree-cleanup`),
`./equin db fork --replace` (`framework/cli/db`).
