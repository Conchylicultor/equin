# deps/pin-drift

The health report's **Pinned binaries** row: every dependency declaring a
`pin` (`infra/deps` § Pinned installs — the embedded Postgres's
`postgres-binaries`, PgBouncer's `pgbouncer-binary`) against what main's
checkout declares. A pin never follows a `bun install` on purpose; this row is
what makes "main now declares another version" visible, so someone decides to
switch. Generic: it names no dependency, a new pin shows up with no change here.

## What it compares (`machine/internal/check.ts`)

`pinStatus(dep, { root })` (the engine, read only) for each pinned dependency,
`root` = main's checkout (`getMainRepoRoot` — the gateway runs the daemons'
start scripts from there, so it is whose declaration `pinnedDep` drifts from;
not a worktree's, not main's served slot):

- the pinned install (its version when the source reads one —
  `DepSource.version`; package-copy reads the lock's and the copy's own);
- `running`, the install the live daemon was started from (its
  `<holder>-running` hold) when it is another — a pin moved since;
- what main declares: the same, another (`blocked` = the pin's
  `switchBlocked(from, to)` — Postgres refuses a major), or unreadable.

Not applicable on a release (its bundle sealed the binaries) or a checkout with
no pin.

## Freshness (`machine/internal/served.ts`)

Pushed (`deps.pin-drift`, `needsMachine`), re-read on: every advance of
`refs/heads/main` (main's bun.lock moved — the weekly npm upgrade), and, while
subscribed, any change under the pinned dependencies' own cache dirs
(`deps.pinned` watcher; `env/` ignored) — a `./equin deps pin`, a daemon's
fresh start moving its running hold.

## The row (`web/`)

`HealthReport.Row` `pinned-deps`. `ok` "Up to date with main" (or nothing
pinned yet — the next start pins main's); `attention` naming each lag
("postgres-binaries 18.1.0 → 18.6.0", "… → 19.0.0 blocked", "pgbouncer-binary
still runs 1.24.0, pinned 1.24.1"); `unknown` when a declaration cannot be
read. Expanded (`PinDriftDetail`): per dependency, pinned vs declared, and
either the switch — `cd <main checkout> && ./equin deps pin <id>`, copyable,
applying at the pin's `appliesAt` (nothing restarts) — or why it is blocked. A
Postgres major says no upgrade procedure exists yet; choosing one is the
user's decision — this row never offers to run it.

## The lag's bound (`machine/internal/decisions.ts`)

A pin lagging main is bounded like a dependency hold (`infra/deps` § Pinned
installs, `reviewPin`): past `PIN_LAG_MAX_DAYS` (30) from when the weekly run
first saw it, or past a stay's `reviewBy`, a person must decide. The decision
surfaces in the **weekly Dependency upgrades task**: this plugin contributes
the `pinned-binaries` `DecisionDeclare` source (`updates/server`), whose
`pending(now)` reviews every pin with `record: true` and answers each due one with its two
options — the switch command (or why it is blocked) and the `pin-stay`
command. The task's agent raises one flag listing them and never acts. A
stay in force (`./equin deps pin-stay`, at most 90 days) silences it until its
`reviewBy`; then it is due again — so a lag only a Postgres major could close
comes back at most every 90 days, never weekly once decided.

The lag's clock starts where a lag starts: on main, the `refs/heads/main`
reaction records every pin's review before the row re-reads
(`recordPinReviews`), and the weekly run records again — so it starts even
while an upgrade task is open or the automation is off (it then only goes
unannounced in a task; the row still says "decision due"). A decision-only
task counts as the automation's open task: upgrades wait until the person
answers it (the flag) and the task is closed — on purpose, a due decision is
not left behind.

The row reads the review without writing it: a stay in force is `ok` ("stays
on 18.1.0 until …"); a lag says when it is due ("decide by …"), overdue
("decision due since …") or lapsed. Expanded, each lagging pin shows its
review and the `pin-stay` command beside the switch. The watcher also covers
the `state/deps-pins` records.
