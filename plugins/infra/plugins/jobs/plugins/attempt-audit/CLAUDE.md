# attempt-audit

Files every failed job attempt as a `job-attempt-failed` report, then says
in that same report what happened next: recovered on attempt N, or gave up.

## Every failed attempt is reported, and the report learns its sequel

A retry that succeeds does not explain the failure it retried: it turns a
deterministic bug into a flaky one. So an attempt is reported the instant it
fails, as an `error`, whatever the retry budget says — never delayed until the
run settles, never thresholded, never downgraded once it recovers. What the
report cannot know when it is filed is the run's outcome, so it is filed with
`fate: retrying` (or `last-attempt`) and **restated** when the run settles
(`reports/engine`'s `restateReportOccurrence`): that occurrence's message, and,
while it is the row's newest occurrence, the row's message, `data.fate` and its
bell line. Restating is not a recurrence: no count, no re-alert, the bell's
read / dismissed state and the linked task untouched. The report stays open for
investigation either way.

The message leads with the fate (`Recovered on attempt 2 · worktree.prepare
failed on attempt 1/5: …`), so the bell's one-line cut never drops it.

## How an attempt is linked to its run's outcome

Generic, no per-job code — the parent's queue announces both halves on
`jobAttemptSink` (`jobs/server/internal/attempt-seam.ts`), keyed by the queue
row:

| event | announced by | fate |
| --- | --- | --- |
| `failed` | the desktop dispatch / the in-process row runner, every failed attempt | `retrying` / `last-attempt` |
| `settled` `recovered` | the same, when attempt N > 1 completes or suspends | `recovered` |
| `settled` `dead` | `announceRunDead`, wherever a run dies (last attempt failed, worker died on it, cancelled) | `gave-up` |
| `settled` `superseded` | the stuck-lock sweeper, deleting a row a re-queue retired | `superseded` |

`job_attempt_reports` holds each unsettled attempt's link (row id + attempt →
report id, occurrence instant, payload), because the next attempt often runs
in another process — a deploy restarted the backend between the two. The
settle restates every link of its row and deletes them. A per-row in-process
mutex keeps one row's events in announcement order (a last attempt's link is
written before its death restates it). A link a lost settle leaves is swept
after a day; its report keeps saying `retrying`.

A superseded row's last attempt announces no death (its run is the newer
row's): its link is settled `superseded` when the stuck-lock sweeper deletes the
row, which it does only once that attempt is over — after its `failed` event, so
the per-row order holds. `superseded` says a newer row owns the run; it does
not follow that row's outcome (its own failures are reported on their own).

Accepted residuals: a report shed under host duress replays later as filed and
is not restated; one collapsed into a `report-storm` rollup has no row to
restate.

Before this plugin attaches (boot), and on a host without the reports engine,
the parent files a failed attempt as a plain `crash` server error, as before —
never silently.
