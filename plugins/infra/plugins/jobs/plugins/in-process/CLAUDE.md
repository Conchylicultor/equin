# in-process

The `JobQueue` (`infra/jobs`' host service) of a host without the desktop's
graphile queue — the browser composition and the portable boot test. The
desktop never boots it: it is a host provider, which no composition bundles
(`plugin-meta/closure`'s `hostProviders`), and `jobs#machine` provides the desktop's queue.

- **A row runs in this process when it is due**, through the jobs plugin's
  portable row runner (`UNSAFE_runJobRow`: schema-drift check, the durable
  `ctx`, suspension, failure classification, step/wait-log teardown). No slot
  ladder, no advisory lock, no hold-class deadline.
- **The rows live in the host's own database** (`jobs_in_process_rows`,
  `server/internal/tables.ts`), as graphile keeps the desktop's: a browser
  host's rows outlive the tab (PGlite in IndexedDB), and Reset wipes them with
  the rest. Memory holds the working copy (timers, Debug → Queue's answers,
  `keysInFlight`, `settle`); every change of a row is written through
  (`row-store.ts`, in order per row), and `start()` reads back what an earlier
  process left. The tables exist empty in every other database (one migration
  history); both are excluded from the change feed — nothing reads them live.
- **A `tx` enqueue writes its row in the caller's transaction** and joins the
  working copy at commit (`database`'s `afterCommit`): a rollback drops the job
  with the caller's writes, a commit keeps both — never one without the other.
- **Row ids are uuids**, never a counter restarting with the process: a durable
  run's step and wait logs (in the same database) are keyed by the row id.
- **A `jobKey` collapses onto the pending row holding it** (graphile's replace
  mode): newer payload and due time, same id; the newer row is removed. Rows a
  crash left holding one key collapse again on load, the newest winning.
- **An attempt is counted when it starts**, as graphile counts one at lock: a
  run whose host ended mid-attempt (the tab closed) runs again as its next
  attempt, and one that was on its last attempt is loaded dead and its job told
  (`onDead`, cause `worker-died`) — a run that keeps ending its host cannot loop.
- **Retries** back off like graphile's (`exp(min(attempts, 10))` s); a
  permanently-failed row stays listed `dead` until retried or removed.
- **Scheduled jobs** fire on a one-shot timer to their next due minute (the
  portable crontab reading in jobs `core`), re-armed after each tick — every
  resolvable schedule, since this host is its own instance. Each tick records
  its time (`jobs_in_process_schedules`, graphile's
  `known_crontabs.last_execution`); at `schedule()` a job declaring
  `catchUpWithinMs` gets ONE tick for the latest it missed while no process ran,
  if that is within the window (`_cron.backfilled`); a schedule seen for the
  first time records now and catches up nothing. `refreshSchedules` never
  catches up.
- `createInProcessQueue({ runRow?, store? })`: the suite
  (`in-process-queue.test.ts`) drives the bookkeeping with fake jobs over
  `memoryRowStore()` (a reload = a second queue on the same store);
  `durable.test.ts` proves the database store on a PGlite reopened from disk.

## `settleJobQueue()`: run the queue dry

Exported from the server barrel; what a browser host's demo seed calls between
its steps, standing for "time has passed". It reads the active `JobQueue` and
**throws** unless it is this queue (the graphile queue has no settle).

1. Yields one macrotask first, so rows a just-committed transaction queued
   (`afterCommit`) are in before the first look.
2. Runs every waiting row now, future-dated ones included (a debounce such as
   pages.history's 4 s, a retry's backoff); while a settle is in progress,
   every row armed later — one a run queues, a retry — is fast-forwarded too.
3. Follows the cascade: it resolves on the activity that leaves the queue
   empty, never by polling. A two-hop dispatch (events) queues the child
   before its own row is removed, so the queue is never empty in between.
4. **Rejects**, naming each job, its row, attempts and last error, once any
   row is dead (an earlier dead row too), and when the queue is not started
   (or is stopped mid-settle) with rows left that nothing would run.

Concurrency is unchanged: due rows still run concurrently, as they always do
here. Cron schedules are timers, not rows — a tick not yet due is left alone.
