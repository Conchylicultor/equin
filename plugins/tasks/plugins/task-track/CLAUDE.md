# task-track

Per-task **track** — `main` or `sidequest`. Design:
`research/2026-09-27-tasks-track-main-vs-sidequest.md`.

- **Main**: on a feature's critical path — the feature is unfinished until it
  is done. Chained into the dependency graph and auto-started when an agent
  files them (`add_task` with `track: "main"`).
- **Sidequest**: off the critical path — any follow-up the feature can ship
  without (caveat, bug, cleanup). Being a follow-up never makes a task main;
  only the critical path does. Runs after
  the task it was filed from, is never spliced into that task's chain, and is
  never auto-started by an agent. A human may still arm one from the task
  detail's auto-start picker, and may switch a task's track from the detail
  header's Track row. A supervising agent switches it with `edit_task`'s
  `track` — arming never does, so a sidequest repurposed into critical-path
  work stays a sidequest until an edit says `track: "main"`.

## Storage

The set of tracks is closed, so it is plain data in `core/` (`TASK_TRACKS`,
`TRACK_META`) — not a registry. The `tasks_ext_track` entity-extension table's
`track` column is `enumTextField(TASK_TRACKS, { default: "main" })` with DB
default `'main'`, and holds a row only for a NON-default track:
**absence = main** — the field's declared default, which is also what every
list exposing the track reads for a task with no row. That default is a real
value, not "unknown" — every filing path that does not choose a track (the
draft form, Improve, the chain endpoint, `propose_task`) is main with no code
change. `setTaskTrack(id, "main")` deletes the row.

## Reads

One lookup-only `liveCollection` (`task-tracks.by-id`: `:rows` alone, never
preloaded), bounded by construction:

- `useTaskTrack(taskId)` — point read, exact, a `ResourceResult<TaskTrack>`: `loading` until known (never a
  stand-in "main").
- Nothing reads every track: the sidequest launch list filters `tasks.tree`
  by the exposed track on the server. The whole set (`task-tracks.all`,
  preloaded at boot) was dropped on 2026-11-05 with a key rename, so an older
  tab subscribing `{}` gets `unknown-key`.

No list reads it: the shape EXPOSES the track (`exposes`, served by
`LiveColumns.Expose(tasksTrack)`), so every list whose rows reach a task — the
task list (`taskWindow` is `from: tasksEntityRef`), the conversation lists —
gets a `track` field (id `track`), filtered, sorted and grouped by it, with no
list code. Its presentation (`FieldPresentation.Register({ owner:
taskTrackShape.exposure })`) is the default enum chip in each value's
`TRACK_META` tint and hint.

The track is decided per filing and is NOT inherited by subtasks (it is not a
`TaskLaunchServer` option).

## The CLI read (`cli/`)

`checkoutTrack(worktreeName)` answers the track of the task whose attempt a
checkout is (`track` / `no-task` / `unavailable`), for a CLI process with no
backend: a raw `pg` query on the MAIN database (the checkout's fork would be
stale after a switch). Its table and column names are hand-spelled and pinned to
the drizzle tables by `checkout-track.test.ts`. op-runtime reads it to queue a
sidequest's ops at low host-admission priority, behind the main track.
