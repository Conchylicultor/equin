# orchestration

Building blocks that state and enforce what agents may do inside a task subtree:
`mandate` (a policy on a task covering its subtree, resolved nearest-wins up
`tasks.folder_id`), `tree-digest` (what an agent is shown of that subtree; each
line's words are `TreeDigest.Annotation` contributions) and `watch` (events in
a subtree reach the nearest live watcher, as one turn per batch).

## The one rule: names no workflow, automation or track

Everything under this umbrella is **workflow-agnostic**. No plugin here may name
a specific workflow (interactive, push-and-exit, …), an automation (autopilot,
report investigations, …), a track (`main` / `sidequest`) or a capability. They
own generic registries and resolution; each capability is declared and described
by the plugin that owns it (`Mandate.Capability`) — a plugin here may declare
its OWN capability (`watch.children`), never another's — the same goes for
digest words (`TreeDigest.Annotation`), watch sources (`watchSource`) and code
watchers (`WatchHandler`), and named compositions of
grants live outside, in `tasks/mandate-presets`. If code here needs to know about
one of those, the abstraction is leaking — redesign the generic API instead.

Plans: `research/2026-10-28-tasks-mandate-building-block.md`,
`research/2026-10-28-tasks-watcher-report-building-block.md`.
