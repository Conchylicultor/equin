# policy

The mandate's value types (`defineCapability`, `MandatePolicy`, `mandatePolicy`,
`MandatePolicySchema`), as a leaf of its own.

**Why a leaf.** `tasks-core` stores a policy (the `tasks.mandate` column, decoded
by `MandatePolicySchema`), and the mandate's server half resolves it through
`tasks-core` (`nearestMandate`). Both in one plugin would be a
`tasks-core → mandate → tasks-core` cycle; this leaf imports only `zod` and
`packages/zod-parser`, so both sides import it.

- `defineCapability<T>({ id, schema, label })` → `Capability<T>`; its
  `grant(value)` parses the value now, so a bad grant throws at its author.
- `mandatePolicy(grants, { root?, below? })` is the only way to build a
  `MandatePolicy` (branded). `grants` cover every conversation in the tree;
  `root` only the conversation on the mandate's own task, `below` only those
  on the tasks under it (stored as `@root` / `@below` sub-records — a
  capability id cannot start with `@`). A capability granted twice where both
  would cover one conversation throws; once to `root` and once to `below` is
  fine.
- `MandatePolicySchema` checks the record's shape only; each value is parsed by
  its capability's own schema where it is read (`grantOf`, mandate server).
