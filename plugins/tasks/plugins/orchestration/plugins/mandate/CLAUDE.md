# mandate

A **mandate** is a policy on a task stating what an agent may do inside its
subtree. It is resolved **nearest-wins** up `tasks.folder_id`: a task with no
mandate of its own works under its nearest ancestor's. Every root task states
one (`tasks_root_has_mandate` CHECK, and tsc on `CreateTaskInput`), so every
task resolves to a policy. Plan:
`research/2026-10-28-tasks-mandate-building-block.md`.

## Pieces

- **Policy types** — the `policy` leaf (`plugins/policy/core`):
  `defineCapability`, `mandatePolicy(grants)`, `MandatePolicySchema`, and
  `defineMandate({ id, label })` → `MandateRef`, the only spelling of a named
  mandate.
- **Named mandates** — the `definitions` sub-plugin (portable):
  `MandateDefinitions.Definition({ mandate, policy })` (what one named mandate
  grants) and `MandateDefinitions.Source({ id, definitions })` (a runtime
  family — one per automation), read at every lookup
  (`mandateDefinitionEntries`; an id defined twice throws), and the
  `mandate.definitions` value (id + label of each).
- **Storage** — a task NAMES its mandate: `tasks.mandate_ref` (server-only, off
  the wire and off `tasks_v`), with `nearestMandate` / `setMandate(taskId,
  ref)` / `clearMandate` in `tasks-core`. `clearMandate` refuses on a root; a
  re-file to the root (`prepareRefile`, shared by `updateTask` and the drag
  move) copies the ref the task had. Never the grants: a change to a
  definition reaches every tree under it, running ones included.
- **Effective mandate** — tasks-core's `tasks_ext_mandate`: every task's
  nearest `mandate_ref`, kept exact in the same transaction as each write that
  moves it (`refreshEffectiveMandates`; re-derived whole on boot), exposed as
  the `mandate` field (Mandate: Interactive / Supervisor / an automation's) of
  every list whose rows reach a task — filter or group by it.
- **Capabilities** — declared (core) and described (`Mandate.Capability({ cap,
  describe })`, server) by the plugin that owns the behaviour. This plugin names
  none of them.
- **Enforcement** (server):
  - `mandateOf(taskId)` → `{ kind: "found", rootTaskId, mandateId, policy } |
    { kind: "none" }` — the nearest ref, resolved to its definition's policy
    NOW. A stored id nothing defines throws (never "no powers").
  - `grantOf(cap, conversationId)` → the parsed value, or `null` when not
    granted — the whole-tree grant, or the one scoped to where the
    conversation sits (`root`: on the mandate's own task; `below`: under it); a stored value the cap's schema refuses **throws**. Concurrent
    calls for one conversation collapse (`createInflight`), since every gated
    tool's `when` runs on each MCP request.
  - `granted(cap)` — an `Mcp.tool` `when` gate.
  - The `mandate` system-prompt section (`SystemPrompt.Section`,
    `conversations/system-prompt`): `## Mandate` and one `describe(value)` line
    per granted capability whose describe is not `null`. A capability that only
    gates a tool returns `null` — the tool appears only when granted and its
    description states its limits — and so does a value CLAUDE.md already says
    (push / close only when asked). The Mandate holds only what nothing else
    tells the agent (how to pace itself while it watches, a push or close on
    its own initiative).
- **Debug** — `mandate.capabilities` (core, a fixed `liveValue`): every
  contributed capability.

Plan: `research/2026-10-30-tasks-named-mandates.md` (named mandates replaced
the stored grants).

The presets (interactive, supervisor) live in `tasks/mandate-presets`;
automations define theirs through `defineAutomation({ mandate })`.
