# tree-digest

What an agent is shown of the task subtree its mandate covers (the root is
`mandateOf(<the conversation's task>).rootTaskId`). Plan:
`research/2026-10-28-tasks-mandate-building-block.md` § Tree digest.

- **`treeDigest({ conversationId, annotate })`** → `{ text, full } | null`.
  With no `digest_cursors` row for (conversation, root) it is the whole
  subtree, indented; otherwise only the tasks created or changed after the
  cursor. Capped at 40 lines, then `+K more — call task_tree`. Advances the
  cursor to the database clock read BEFORE the tasks, so a concurrent change is
  shown twice rather than skipped.
- **`taskTree({ conversationId, annotate })`** — the whole subtree (capped at
  500 lines), read-only: the cursor does not move.

"Changed" is a task's `created_at` / derived `updated_at`
(`database/derived-updated-at`, see `tasks-core` `touchedBy`), or the
`updated_at` of one of its attempts or their conversations — the facts its
derived status reads. A side-table write (track, auto-start marker) moves none
of them, so it is not a change here.

Names no track or workflow: each line is the task's id, title and derived
status; anything more (track, armed) is the caller's `annotate`. The policy is
`server/internal/digest.ts` over a `DigestStore` port (tested in memory); the
database binding is `store.ts`. The `task_tree` tool, the digest appended to
`add_task` and the `tree-digest` instructions section are `tasks`' (machine).
