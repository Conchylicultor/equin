# task-triage

Triage as a property of **any task**: a read-only agent reads the task against
the main checkout's code and rates it — verdict, MoSCoW **priority**, **type**,
risk, a context for the person, at most one one-click question. Design:
[`research/2026-10-22-tasks-task-triage-card.md`](../../../../research/2026-10-22-tasks-task-triage-card.md).

## Model

- **One row per task** in `tasks_ext_triage` (`core/internal/resources.ts`).
  `state` is the run's — `queued · running · done · stale · failed` — and is
  *stored*, so lists filter by it; no row is **Not triaged** (`null`).
- **Read a row through `parseTriageRead`** (`core`), never field by field: it
  returns the `TriageRead` union, so a result is reachable only in `done` /
  `stale` (and as `previous` while a re-run is in flight or failed). A `done`
  row missing a result field throws.
- **Rank through `compareByTriage`** (`core`): must → should → could → wont →
  untriaged, then oldest filed, then id. Every ranking uses it, so two lists
  cannot drift. Feed it `latestTriageResult(read)?.priority`.
- **The note** is its own extension (`tasks_ext_triage_note`): it exists before
  any run. It is fed to every run's prompt (`{{note}}`).
- **Exposed on tasks** (every task DataView, no list code): `triage` (the
  state), `priority`, `taskType`, `triagedAt`.

## A run

- `requestTriage(taskId, { force })` (server) queues it and wakes the
  dispatcher. A run in flight is left alone; without `force`, so is any task
  that has a row. A triage run's own task is refused.
- `task-triage.dispatch` (singleton, serial) launches queued runs, oldest
  first, while fewer than `concurrency` are `running`. It is woken on every
  request, submit, failure and close — push-based, no polling.
- A run is a `kind: "system"` conversation under the triaged task's own run
  task (`Triage: <title>`, System category, subject kind `task-triage`, reused
  by every re-run as a new attempt), in a `tasks.triage` scratch workspace.
  Read-only comes from the profile's `permissions.deny` (Edit, Write,
  NotebookEdit, Bash): conversations run in `bypassPermissions`.
- The agent reports with `task_submit_triage` (scoped to the profile). The
  task comes from the workspace input, never from the agent. A resubmit
  (a resumed follow-up) replaces the read.

## Failure and staleness

- Launch throws → `failed` (and rethrown). The conversation closes (`done`)
  while `running` → `failed`. The hourly sweep fails runs that have not
  submitted 30 min after starting, and marks reads older than `staleAfterDays`
  `stale` (`old`).
- `tasks.titleChanged` / `tasks.descriptionChanged` mark a `done` read `stale`
  (`edited`) only when the text differs from the read's snapshot — the title
  event also fires on creation and Haiku re-titles.
- The hourly sweep is a schedule, so it runs on **main only**.

## The card (`web/`)

- `TaskDetailSlots.Section` `triage`: the header carries the state chip and
  when (Ran · Started · N ahead), Conversation (whenever a run exists) and
  Re-run (on a current read); the body renders the parsed `TriageRead` per
  state, then the note (autosaved, registered with `useRegisterFlush`) and the
  Approve footer (`automations`' `useTaskApproval` / `useSetTaskApproval`) —
  approvable whether or not triage ran.
- Not known yet renders loading everywhere (the read, the note, the approval):
  never a "Not triaged" or "Approve" stand-in.
- Chips come from the vocabulary's option meta (`OptionBadge`), the same meta
  the exposed list fields present (`FieldPresentation.Register`).

## Consumers

- `tasks/sidequest-autopilot` queues reads of new sidequests (`requestTriage`)
  and ranks / pre-ticks its launch list from them (`compareByTriage`).

## Plugin reference

- Description: The Triage card in the task detail: the state chip and when it ran (or its place in the queue) in the header, with Conversation (the run's, for follow-up questions) and Re-run; the body per state — Run triage when none, a placeholder while queued or running, the read (Verdict · Priority · Type · Risk, the summary, one question with one-click answers), greyed under a Re-run notice when stale, the error with Re-run when failed — then the person's autosaved note and the Approve / ✓ Approved toggle, which needs no triage. Presents the exposed Triage, Priority, Type and Last triaged fields in every task list, and registers the triage config (its model picked from the live model catalog). Owns task triage: the tasks_ext_triage side-table (one read per task — run state queued / running / done / stale / failed, verdict, MoSCoW priority, type, risk, context, one one-click question) and tasks_ext_triage_note (the person's note, fed to every run). A read goes stale when the task's text changes or after `staleAfterDays`; a run whose conversation closes without a read, or that has not submitted after 30 min, fails. Exposes Triage, Priority, Type and Last triaged to every list of tasks; requestTriage is the API other plugins queue a read with.
