# structure-records

The structure tree as build tooling reads it — the check pass, codegen's
faceted trees, `./equin plugin move` — with each plugin key file's facts a
plugin record, so a pass parses only the key files an edit touched.

## Why

A plugin's node is a function of its folder's membership and of its key files
(`PLUGIN_KEY_FILES`: the four runtime barrels and `package.json`). The reading
build (`plugin-tree/core`'s `buildPluginTree`) read and parsed all ~3.8k of
them on every call, and a check pass built the tree three times — once for the
checks (`buildStructureTreeOnce`), once inside each of codegen's faceted trees
(barrel-free, enriched): ~11.6k reads and ~0.5 s of parsing per pass,
whatever the edit (measured 2026-11-13).

## How

- `key-facts.scan.ts` — a `FileFold` (plugin-records § Folds): a key file's
  facts (`parseKeyFile`: a barrel's own `export default { … }` fields, a
  `package.json`'s description and plugin flags) keyed by its blob, folded
  along the directory tree. An unchanged tree is one lookup; an edit re-parses
  the edited key files. A barrel whose description cannot be read throws from
  the scan, so it fails every pass, stored or not.
- `buildRecordedPluginTree(pluginsRoot, { repo })` — membership from the set
  (`findAllPluginDirs`), facts from the fold, linked by core's
  `assemblePluginTree`. The same tree as `buildPluginTree`: pinned by
  `recorded-tree.test.ts` over the real checkout, and by edits that must
  re-answer (a barrel edited, removed, a package flag set).
- `buildStructureTreeOnce(pluginsRoot, repo)` — the one structure tree a check
  pass shares (frozen; see plugin-tree's CLAUDE.md), built through the above.

Not in `plugin-tree/core`: that barrel is in the serving backend's closure
(the watcher-kept `StructureIndex`), and the record store is build tooling — it
loads record jobs by computed path, which `boot:closure-digestable` refuses.
