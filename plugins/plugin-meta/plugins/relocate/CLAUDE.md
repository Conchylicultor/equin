# relocate

`./equin plugin move <from> <to> [--dry-run]` — moves or renames a plugin
and every descendant in one step. Design:
[`research/2026-09-23-global-plugin-relocation.md`](../../../../research/2026-09-23-global-plugin-relocation.md).

## What it does

1. **Refuses** in the main checkout, on a dirty tree that holds anything but
   earlier uncommitted moves (`--dry-run` only notes it — see *Chaining moves*),
   when `<from>` is not a plugin, `<to>` exists, `<to>` sits inside
   `<from>`, `<to>`'s parent is neither `plugins/` nor an existing plugin, or
   `config/<to slash path>` exists.
2. **Locates before moving**: `findPluginRefs` (plugin-refs) over the repo file
   set, and `findPluginMentions` of the moved plugin (its path and dot id
   written anywhere in free text). Both carry old paths and old offsets, so
   nothing is read after the move.
3. **Plans** (`cli/internal/plan.ts`, pure, unit-tested): for each ref,
   - path ref inside the moved subtree → swap the dir prefix;
   - dot ref inside it → swap the id prefix;
   - relative ref whose source OR target moves → resolve against the source's
     old location, map the target through the move, re-relativize from the
     source's new location (`./` kept where it was written, and always for CSS
     — a bare `@import` is a package);
   - a **path mention** no ref covers (a comment, a message, a fixture, a
     specifier held as data) → swap the dir prefix; an **fs-path mention**
     (`a/plugins/b`, a registry lookup's spelling) → swap the fs-path prefix;
   - a **dot mention** no ref covers → left as written and listed under REVIEW.
     A dot id can be a stored identity (a job name, a config key, a row's
     plugin id); renaming it in code would orphan what is stored under it, so
     each one is a decision: rewrite, migrate the data, or exempt.

   Edits apply back-to-front per file; overlapping ranges or a range that no
   longer holds its value throw. Derived files are never edited — a build
   rewrites them from their source: `*.generated.ts`, `bun.lock`, and config
   snapshots (`*.origin.jsonc` / `*.ancestor.jsonc`; the compositions origin's
   ids are rewritten in its `defineConfig` source instead). In `research/` only
   links are.
4. **Applies**: `git mv` the plugin dir and `config/<old slash path>` (if
   tracked), writes each rewritten file at its new path, and re-derives every
   moved `package.json` `"name"` (`packageNameFor` + codegen's
   `withPackageName`) so no install sees a stale or duplicate workspace name.
5. **Reports**: per-kind edit counts and per-file edits; `@source` globs that
   covered the old location and will not cover the new one; the namespaces
   whose saved settings sit under the old
   slash path; the `plugin_health_reviews` ids that orphan.
6. **Records the move** in the committed ledger `core/plugin-moves.json`
   (`appendPluginMove`), in the same diff as the code.

Then: `./equin build` (registries, docs, CLAUDE.md autogen blocks,
`bun.lock`), then `./equin check` — the same checks validate the refs the
mover rewrote, so anything it missed fails there.

## Nothing names a moved-away plugin

`relocate:moved-plugins-unnamed` (`check/`) reads the ledger and, for every
entry whose old directory is not a plugin again (no tracked `package.json`
there — a reused name belongs to its new owner), fails on:

- any **mention** of the old path, fs path or dot id (`findPluginMentions`) outside
  `research/` and derived files — what the mover only reported, and what
  arrived after it;
- any **file under the old directory** — work that landed on the old path
  after the move.

Both are what a rebase brings: a main commit that adds a file under a moved
plugin's old path either lands there or is carried by git's rename detection
into the new directory with the old names still inside it. A name kept on
purpose (the ledger itself) is exempted by its plugin's `exempt/index.ts`.

## Chaining moves

Several moves can share one diff. Each move records the paths it touched — both
sides of every moved file, every rewritten file, the ledger, and `bun.lock`
(the next `./equin` reinstalls from the renamed workspaces) — in
`<git dir>/equin-plugin-moves-touched.json`, keyed by its ledger entry. The
next move accepts a dirty tree only when every dirty path
(`git status --porcelain -z --untracked-files=all`) is one that an uncommitted
ledger entry (in the working ledger, not in HEAD's) recorded. Any other edit
still refuses, and is named. The record sits in the git dir, not in the
committed ledger: it describes one uncommitted diff and means nothing once that
diff is committed.

## Committed overrides follow the move

A committed override (`config/**/<name>.jsonc`) anchors its `// @hash` to its
origin, and the mover cannot re-stamp it: the origin is regenerated by codegen,
and a renamed key re-sorts in it, so its new hash is unknown until the build.
So the build does it (`restampMovedOverrides`, called from
`build/cli/internal/app-artifacts.ts`): it snapshots every origin before
codegen, and for each origin whose hash changed, re-roots the OLD origin's
reorder keys through the ledger. When that changes a key and yields the new
origin (arrays as multisets), every override anchored to the old hash — base and
`@app/<id>/` scopes — is re-stamped, body untouched. Any other change falls
through to `config-origins-in-sync` and the authored-override `@review` re-mark,
as before. This is why origins must reach the build un-edited.

## Saved settings follow the move

The user's own config (`~/.equin/state/config/<namespace>/`) is not in
git, so no commit can carry it — and a hand-run migration is a step that gets
skipped. Instead every `./equin build` calls `applyPluginMoves` for its
namespace just before it propagates the git config there
(`build/cli/internal/deploy-namespace.ts`). For each ledger entry that
namespace has not applied (recorded in its `.plugin-moves-applied.json`):

- files under `<from path>/` move to `<to path>/`; a file already at the
  destination wins and the source stays, where the orphan audit flags it;
- every saved reorder key `"<from…>:<id>"` in any of the namespace's files is
  re-rooted, found by the same `scanReorderItemRefs` the git-layer rewrite uses;
- every rewritten default gets its new `// @hash`, and each override anchored to
  the old hash is re-stamped, so overrides stay in force instead of going stale.
  A rewritten origin that is the checkout's git-layer document but for order (a
  renamed key re-sorts in the regenerated catalog) takes that document's hash —
  the one propagation stamps next — so the re-stamped override survives
  propagation instead of turning into a conflict.

The marker, the fresh-namespace rule and the hash re-stamping are the shared
config ledger's (`config_v2/plugins/ledger`), which config migrations
(`defineConfigMigration`) ride too.

So a namespace's settings change exactly when its code does: the worktree that
moved the plugin on its next build, main on its auto-build after the push, new
worktrees by forking main's already-migrated dir, older worktrees when they
rebase. Entries are keyed by `at from to`, so a later plugin reusing an old id
is never swept along, and a namespace created after an entry records it without
moving anything.
