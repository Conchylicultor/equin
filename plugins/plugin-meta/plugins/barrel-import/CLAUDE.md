# barrel-import

## What is stubbed and why

- **React is real.** `react`, `react/jsx-runtime`, `react/jsx-dev-runtime`,
  `react-dom` and `react-dom/client` load unstubbed (once per process, ~50–75 ms).
  A hand-kept React export list broke the build every time web code imported a
  name it lacked, since a static named import is bound at link time. Consumers
  only read plain contribution/slot data, never fake React semantics. The fake
  `window` must not gain a `document`, so react-dom stays on its no-DOM path.
  `core/stubs.test.ts` pins this down.
- **`AUTO_STUB_PACKAGES`** are stubbed for cost (recharts) or CJS/DOM conflicts,
  with their exports derived from each package's `.d.ts` (`barrel-stubs-in-sync`
  enforces the generation).
- **CSS files** become empty modules (`onLoad(/\.css$/)`).
- **No hand-written export lists.** A package is either loaded for real or
  stubbed from its own `.d.ts`; `web-sdk/core` and `database/server` load for
  real for the same reason.

## One import at a time

`importBarrel` admits a single import process-wide (a `createSemaphore(1)` lane).
Barrels import barrels, so the module graph has cycles, and ESM answers a dynamic
`import()` for a module already being evaluated with its *partial* namespace — a
reader that then touches `default` gets `Cannot access 'default' before
initialization`. That only needs two import loops overlapping, and this process
has ~7 of them (the two scoped slot-declaration passes, the docs tree,
`token-group-vars`, `config-origin`, `registrations-paired`, the page checks)
running under the check runner's `Promise.all`. The lane is what makes any pair
of them safe; the second one through finds the ESM cache warm, so it costs
essentially nothing. See `research/2026-08-20-global-slot-naming-witness.md`.

## Each import yields, and is marked

Inside the lane, every import is followed by a macrotask yield. A loop over ~800
barrels used to evaluate them back to back and hold the thread every other check
shares for seconds; yielding inside the lane keeps import order intact.

Each import also runs as a `barrel import` thread activity
(`withThreadActivity`, `infra/stack-sampler`), detail = the repo-relative barrel
path. Loading a module leaves no JS frame on most stack samples, so without the
mark the check-thread watch could only call that time `native (anonymous)`.

## A barrel loads as a function of its code (the load guard)

`importBarrel` imports every barrel through a generated wrapper
(`core/internal/load-guard.ts`): `import "<enter>"; import "<barrel>";
import "<leave>"`. ESM evaluates a graph's new modules depth-first and
synchronously, so between enter and leave runs exactly the top-level code of
the modules this import evaluates — never a concurrent check's work while the
import loads files (AsyncLocalStorage does not reach module evaluation in Bun,
and stack frames do not mark top-level code, so the span is how it is told
apart). Inside the span:

- a `timed-fs` call (`installFsCallGuard`), a `process.env` read or listing,
  and `process.cwd()` throw `BarrelLoadReadError`, naming the read and the
  module that made it;
- except the declared load inputs, whose values `barrelLoadInputs()` returns
  and plugin-records' evaluator key folds in: `NODE_ENV`, `EQUIN_DIR` and the
  resolved data root (decided before the first span), `EQUIN_PG_PORT`,
  `EQUIN_PG_SOCKET_DIR`, `EQUIN_MIGRATIONS_DIR` — import-frozen constants of
  the machine or the install, the same for every process sharing a store;
- and except reads a package makes (the innermost frame is under
  `node_modules/`): a package's code is pinned by the lockfile, and how it
  probes its host as it loads is not ours to change.

Why: an evaluated record is keyed by the barrel's code; any other load-time
input would be served stale to every checkout. Every barrel import is
guarded, not only a record's, because a module evaluates once per process,
under whichever import reaches it first.

Not seen (the daily `plugin-records.verify` still catches what slips):
`Bun.env` / `import.meta.env` (not replaceable in Bun), untimed reads
(`Bun.file`, `require("fs")`), other host reads (`os.homedir`, a spawn), a
package's reads, modules evaluated before the first barrel import, and the
top-level code after a top-level `await` (the graph suspends there and the
span closes, rather than staying open over other code — pinned by a test).

The barrel is resolved with `Bun.resolveSync` before the wrapper imports it: a
static import answers from the resolver's cached directory entries, so a
barrel written after its folder was first read would not be found.
