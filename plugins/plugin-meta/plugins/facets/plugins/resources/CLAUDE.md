# resources

Extracts the live-state resources each plugin SERVES from its `server/` and
`central/` directories. Data is `{ server: ResourceDef[], central: ResourceDef[] }`.

`extract` reads the plugin's own files only (its result is a plugin record,
keyed by them — a read outside throws under the strict snapshot). So a register
call serving a descriptor IMPORTED from another plugin's barrel
(`serveValue(modelCatalog, …)` with `modelCatalog` from
`@plugins/conversations/plugins/model-provider/core`) is left unresolved:
`extract` records it in `raw.imported`, with the plugin's own descriptor index
in `raw.descriptors`, and `relate` — which sees every plugin's data — resolves
each against the index of the plugin it imports from, adds what it serves, and clears
`raw`. A change to the other plugin's descriptor re-extracts that plugin, and
the next `relate` picks it up.

A resource is declared at a descriptor factory call (`core/`/`shared/`, carrying
the key, keyed-ness and bounded membership) and served at a register call
(`server/`/`central/`) that references it. Which calls count is NOT decided here
— both name sets come from `network/live/resource-vocabulary/core`, whose
key set `tsc` derives from the live-state / query-resource / network/live
barrels themselves.

The scan RESOLVES OR THROWS: a descriptor identifier bound in the file but
matching no descriptor raises, naming file, line and identifier (in `relate`
for one imported from another plugin). Only an unbound
identifier (a function parameter, i.e. a runtime value) is dropped. Silence there
is what let ~10 plugins' resources go unreported — an unrecognised factory reads
exactly like a plugin that declares nothing.

The flat register form `defineResource({ key, mode, … })` follows the same rule.
Its `key:` is either a string literal or `<descriptor>.key`, and the descriptor
is resolved exactly like the descriptor form's argument. Any other non-literal
key throws. Until 2026-09-23 this branch dropped every `X.key`, which hid 14
resources (all of Sonata's, the page editor's and links', and two data-view ones).

The delivery mode is read, never guessed. A keyed descriptor passed as the
first argument is `keyed`; a `serveValue` is `push`, or `invalidate` when its
`liveValue` declares `load: "on-demand"` (or `"snapshot"`) — except a
`paged` value's, whose pages are `keyed` (a window) and whose `:meta` sibling
(declared `paged.meta`) is `push`, as the vocabulary's `liveValue` mints say
(a paged `load: "snapshot"` value's pages and meta are both `invalidate`); `serveCollection`'s
`:groups` is `push`. Everything else is an old form (`defineResource` /
`defineExternalResource`) — the flat form, or the two-arg form over a non-keyed
descriptor — and must show a literal `mode:` in its options object (read at
that object's own depth, so a loader's object literal never counts). The runtime
has no default, so a missing or non-literal one throws, naming the call.

An external `serveValue`'s declared freshness is read too: its options' own
`changes:` — the literal `"notified"`, or the one key of an inline
`{ immutable | fixed | snapshot: … }` — rides the resource as `changes` and
reads after the mode (`icons.resident-sprites` (push, fixed),
`heap.stats` (invalidate, snapshot)). Anything else there throws.

A value's list bounds are read at its DECLARATION: every `list-bound` marker
(`wholeList` / `wholeRecord` → `whole: <reason>`, `cappedList` /
`cappedRecord` → `capped: <max>` as written) in the declaration's args and,
transitively, in the initializer of each column-0 `const` of its plugin the
text names, ride the resource as `lists` and read after the freshness. A
marker inside a schema imported from another plugin is not seen; a `reason:`
that is neither a string literal nor the name of a module-level `const` of
one (a reason several lists share) throws. The markers are the only source: a serve call
names no bound (`research/2026-10-22-global-live-bounds-independent-of-freshness.md`).
