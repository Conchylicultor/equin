# boot-monitor

Time-to-ready boot monitor — the producer that makes a **slow server boot** a
first-class slow event: one `slow_ops` row (`operationKind: "boot"`,
`operation: "server-ready"`) plus one coherent trace (`kind: "boot"`, section
validated by `debug/trace/boot`) per boot that took longer than
`readyBudgetMs` to become ready. Follows the one-signal-one-plugin
debug-monitor precedent (`stall-monitor`); the job copies `boot-budget`'s shape
(per-worktree minute cron, `dedup: "singleton"`, `maxAttempts: 3`, module-level
per-boot dedup — process lifetime = boot epoch).

**Division of labor vs `boot-budget`:** boot-budget answers "*which hook* is
heavy" (one deduped report per over-budget span, per-phase budgets); this
monitor answers "did *this boot* take too long to become ready" (one aggregate
row + trace, one `readyBudgetMs`). Neither replaces Debug → Boot Profile, the
always-on deep-dive — this is **trip-only**: boots ready within budget mint
nothing.

Key mechanics:

- **The trip metric is time to ready**: `getProfilingData().timeToReadyMs`,
  ms from process start (`performance.timeOrigin` — the clock `boot.jsonl`
  and the gateway measure on) to `markServerReady()`, which stamps it — the
  `onReadyBlocking` barrier done, the flag the gateway hot-swaps on. Never the
  profile's end (`totalDurationMs`): that waits for the settled phase's
  warm-up drain, background work each warm-up's own budget already judges
  (slow-ops). Judging the drain here once filed ~11 s "boots" for a main that
  served in ~2 s (`server-boot`, the fingerprint retired with it).
- **Readiness guard.** Ticks are skipped (not marked) until `timeToReadyMs` is
  set; it is final once stamped, so the first tick after it judges. The
  section carries every span recorded by then (post-ready ones as context).
- **Evidence-first.** `captureTrace` runs before `recordSlowOp` (the documented
  contract in `record-slow-op.ts`), so the row/report carry the trace id.
- **Gateway handoff.** `POST /api/boot/gateway-report` (body =
  `BootGatewaySchema` from `trace/boot/core`, all fields optional for version
  skew; no auth — the gateway dials the unix socket directly, the same trust
  surface as `/api/health/ready`) stores the gateway's spawn/readiness stamps in
  a module-level box the job folds into the section at mint time. The POST
  lands ~100 ms after the proxy swap, the mint at a minute tick, so it is
  almost always present. No POST (older/unrestarted gateway) →
  `section.gateway` is simply absent. The gateway wait is section *evidence*,
  never the trip metric (gateway-version-independent).
