# client-rate

Catches **one browser tab reloading (or navigating) in a loop** — what no
call-count alarm sees. `debug/op-rate` judges each op against its own history,
but a reload loop is spread thin across ops: a tab reloading 34×/hour adds ~280
subscriptions per 5 min in total, only ~34 an hour to each resource key — inside
every op's usual range. Counted per tab, it stands out.

## How it judges

- **Who a client is**: the latency ledger stamps every page load / navigation
  (`latency_ledger_interaction`) with the tab's id (`primitives/scope/tab-id`:
  session-scoped, the same across the tab's reloads) and whether automation
  drives it (`primitives/scope/automation`: `navigator.webdriver`). A tab whose
  storage cannot hold an id (`NO_TAB_ID`, shared by every such tab) is sent as
  no client — unknown, never pooled.
- **The unit is a client-route-hour**: one tab's loads (or navigations) of ONE
  route in one UTC clock hour. A loop repeats where it goes (a reload, a
  redirect ping-pong); browsing goes somewhere new — an agent exploring 30
  different routes in an hour is not a loop.
- **Usual** = the 99th percentile of every client-route-hour over the 7 UTC
  days before today (today excluded: a loop that started today is never its
  own baseline). Page loads and navigations each have their own. Read once per
  clock hour (late posts still land in it).
- **Trips** when a tab's count of one route in the clock hour so far passes
  `baselineFactor` (3) × usual. The hour so far only grows, so it never fires
  early. A job every 5 min (`debug.client-rate-monitor`, per worktree).
- **Warm-up**: under 100 client-route-hours of history a kind is not judged
  (logged to the `client-rate` channel). Rows from before the ledger carried a
  client id belong to no client.
- **Nothing is left out.** Automated tabs (the agent browser, e2e runs) are in
  the history and judged alike; the report marks them.
- **A page that unloads before it settles is still a row**: on `pagehide` the
  collector cuts the load in flight short (censored) before the final flush —
  otherwise a tab reloading faster than its page settles, the worst loop,
  would leave nothing to count.
- One report per (kind, app of the route) — the same loop in a fresh tab lands
  on the same report; it names the tab, the route, and everywhere the tab went
  that hour.

## What it does not see

A loop that opens a **fresh browser** each time (an e2e script, a scheduled
job such as `desktop.fullscreen-budget`) is a new client per load: one page
load per client, by design not a client loop. Its volume shows as page loads
of that route, not as one client's.

## Plugin reference

- Description: Client-rate report renderer: a one-line Debug → Reports summary (how many page loads one tab made this hour, against the usual client-hour, marked when automated), plus the config registration. Per-client page-load judge: a per-worktree job that counts each browser tab's page loads and in-app navigations in the clock hour so far (the latency ledger's interactions, by tab id) and files a client-rate report when one tab is far past what a client usually does in an hour (the 99th percentile of the last 7 days' client-hours) — the reload loop a per-op call-count alarm cannot see. Automated tabs are judged alike and marked.
