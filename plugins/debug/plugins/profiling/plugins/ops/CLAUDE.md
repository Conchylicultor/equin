# ops

Op contention profiling for Debug > Profiling, over the op-store's live
`opsHistory` collection (`op-log/plugins/op-store/core` — the DB fold of
`op-log.jsonl`, 30-day retention). Web-only: no endpoint, no file read. Rows are
projected to op-log's read-model record in the browser
(`toOpRecord(opRowToFoldState(row), now, sleepNow)`), so an in-flight op's span
and open wait grow with `now` (a 5 s presentational tick in the Gantt, 1 s in
the detail — and no tick at all once every op on screen is closed). `sleepNow`
is the machine's sleep clock (`useSleepNowForFold()`,
`infra/host/plugins/machine-sleep/web`), read only while something is in
flight: it lets the fold count a nap since an op's last event as asleep rather
than as work. A closed op's sleeps are stored on its row, so it takes `null`.

## Surfaces

- **Profiling section** (`OpSection`): every op requested in the last 24 h —
  `useLive(opsHistory, { where: requestedAt >= cutoff, limit: OPS_READ_LIMIT })`
  (`opsHistory.window.window.maxLimit`, read off the collection), the cutoff
  floored to 5 min so the subscription tuple is stable.
- **Worktree Gantt** (`WorktreeOpGantt`, exported; the conversation's `/pp`
  pane): two reads. First that worktree's own ops (`where: { opSlug }`); their
  span ± 20 min, floored / ceiled to 5 min, is the window. Then every op
  overlapping the window (requested in it, or completed in it). While one of the
  worktree's ops is in flight the window is open-ended rather than re-keyed as
  it grows.
- **No Gantt read is taken for the history as a set.** Each is newest
  first, at `OPS_READ_LIMIT`: the section's and the worktree window's are time
  ranges stated in their query (the 24 h cutoff, the window); the worktree's
  own read has no time bound but the store's 30-day retention, so a worktree
  with more ops than that starts its span late. A read that comes back full
  draws the newest ops and says it may hold older ones above the chart
  (`LiveOpGantt`'s `capped`; a read of exactly `OPS_READ_LIMIT` says so too —
  full cannot tell "exactly" from "more").
- **Op detail** (`opDetailPane`): `useLiveRow(opsHistory, opId)` — the stat
  grid **Wait / Work / Asleep / Total** (Asleep only when the op slept; the
  four reconcile exactly, off the fold's one breakdown), the timeline with every
  wait and every nap (hatched, titled `Asleep 3h 40m`, or `… (position
  approximate)` when no wake instant placed it), every wait's reason, requeue
  cycle and result, every step, the lane.

## The render model

An op is **one bar** spanning `startMs → startMs + totalMs`, colored by `kind`,
with each entry of `waits[]` painted as an overlay segment at its own true offset
*inside* that span (see `op-gantt`). Waits interleave with real work, and one op
may carry several waits of the same kind (a build re-queues for the host grant
across requeue cycles), so a renderer must handle N segments at arbitrary
offsets. That is also why an op's span is `requestedAt → requestedAt + totalMs`
and **never** `waitMs + holdMs`: that sum omits every work gap between the waits.

The axis is the **wall clock**, so waits sit on their wall fields
(`atMs`/`wallMs`, `waitPlacement`) when present, and every entry of `sleeps[]`
is a hatched **Asleep** overlay painted on top (the shared hatch,
`HATCH_STYLE`/`HATCH_CLASS` from `debug/profiling/web`, also the Timeline's
sampler-void look). Work is `totalMs − waitMs − asleepMs`, never counting a nap.

## Grouping

A row is keyed on the op's `opSlug` — the basename of the checkout root the
writing CLI derived — so a worktree's push, build, check, test and e2e bars land
on one row. A line with no slug (a foreign writer, or one predating the slug) is
filed under its branch, reduced to the bare id (`claude-web/att-x` → `att-x`).

Row labels come from `useConversationTitleBySlug()` (`conversations/web`, the
same lookup the op-status banner uses): the slug is the attempt id, so any
worktree with a conversation in the live lists gets its title; others fall back
to the bare id. `web/internal/op-groups.ts` holds the pure projection.
