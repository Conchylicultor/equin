# gateway-panic

A request handler that **panics inside the gateway** is a report. Before, a
panic in `Proxy.ServeHTTP` was caught by net/http's own recover: one
`http: panic serving …` line through the server's ErrorLog, the connection
dropped, nothing filed. On 2026-11-08 18:21–18:32 main's every request
dereferenced a nil backend (`(*backend).incHTTP`, 240+ times) and nothing
reported it — main, which drains reports, was the thing down.

## Who files it, and when

`gateway/handler_panic.go`. `Proxy.ServeHTTP` defers `recoverHandlerPanic`
first thing: the request gets a 500 naming the panic, `gateway.log` gets it at
error with its stack, and it is written as one `gateway-panic` entry into the
report outbox (`reports/outbox`, the `backend-crash` writer). Main drains it
once it is up — the outbox outlives the outage. `http.ErrAbortHandler`
(net/http's quiet abort, used by the reverse proxy) is let through, unreported.

**Coalesced per site.** The site is the function the panic was raised in (the
frame below `runtime.gopanic` / `runtime.sigpanic`) — the fingerprint. The
first panic at a site is filed at once; the ones after it within a minute are
counted and filed as one entry (`count`, `firstAt`, `lastAt`, the latest
request) when the window closes. A storm files at most two entries a minute
per site, whatever the request rate.

## A cross-language contract

`gateway/testdata/gateway-panic-entry.json` is the entry the Go writer builds
(its test asserts exactly that) and the entry `core/kind.test.ts` parses with
the outbox envelope and this kind's strict schema. The value and stack bounds
are `backend-crash`'s (`CrashLineSchema`, `CrashTailSchema`).

**Takes effect on a gateway restart** (`./equin start --force`): `./equin
build` neither rebuilds nor restarts the gateway.

Literals `gateway-panic` (the kind, the Go `gatewayPanicKind`) and the
fingerprint `gateway-panic:<site>` are persisted — do not rename.
