# service-down

A supervised service that **stops answering mid-session** is a report. The
gateway supervises the daemons listed in `database.json` (embedded Postgres,
PgBouncer); when one dies, every database connection on the machine fails, and
all the user saw before this was the downstream errors — the only record of the
cause was the gateway's in-memory `crashed` state (`/gateway/services`), and
nothing at all when the watchdog's re-start brought it back.

## Who files it, and when

`gateway/service_report.go`. The watchdog (`supervisor.go` `runWatchdog`) is
the one place that sees a service go: its readiness probe fails. It re-runs
the start command once, then files ONE `service-down` entry in the report
outbox (`reports/outbox`, the same writer as `backend-crash`) when the outage
**settles**:

- `recovered` — the start command ran and the probe answered again;
- `crashed` — the start command failed, or the service never answered; the
  service is left `crashed` and is no longer watched (unchanged behaviour).

Settled, not detected: the outcome is evidence, and while the database is down
main could not record the entry anyway. A `crashed` entry waits in the outbox
until main can drain it.

**Generic by construction.** The supervisor knows a service only by its
config, so the payload holds only what every service has: the probe and the
dial's error, when it last became running, the start command's output (fresh
start vs "already running; reattaching" — whether it was really dead), and the
last 60 lines of its own log channel (`services/<name>.log`, its log relay's
file) as of the detection. A new service in `database.json` is reported with
no code anywhere.

A service is a daemon its start command forked, not the gateway's child, so
there is no wait status — no signal, no pid. The report says what was
observed (a failed probe), never more.

Not seen: a crash Postgres recovers from by itself (a backend process killed,
the postmaster resetting) — the socket keeps accepting, so the probe never
fails. Postgres logs that in its own log.

## A cross-language contract

`gateway/testdata/service-down-entry.json` is the entry the Go writer builds
(its test asserts exactly that) and the entry `core/kind.test.ts` parses with
the outbox envelope and this kind's strict schema. The tail bounds are
`backend-crash`'s (`CrashTailSchema`), pinned to the Go constants by its test.

**Takes effect on a gateway restart** (`./equin start --force`): `./equin
build` neither rebuilds nor restarts the gateway.

Literals `service-down` (the kind, the Go `serviceDownKind`) and the
fingerprint `service-down:<service>:<outcome>` are persisted — do not rename.
