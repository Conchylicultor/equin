# browser-recordings

Every headless browser drive an agent makes is recorded, and the recording is
shown under the tool call that made it — the headless counterpart of
Claude-in-Chrome's GIF recorder, with nothing to opt into. Two producers, one
store, one view:

- an **e2e run** (`./singularity run …/e2e/x.ts`, a Bash call): a step per
  Playwright API call, each with its frame;
- a **page-changing `browser_*` MCP call** (`RECORDED_BROWSER_TOOLS`): one step,
  the tab after the call.

Design: `research/2026-10-18-global-browser-recordings-v2.md` (v1, with
Playwright traces: `research/2026-10-17-global-e2e-recordings.md`).

## The store

`<data dir>/<toolUseId | "manual">/<runId>/` — `manifest.json` (`core/`:
`source` e2e|mcp, `steps` with title, timing, error, frame path) and
`frames/<sha1>.{jpg,png}`, full-resolution, one file per distinct picture. Written
only through `plugins/writer` (`openRecording`, node-only so the web bundle
never pulls `node:fs`): frames as they come, the manifest LAST — a run without
one is invisible — then the newest 200 runs are kept. No Playwright trace and
no DOM snapshots: nobody opens them.

## Producers

- **e2e** — `e2e-harness/e2e/recorder.ts` (it owns the browser lifecycle it
  hooks). Steps from Playwright's client instrumentation
  (`browser._instrumentation`, private, asserted at startup; route plumbing and
  the recorder's own CDP traffic filtered out). Frames from a JPEG (q90) CDP
  screencast per page: the recorder keeps only the latest frame, and a step
  takes the one on screen at its end (or painted within 300 ms) — nothing is
  awaited in the script's path. `--no-record` opts out.
- **browser_\*** — `infra/mcp/browser/server/internal/record-call.ts`: after
  the call, the backend asks the host for a `browser_screenshot` of the tab and
  writes a one-step recording; a failed call is recorded with its error.

## How it reaches the tool call

- Bash: the PreToolUse payload carries `tool_use_id`; the guards plugin's
  `e2e-tool-use-id` guard rewrites an e2e command to
  `export SINGULARITY_TOOL_USE_ID=<id>; <command>` (`TOOL_USE_ID_ENV`, guards
  core). A run with no id (a human at a terminal) goes under `manual/`.
- MCP: Claude Code sends the id in the `tools/call` request's `_meta`
  (`claudecode/toolUseId`); `infra/mcp` hands it to every handler as
  `McpToolCallContext.toolUseId`.

## The view

`isRecordedToolCall(name, input)` (core) is the one classification. The
tool-call renderer hosts `JsonlViewerTool.Footer` under every card; this
plugin's footer reads the `browser-recordings.runs` live value for a recorded
call and draws one filmstrip per run (consecutive steps on the same frame fold
into one thumbnail, a failing step is ringed, each run its own image gallery so
the viewer's slideshow plays it). The same strips are gathered as the
conversation's Browser recordings artifact. Pushed: the server watches the
recordings root once (`acquireDirWatch`) and notifies the call whose manifest
landed. Frames are served by host-fs raw.

Not covered: a context a script creates on `harness.browser` directly (not
through `session()`), a run killed before its teardown, and per-action frames
inside one `browser_batch` (one frame per call).
