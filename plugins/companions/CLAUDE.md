# companions

Umbrella for equin's **companions**: the surfaces equin shows outside its own
tab — the OS menu-bar tray (`menu-bar`) and the Chrome extension
(`browser-extension`).

## What a companion is

A thin shell (a native helper, an extension popup) that loads an equin route
(`/home/<companion>?embed=1`, chromeless) and adds a **bridge**: the few
capabilities only the shell has (resize its window, open a URL in the default
browser, read the active browser tab). Everything else — the
sections, the theme, the data — is the page's, so it updates with main like any
other page; the shell rarely changes.

Every companion is a layout over `panel` (the shared primitive): the same
`CompanionPanel`, `PanelSection`, header, footer, `Companion.Status` slot and
`companion` theme. Each companion keeps its own ordered section slot (e.g.
`MenuBar.Section`), so ordering is per companion, in that slot's reorder config.

## The bridge rule

A shell is installed once and may be older than the page it loads. So:

- **A host offers versioned capabilities.** Its `hostInfo()` answers a
  `version` and a `capabilities` record; a method exists only when its
  capability is on (e.g. `menu-bar/core/native-bridge.ts`).
- **The page hides what an older host can't do.** A section that needs a
  capability the host lacks renders `null` (or its plain-browser fallback); it
  never calls a method the host did not offer.
- The page reads the host as a state — pending, absent (a plain browser tab),
  or present — never assuming one before it answers.
