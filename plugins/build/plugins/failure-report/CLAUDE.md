# failure-report

A failed build of **main** is a report: kind `build-failed`, category
`error`, so the Error reports supervisor stream carries it. It gets the
fix ledger with no extra code: `./equin push --fixes-report <id>`, Fixed once
main builds the fix, Regressed if it fails the same way again.

## Filed where the build's outcome is told

`fileBuildFailureReport` (`machine/`) is called from build/machine's
`notifyBuildFinished`, the one place every build's outcome is told: the
supervised job's `onEnded` for a button build, and `onAutoBuildTerminal` for
a convergence-run build (once per run, under its advisory lock). It runs in the
namespace's own backend, and it files only when that backend is main.
Only the `failed` status files. `superseded` (the tree moved mid-build, a
deploy race), `killed` (a signal from outside) and `interrupted` (the process
vanished, e.g. the machine went down) say nothing about the code, and
`buildStatusOf` already tells them apart. A failure on wake carries
the engine's `afterWake` fact like every report.

**Main only.** About 1 in 5 worktree builds fail (85 of 393 over two days),
against 3 of about 170 main builds. A worktree build failing is the agent's own
feedback loop, about unfinished work. Filing those would flood the stream and
the fan-out ceiling.

**No second bell.** The build already rings "Build failed", whose Fix files
the owning Investigate task. The report is filed with `alert: false`. Its row,
count, fix ledger and stream announcement are unaffected.

**The occurrence's commit is the commit the build built**, not the backend's
pin. That commit is the code that failed, and a fix's regression is judged on it.

## Deduped on what failed, not on the run

`buildFailureOf` (`core/`) reads the run's transcript, cut into step blocks by
op-runtime's `parseStepBlocks`:

- the first failed step block gives its label, its failing checks
  (`• <id> ... FAIL`, as tooling/checks prints them) and its first error line;
- with no failed block (a crash or an abort before the verdict), it reads the
  output the run ended in, cut at the verdict banner.

`buildFailureSignature` is the identity: the step, then its failing check
ids when there are any (a check's message varies, its id does not), else
the error line with absolute paths, hashes and numbers normalized away. A
check that fails on 5 rebuilds in a row is one report with count 5.

## The owner is the build's Investigate task

Every occurrence's `url` is the run's page. When a task is filed about a build
run (subject `run:build`, the runs list's and build-fix's Investigate),
task-subject's `TaskSubject.Linked` listener (contributed by build/machine,
which owns the run's route) calls `linkRunReport`. The report whose kept
occurrences include that run takes the task as its `task_id`, and the newest
owner wins. The engine announces only unowned reports, so once owned it stops
reaching the supervisor stream. A task filed before the report landed is linked
at filing time.
