# step-baseline

Compares each of main's builds with its own normal, step by step, and files a
`build-step-regression` report when a step jumps.

Why: on 2026-11-03 main builds went from ~1 min to ~9 min. `artifacts:detect`
alone went from 20 s to 170 s, and nobody was told: the user noticed slow
builds by hand, a day later. The data was in every build profile; nothing
compared it with anything. Most of that week's slowdown was our own code doing
far too much file work even when nothing changed (a build re-reading ~450k
links, a check re-reading 11k files per run), cheap on a warm cache, so it went
unnoticed until a host problem multiplied it. Track: wiki page
`block-ac80ec7c-c265-48e7-81fe-f16efb7b4bf7`.

## What is recorded (no new store)

- **Per step, its duration and its file calls by kind** (stat / readdir /
  read / glob, and the path prefixes most went to), in the build profile the
  build already writes (`build-profile-<id>.json`, `BuildSpan.fs`). The counts
  come from `packages/timed-fs`, which every non-browser file call goes
  through: a span of the build process counts the calls the process made in
  its window; a check span carries its own check's calls.
- **Per check, the same counts** on the check run's `end` record in
  `check-progress.jsonl` (`fs`), counted under the check's own async context
  (`withFsCallTally`), so a standalone `./equin check` records them too; the
  build copies them onto its `check:<id>` spans with `cached`.
- **Waits are marked** (`BuildSpan.wait`): the build lock, the host grant,
  Postgres, the DB fork, the duress hold, and a backend or central adopting
  the deploy or booting. Their length is another party's, so no baseline
  judges them.

Not counted: writes, `Bun.file()` reads, module loading, and calls made in a
Worker or a child process (type-check's worker, vite's builders, git).

## The rule (`core/internal/detect.ts`, `STEP_BASELINE_THRESHOLDS`)

Main's build, after writing its profile, reads main's earlier profiles (the 50
its data dir keeps) and judges itself (`cli/`'s `judgeBuildSteps`). Only a
build that **rebuilt nothing** (`artifacts:build (0 stale)`, 45 of main's
last 50) is judged, against the earlier builds that rebuilt nothing — the same
work. A step fires when, against the median of its last 20 such samples (at
least 5):

| metric | bar |
| --- | --- |
| time | ≥ 3× the median, ≥ +20 s, above the samples' 90th percentile |
| file calls | ≥ 2× the median, ≥ +5,000 calls, above the 90th percentile |

…and **it held**: the same step and metric also fired in the previous
same-work build, against its own baseline. One slow build is a cache miss or a
busy minute (a host snapshot re-taken, the fleet at load 90); a slowdown that
holds is the step's or the host's. It costs one build of delay.

A check answered from the cache is not a step (it did none of its work).
Agent checkouts record but are not judged: a moving branch's few builds are no
baseline. One report row per step and metric
(`build-step-regression:<metric>:<step>`); each build the step stays slow in
bumps its count.

## Thresholds come from the recorded history

`scripts/replay-build-profiles.ts` replays profiles through the detector, each
build judged against the ones before it:

```sh
./equin run plugins/build/plugins/step-baseline/scripts/replay-build-profiles.ts           # main's series
./equin run plugins/build/plugins/step-baseline/scripts/replay-build-profiles.ts --host    # every checkout as one series
```

A checkout keeps only its newest 50 profiles, so main's own from 2026-11-03/04
are gone; agent checkouts that built across the incident still hold theirs,
and `--host` reads them all as one series (603 builds, 2026-10-13 → 11-11, 339
that rebuilt nothing). On 2026-11-11:

- **The incident fires**: every same-work build after the first — 11-03 17:26
  (`artifacts:detect` 157 s vs 1.6 s), 11-04 01:38 (168 s), 11-04 15:46 (226
  s, with `pluginDocs` and `viteBuild`). The first incident build (11-03
  17:25) is the "once" the hold rule waits out.
- **The healthy builds since stay quiet**: 0 of the ~530 builds from the
  fseventsd fix (11-04 16:23) to 11-11, and 0 of main's own 50 (11-10/11).
- One earlier firing, 10-28 12:02 (`viteBuild` 132 s vs 16 s): the week when
  every build's `detect` ran the whole-cache web-artifact prune (84–112 s,
  since moved to an hourly job) — a real regression of the same class.
- Without the hold rule and the wait marks, the same history fired on 30–54 of
  ~150–217 builds a day (host-grant queues, backend boots, host-snapshot
  re-takes).

File calls have no history yet (the counts start with this plugin), so their
bar is set from the incidents they must catch, each far above it: ~450k
readlinks in one step, 11k files re-read per check run. Re-check it with the
replay once main holds counted builds.
