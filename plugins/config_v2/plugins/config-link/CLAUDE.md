# config-link

Affordances that link an in-context surface to its backing config. The premise:
a `config_v2` `ConfigDescriptor` already self-identifies its settings location
through the `ConfigV2.WebRegister` registry (`useConfigRegistrations()` maps every
registered descriptor → `storePath`, and the `settings` plugin's
`configDetailPane` renders one descriptor's editor). So the descriptor *is* the
link — surfacing a "configure this" control needs no new registry and no
per-surface wiring beyond passing the descriptor the surface already reads with
`useConfig()`.

## What it exposes

- **`useConfigLink()`** — returns `(descriptor) => LinkTarget`: the in-app link
  to that descriptor's config nav + detail chain, rooted in the focused app.
  Spread it with `activationProps` (plain click navigates, ⌘/middle-click opens
  a browser tab) or run it with `runActivation`. Resolved when followed, so an
  unregistered descriptor throws loudly at the click, not at render.
- **`<ConfigGearButton descriptor />`** — a compact gear `IconButton` spreading
  `useConfigLink()`'s link (isolated, so its container's click never fires). Drop in anywhere (e.g. the top-left of an expanded panel).
- **`<ConfigPopoverHeader label descriptor />`** — the standard header for a
  config-backed popover: an eyebrow `SectionLabel` + trailing `ConfigGearButton`.
  Swap a bare `<SectionLabel>` for this and the affordance comes for free.
- **`<ConfigMenuHeader label? descriptor />`** — the menu twin of
  `ConfigPopoverHeader`: a sticky header row (optional `SectionLabel` + trailing
  `ConfigGearButton`) for the generic `header` slot on the ui-kit menu chrome.
- **`<ConfigSelectContent descriptor label? />`** — drop-in replacement for
  ui-kit's `<SelectContent>` that bakes a `ConfigMenuHeader` into the dropdown's
  sticky header, so a config-backed `Select` can't render without the gear.
- **`<ConfigMenuContent descriptor label? />`** — the `DropdownMenu` twin: a
  drop-in replacement for `<DropdownMenuContent>` with the gear baked in.

## Convention

Any chip/popover whose body is driven by config should use
`ConfigPopoverHeader` (or drop a `ConfigGearButton`) instead of a plain section
label. A config-backed `Select` / `DropdownMenu` picker **must** use
`ConfigSelectContent` / `ConfigMenuContent` (not raw `SelectContent` /
`DropdownMenuContent`); an inline chip surface with no menu chrome drops a plain
`ConfigGearButton`. This keeps "where do I change this?" one click away from the
thing it configures, consistently, without each surface re-deriving navigation —
and the gear lives *inside* the picker chrome, so it can't be forgotten.

This plugin only *navigates* to config — the `settings` plugin owns the panes
and the editor.
