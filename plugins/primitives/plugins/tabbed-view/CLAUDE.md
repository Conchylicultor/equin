# tabbed-view

The **bespoke-only opaque-view host** factory. `defineTabbedView<ViewProps>(id)`
returns a `{ View, Host }` pair: each consumer contributes its own set of opaque
view components to the per-instance `View` slot, and `Host` renders the active
one beneath the shared switcher chrome. Use it when a surface has a *small, fixed,
bespoke* set of views that pass through caller-specific `ViewProps` (e.g.
conversations' Queue/Grouped/History, debug slow-ops' Local/Cluster) — each tab
host having a *different* set of tabs is exactly why this is a factory, not a
global slot.

Post-`unified-view-switcher` roles:

- The **generic named-instance** role (config-authored N instances per type,
  per-view sort/filter/search) lives in `data-view` + its `view-core` child — not
  here. `tabbed-view` is deliberately the opaque-view escape hatch, not a
  data-surface engine.
- The **chrome** (`<ViewSwitcher>`) and the **device-local active-id**
  (`useActiveViewId`) both come from the `view-switcher` primitive. `tabbed-view`
  owns no persistence logic of its own — it wires `useActiveViewId(id)` into the
  shared switcher, or defers to the caller in controlled mode.

## Per-tab gates and badges

A tab contribution may declare two hooks, called with the host's view props:

- `useAvailable?: (p) => boolean` — `false` ⇒ the tab is not in the strip and
  cannot be active. Same rule as detail-sections: **loading ≠ unavailable** —
  answer `true` while the fact is pending (the body shows its own loading
  state), so a tab never pops in late.
- `useBadge?: (p) => { count } | null` — a count pill after the title.

Hooks cannot run in a filter, so each one runs in its own probe component (the
detail-sections gate technique) that reports into a per-host store from a layout
effect — the host re-renders before paint. On the render before the probes
report, a gated tab counts as shown but **no body is mounted** until every gate
has answered, so a tab that turns out unavailable is never mounted.

## Who owns the active tab

- **Uncontrolled** (neither prop): the device-local `useActiveViewId(id)`.
- **Controlled**: pass `onActiveChange` AND `activeId` (required in that arm,
  `undefined` = none named) — e.g. a pane's `:tab?` URL param. The host never
  writes the device store and never calls `onActiveChange` by itself.

Either way the shown tab is derived: the requested id if it names an available
tab, else the first available one (the request is left as is — a URL naming an
unavailable tab is not rewritten).

## Strip look

`defineTabbedView(id, { strip })`: `"pill"` (default, ghost pills) or
`"underline"` (a tab strip on a hairline, the selected tab underlined — a page's
section tabs). The look is the instance's, not a per-render choice; it maps to
`<ViewSwitcher variant>`.

The strip also decides the scroll model. A pill strip is fixed over a scrolling
tab body (`Column` header / body). An underline strip is a page's: the whole
page — header, strip, tab body — scrolls as one, and the strip pins to the top
as it reaches it (`<Sticky mask>`, a direct child of the scrolled block so it
stays pinned for the page's whole length). A tab body under an underline strip
is therefore in page flow, not a `fill` cell.
