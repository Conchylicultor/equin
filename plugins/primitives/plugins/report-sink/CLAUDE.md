# report-sink

Three module-level sink factories in `core/` (web and server both import
them). Pick by who listens and whether a late listener should still hear it:

| Factory | Listeners | Emitted with nobody listening | A listener throws |
|---|---|---|---|
| `defineReportSink` | ONE handler (`register` replaces) | held (first 100), replayed on register | swallowed — error path |
| `defineRequestSink` | ONE handler, answer returned | `undefined` (the "no consumer" branch) | swallowed, `undefined` |
| `defineObservationSink` | MANY (`subscribe` → unsubscribe) | dropped | others still run; rethrown on a microtask |

- **Report sink** — a primitive's soft *failure* report that one domain plugin
  (usually `reports`) maps to `report()`. Boot-time failures fire before the
  handler's mount effect, so they are held.
- **Observation sink** — a *measurement* (a latency sample) any number of
  consumers read side by side without evicting each other. Nothing is held: a
  measurement matters only to whoever watches now. `hasSubscribers()` lets a
  hot-path producer skip building a body nobody reads. A throwing subscriber
  must not break the producer's path, but stays loud (uncaught on a microtask).

**Who registers, and when.** In the browser a collector registers from its
mount effect. On the server a handler is never `sink.register(fn)` from a
lifecycle hook: it is a `sinkHandlers` entry (`sinkHandler(sink, () => fn)`,
`framework/server-core`), attached by the framework in every boot mode — an
exec child skips `onReady`, so a handler registered there never drained a
supervised job's child. The `report-sink/no-direct-sink-register` lint
(type-aware, outside `web/`) enforces it.
