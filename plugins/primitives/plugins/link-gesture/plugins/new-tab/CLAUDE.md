# new-tab

The new-browser-tab control, in every form it takes, owning the **open-in-new
glyph and the behaviour together** — so the arrow cannot be paired with
anything but "open this in a new browser tab".

"New tab", unqualified, always means a **browser** tab. A tab of the app's own
tab bar is a different thing with a different glyph (`navIcons.newAppTab`,
opened by `navigate(url, { newTab: true })`), and a host file opened with its
default app is a third (`navIcons.hostApp`).

| Form | Use for |
|---|---|
| `<NewTabButton href label? />` | icon-only button (an `IconButton`, ghost) — row actions, pane headers |
| `<NewTabButton href variant?>words</NewTabButton>` | text button, glyph leading |
| `<NewTabMenuItem href label? >words?</NewTabMenuItem>` | menu entry; no children = bare glyph item; `href: undefined` disables it |
| `<NewTabLink href>words</NewTabLink>` | inline text link, glyph trailing (a real `<a>`) |
| `newTabAnchorProps(href)` | a component rendered AS a link (`<Badge as="a">`, `<Button render={<a/>}>`) |
| `<NewTabGlyph />` | the bare mark, only where the CONTAINER opens the tab (a row, a thumbnail hint, an `<a>` chip) |

`href` is an app path of this origin or an absolute URL; the buttons and menu
item also take a thunk, evaluated inside the click, for a destination only known
then; `href: undefined` disables the button or item. None takes an `onClick`: the behaviour is the component. Every click stops
propagating, so a new-tab control inside a clickable row never also activates
the row. Opening goes through `link-gesture`'s `openInBrowserTab` (`noopener`,
plus `noreferrer` off-origin).

**Lint: `new-tab/no-adhoc-new-tab`** (closed) flags every read of
`navIcons.newTab` outside this plugin, dotted or destructured. The fix is one of
the forms above — or, if the control does not open a browser tab, another glyph.
