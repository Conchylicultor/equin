# sortable-list

The one way into `@dnd-kit` for a sortable list: `SortableList` owns the
context, sensors (pointer; keyboard with `keyboard`) and optimistic order;
`SortableItem` owns the node, the activator (`handle` → `handleProps`, ref
included) and the transform.

The transform is `CSS.Translate`, never `CSS.Transform`. With no `DragOverlay`,
dnd-kit scales the dragged item to the rect it is over, so `CSS.Transform`
squashes an item onto a differently-sized neighbour's aspect ratio. It is the
snippet in dnd-kit's own docs and invisible with equal-size items, which is why
it kept coming back. Two lint rules (`lint/`) close it:
`sortable-list/no-scaling-transform` bans `CSS.Transform` everywhere, and
`sortable-list/no-raw-dnd-kit` bans importing `@dnd-kit/*` outside the drag
primitives (this one, rank-reorder, tree, the page editor) — extend this
primitive rather than wiring `useSortable` by hand.

## `DeferredSortableList` — draggable only in a mode

For a list that is sortable only in a mode (reorder's edit mode) and plain the
rest of the time. `SortableList` wraps its items in a `DndContext` and every
`SortableItem` runs `useSortable` (~50 hooks) even while `disabled`; mounting the
context only while enabled would instead put a new ANCESTOR in front of the items
on the flip, and React remounts every subtree whose ancestor changes type.

So the drag host is a **sibling** of the items, not their parent:
`DeferredSortableList enabled={…}` provides a per-list binding store and, only
while `enabled`, mounts a plain `SortableList` whose children are one invisible
registrar per id. Each `DeferredSortableItem` publishes its wrapper `div` by id;
the registrar runs `useSortable` against that node and publishes the drag props
(listeners, a11y attributes, `CSS.Translate` transform, `isDragging`) back for
the item to wear. Disabled, nothing is mounted and the item is a plain box;
flipping never remounts an item. A `DeferredSortableItem` outside a deferred
list throws — no host could ever bind it.
