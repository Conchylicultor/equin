# web-locks

The one answer to "can this context lock?" — a page or a worker alike (`core/`).

```ts
const lockHere = webLocks();
if (lockHere.kind === "supported") void lockHere.locks.request(name, () => held);
else /* decide what this feature does with no cross-context coordination */;
```

- `navigator.locks` exists in every browser of the floor but not in every
  context: iOS Lockdown Mode, some in-app webviews, an insecure or opaque
  origin, some worker kinds. A bare `navigator.locks.request` there throws
  "undefined is not an object" — equin.ai's demo worker on Safari never booted
  (report-1795088221-b1uksj). `webLocks()`'s `unsupported` arm carries no lock
  manager, so a caller must branch, and each feature states its own fallback:
  the demo's host storage serves from memory (`host-storage`), a SharedWorker
  transport runs in the page (`networking`), the stall watchdog runs in-tab,
  presence reads `unknown`.
- `locksRefused(err)`: the browser HAS them but refuses this context (a
  `SecurityError`: site data blocked, a sandboxed frame).
- `web-locks/no-raw-navigator-locks` (lint) flags every other
  `navigator.locks` read and `"locks" in navigator`. A self-contained worker
  bundle that may import no other plugin (the shared-ws and stall-watchdog
  SharedWorkers) is a sanctioned exemption in its own `exempt/`: it is started
  only by a page whose `webLocks()` is supported.
