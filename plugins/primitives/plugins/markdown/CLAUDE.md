# markdown

Shared markdown renderer with slot-based enhancers. Every consumer writes
`<Markdown>{text}</Markdown>` — no props, no wiring. Context-specific
behaviors (active-data linkification, file-link detection, image proxying)
auto-activate via `Markdown.Enhancer` slot contributions.

The `<Markdown>` component reads all `Markdown.Enhancer` contributions,
sorts by `stage` (a processing position, not a visual one), wraps `<MarkdownRenderer>` in each enhancer component
(outermost-first), then renders. Each enhancer stacks transforms and
component overrides into `MarkdownEnhancementContext`; the renderer reads
the accumulated context and merges it with the base component map.

Base components include typography overrides, `remarkGfm`, and
syntax-highlighted code blocks via `<HighlightedCode>` from the
syntax-highlight primitive. Inline (non-fenced) code is the one `InlineCode`
element, whose pad, corners, hairline and type are theme tokens (density
`padCode*`, shape `radiusCode` / `borderCode`, type-scale `*Code`, palette
`codeBorder`) defaulting to its old `rounded-md`, `xs` × `2xs`, borderless
caption look. It has no notion of a span's *kind* (path, keyword, removed
token), so a theme can border every chip but cannot tint one kind.

**`/api` addresses are the page's.** The base `img` and `a` render an
`/api/…` address (relative, or absolute on the page's origin) as plain text
when the subtree's transport serves no URL (`useTransport().servesUrls` —
an in-browser server, the demo), so persisted markdown never loads from the
page's real server inside a scope; an enhancer that can resolve the address
over the transport (`markdown-extensions`' `img-enhancer`: an attachment →
`AssetPath`) overrides them. So `<Markdown>` renders under a
`<TransportProvider>`, like every server-backed primitive.
