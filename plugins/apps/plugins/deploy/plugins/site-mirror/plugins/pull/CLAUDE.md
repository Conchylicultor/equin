# site-mirror/pull

Keeps this computer's copies of its deployed sites' mirrored tables: one
`table-mirror/replica` per (deployment, set), owned by `site_mirror_replicas`
(cascades with the deployment and with the replica; left out of forks with the
replicas). Replica ids are `site-mirror:<deployment>:<set>`.

- **Replicas are created on first ask.** `POST /api/site-mirror/sync
  { deploymentId, setId }` creates the set's replica (the set must be one this
  computer declares) and asks for a pull. Its callers are the consumers' tabs,
  which already gate on the deployment shipping the set's plugin
  (`useShipsGate`), so a replica exists only for a set the site ships.
  Without `setId` it pulls every replica the deployment has.
- **Transport** (`server/internal/fetch.ts`): each page one host-only GET
  through `hostOnlyQueryOverSsh` (SSH, or this instance's own gateway for a
  demo's stand-in box), the question base64url (host-only's encoding), the
  answer capped. A rows request carries a key list: the longest prefix that
  fits `MIRROR_QUESTION_MAX_CHARS` travels and the rest comes back as
  `remaining` — the protocol's own "ask again". Every `HostQueryFailure` is
  handed back as `fetch-failed` and recorded on the replica as-is.
- **`site-mirror.pull`** — one bounded chunk (20 fetches) of one replica,
  keyed per replica (a sync while one waits folds into it), `serial` (two
  pulls of one replica must never interleave). A chunk whose budget ran out
  re-enqueues itself, so a first copy is resumable and no run is long. A
  refusal or transport failure is an outcome, never a throw; a throw is a bug
  and is kept as the owner row's `run_error`.
- **`site-mirror.pull-all`** — hourly, main only (no `perWorktree`): drops
  the replicas whose deployment is gone and every orphan `tm_*` schema, then
  creates every sink set's replica for every deployment, then asks for a pull
  of every replica. No in-process timer anywhere.
- **Sets read through a sink** (`SiteMirrorSink`, `server/internal/sink.ts`):
  a set whose rows must never be stored here (site-reports' untrusted
  visitor errors) is read as a change stream through its owner's sink —
  table-mirror's custom sink, which keeps only the content-free key index and
  hands the sink each row content once. Such a set is kept for **every**
  deployment (the pull-all creates its replica; no tab asks) and is read at
  its contributed `pace` only: one fetch step of at most `rowsPerRun` rows
  per pull, no follow-up chunk, a pull within `minIntervalMs` of the last one
  skipped, and the answer capped at the pace's `maxAnswerBytes`. The sync
  endpoint refuses it by id and skips it without one, so nothing but the
  hourly pull-all adds a pull past its flood bound. Site-mirror never names a
  contributor: the contribution is the whole contract.
- **`site-mirror.status`** (`source: "db"` over the owner rows and
  `table_mirror_replicas`, so every applied page re-pushes it): per set, the
  phase, progress (without keys), whether a whole copy is in place, last sync,
  the box's clock at the last page, the last outcome, `pending` (asked for
  after the last attempt ended) and `runError`.
- **`MirrorFreshness`** (web) — the consumer's header line: "Synced 12m ago ·
  Sync now", "Copying… 2 of 4 tables · 12,000 rows", "Reconciling…", "Not
  synced yet"; a failed pull in host-query's vocabulary
  (`HostQueryFailureState`), and `unknown-set` / `unknown-table` /
  `source-older` as "this site runs an older release — deploy it again",
  above "showing data synced 3h ago". On mount it asks for a pull when the
  copy is missing or more than 5 minutes old. Shown in the Analytics tab
  (collect's `analytics` set, which does not read the copy yet) and the
  Messages tab and card (the intake's `site_messages` set).
- **Reading a copy** (server barrel): `readSiteMirror(deploymentId, setId,
  fn)` runs the set owner's own SQL on the deployment's copy
  (`withReplicaSchema`: `ready: false` until a whole copy is in place; no
  replica yet throws — a consumer reads only once `site-mirror.status` says
  `copied`), and `onSiteMirrorApplied(setId, fn)` is its change signal (any
  deployment's copy of the set applied a page). The inbox
  (`site-messages/inbox`) serves its live window through both.

Tests: `./equin test plugins/apps/plugins/deploy/plugins/site-mirror` (the key
list cut); the engine's own round trips are `table-mirror/replica`'s suite.
