# health

## The verdict, read live

`serverHealthRows` (`shared/resources.ts`) is a `liveCollection` over the
`deploy_servers_ext_health` side-table, served from the extension handle
(`serveCollection(serverHealthRows, { from: serverHealth })` — `hostKeyLine` is
`serverOnly`, so it never reaches the wire). Named `…Rows` because
`serverHealth` is the handle.

The hooks never collapse "still loading" into "never checked" — an absent row
is a claim about the server, and a read in flight cannot make it:

- `useServerHealthMap(serverIds)` — the collection's `:rows` point sibling for
  exactly the given ids, as a `ResourceResult` of `Map<serverId, row>`. The
  caller states which servers it is showing (the release column reads
  the deployment rows' own `serverId`s) — never the bounded default window,
  which would drop a server past its rank cutoff. Combine a still-loading id
  source's `pending` with `useCombinedResources` rather than guessing at it.
- `useServerHealth(serverId)` — `useLiveRow`: `pending`, `found: true` with the
  row, or `found: false` (never checked).
- `useServerVerified(server)` — `"pending" | "verified" | "unverified"`, over
  `isKeyVerified(row, server)`, the one statement of the rule.

Each caller decides what pending shows: the status column and badge show
nothing yet, the sections show a loading state, the Deploy buttons say the
verdict is loading, and the SSH-setup card seeds open.
