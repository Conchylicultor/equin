# intake

Visitor messages, on the deployed box. The website's contact card
(`apps/website/landing/contact`) posts here; the deploy app's
[`inbox`](../inbox/CLAUDE.md) reads the stored messages over SSH. This plugin
knows nothing about SSH or the deploy UI.

**A site takes messages by importing the `web` barrel** (`useSendSiteMessage()`),
never only `core`: a composition's closure follows same-runtime imports, so a
site importing just the endpoint contract would ship the form without this
server half (endpoint, table, notify job). Verified with `resolveComposition`
for `website`.

## The endpoint — `POST /api/site-messages`

- `capBodySize(8 KB)` (from `analytics/host-only`), then a strict zod body
  (`core/internal/message.ts`): `message` 1–5000 chars after trim, `replyTo` an
  email ≤ 254, `honeypot`, `elapsedMs`, and the page's `host` / `page`
  (collect's schemas — the gateway rewrites `Host`).
- Answers `{ kind: "sent" } | { kind: "rate-limited", retryAfterS }`.

## Abuse protection (all server-side)

1. **Rate limit** per visitor (`rate-limit.ts`): 3 per 10 minutes, 10 per day,
   per `ip_hash = sha256(install salt ‖ ip)` (`ip-hash.ts`, Web Crypto; the
   salt is one row of `site_messages_salt`, created on first use). The IP comes
   from `requestClientIp` and is never stored. Every stored message counts,
   spam included. Checked under a transaction-scoped advisory lock on the hash,
   so a burst cannot race past it. Over → `rate-limited`, nothing stored.
2. **Spam** (`classify.ts`): honeypot filled, `elapsedMs < 3000`, or
   `isBotUserAgent` → stored `verdict: spam` with its `spam_reason`,
   `notify_state: skipped`, and still answered `sent`, so a bot learns nothing.
3. **Retention** (`retention.ts`): spam is swept after 30 days
   (`defineRetention`, `perWorktree: true` — a deployed release is never main).
   Accepted messages are kept.

`site_messages` is `ExcludeFromChangeFeed`: public traffic writes it and
nothing renders it live.

## The notification — `site-messages.notify`

Enqueued in the message row's own transaction (`intake.ts` takes the enqueue
as a dependency). `defineJob`, keyed by message, `serial` (so the cap's count
is exact), `hold: "seconds"` (a 15 s timeout on the Resend call), 5 attempts.
`notify.ts`:

- `readDeploySecret(RESEND_API_KEY)` (`apps/deploy/deploy-secrets`) — the key
  is declared in `core/internal/secret.ts` and reaches the box only once the
  user approves it on the deployment's Secrets section. `unset` →
  `not-configured`, nothing thrown: a dev worktree has no key by design.
- **Daily cap**: at most 30 emails in any 24 h. Past it → `throttled`; the
  next email that goes out says how many were held since the last one.
- Sends through `integrations/resend` from `equin <noreply@equin.ai>` to the
  site's `CONTACT_EMAIL`, reply-to the visitor, subject "Website message from
  <replyTo>", plain text (the message, the page, the time).
- A failed send records `notify_error` and throws so the job retries; the last
  attempt records `failed` first.

## The host-only list — `GET /api/host-only/site-messages`

`hostOnly()`, `?verdict=&limit=` (default 100, max 200), newest first,
`{ kind: "messages", messages, hasMore }`. `siteMessagesListPath(query)` builds
the path the inbox curls.

## Tests
