# deploy-history

**History** — every run ever launched for this deployment. Design:
[`research/2026-08-05-global-deploy-pane-test-locally-and-one-button-deploy.md`](../../../../../../research/2026-08-05-global-deploy-pane-test-locally-and-one-button-deploy.md)
(Phase C).

Contributions: the site page's **Deployments** tab (`SiteTabs.View`), a live
`DataView` over `deployRunHistory` (`source={deployHistorySource.scoped({ where:
{ deploymentId } })}` — the deployment is the scope, stated as data); the
Overview's recent-deployments card (`SiteOverview.Card`); and the app-wide
**Activity** page (`activityPane`, a `Deploy.Sidebar` entry) over the same
ledger, unscoped. It owns no state and no
writes — the ledger is the [`deployments`](../deployments/CLAUDE.md) sibling's
`deploy_runs` table, written by the same two functions that write the live
`deploy.runs` map. A run opening, finishing or failing reaches its row through
the routed runtime: no revision tick, no refetch, and the history pages past one
window with no cap. The surface's custom columns sort and filter it server-side
(`deployRunHistory.columnScope` IS this DataView's id, asserted at mount);
`e2e/history-live-verify.ts` drives a custom value through the API and watches
the row drop out, come back and move, and a status flip land, without a reload.

## What this history is for

`deploy.runs` is in-memory, so a backend restart empties it — which is correct
for a *live* view (the spawned CLI is not detached; after a restart nothing is
running) and useless as a record. Before this history the pane simply could not
answer *"what is live on this box, and what happened before"* after a reboot, and
the four-step UI it replaced used to say so in a step note. **The point of this
history is to make that caveat false, not to restate it.**

## Reading the row

- **the outcome names the leg** — `Failed on build` rather than `Failed`, because
  which of `converge` / `build` / `ship` died is the first thing anyone asks and
  the row already knows;
- **the message is verbatim** — it is the CLI's own refusal, carried from
  `deploy_runs.message` with nothing rewritten around it. That is also why the
  list view goes through `renderRow`: the field-driven default joins every
  non-primary field into one truncated subtitle, which would clip exactly the
  sentence this tab exists to preserve. The field schema still drives sort /
  filter / search and the whole table view;
- **the commit can be absent, and that is an answer.** It is filled from the
  pinned bundle's own manifest, so an `update` has one and a converge does not;
  a bare `ship` lets the CLI follow `latest-<platform>` inside its own process,
  so this app never saw which bundle went out. HEAD is never substituted — the
  sha of this checkout is not the sha of the bytes on the box;
- **`Running` is readable and can be permanent.** A backend that died mid-run
  left it, because the process that would have stamped the outcome is the process
  that went away. No sweep invents a terminal status nobody observed.

## The release run id is not a link — but no longer for a structural reason

The row shows the full `release_runs.id` as plain text. That used to be forced:
the release run detail hung off `comp/:id`, so opening it needed the
composition's **config-item uuid**, which a deploy run does not carry and a
caller may not invent (stray params are rejected by design).

That blocker is gone. `releaseDetailRoute` was re-parented onto the **paramless**
`compositionsRoute` (`segment: "rel/:runId"`), precisely so that anyone holding
nothing but a ledger row can name it — its whole param set is `{ runId }`. What
is left is wiring, not a shape problem, and the shape is already in this app: the
sibling `composition` section imports a route from Studio's `core` barrel (no web
barrel, no section components) and hands
`compositionDetailRoute.link(studioApp, { id })` to `navigate`. The same call
with `releaseDetailRoute` and `{ runId }` would make this chip a cross-app link.
