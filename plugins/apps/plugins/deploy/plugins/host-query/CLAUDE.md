# host-query

The deploy app's side of a deployed site's **host-only** routes
([`analytics/host-only`](../analytics/plugins/host-only/CLAUDE.md)): a section
on a deployment's page that reads data kept on the box reads it through here.
It ships in the local app only — never in a deployed closure, which must stay
free of SSH (that is why it is not part of `host-only`, which ships on the box).

## Server — `hostOnlyQueryOverSsh(deploymentId, path, schema)`

1. Resolves the deployment row and its server's SSH target through `health`'s
   `resolveServerSshTarget(…, "require-pinned")` — the same address, key and
   host-key rules as the connection check; an unverified server is refused,
   never trusted.
2. Runs `curl -sS -w '\n%{http_code}' -m 10 'http://127.0.0.1:<loopbackPort><path>'`
   over SSH. It goes through the install's **gateway**, never the backend
   socket: `hostOnly` answers only a request with exactly the gateway's one
   proxy hop. No `-f`: the status line `-w` appends tells a 404 from any other
   HTTP error.
3. Parses the body with `schema`.

The answer is `{ kind: "answer", value } | HostQueryFailure | { kind: "not-found" }`,
never an empty value. The failures (core, `HOST_QUERY_FAILURE_ARMS`):
`no-ssh-key` · `unverified` · `ssh-failed` (with the SSH failure kind) ·
`request-failed` (curl's exit code: `CURL_EXIT` 7 site down, 22 an HTTP error
other than 404, 28 timeout) · `route-missing` (the site answered 404: on the
box's own hop nothing else 404s a host-only route, so the release it runs does
not serve this route — deployed before it existed, or its composition does not
ship it; rendered as "deploy it again", never as a generic HTTP error) ·
`unreadable-answer`. A consumer spreads the arms beside its own
answer's in its result schema.

- `path` must sit under `HOST_ONLY_PREFIX` — throws otherwise. `sshRun` joins
  argv with spaces into one remote shell command, so the URL travels
  single-quoted (`?` and `&` are inert) and a path holding anything that could
  leave the quotes (`'`, `\`, whitespace, `$`, backticks…) throws. Encode
  queries as base64url or `URLSearchParams`.
- At most two SSH sessions run at once, across every consumer (a semaphore;
  more readers queue).
- It reads Postgres (deployment, server, pinned host key, key secret) on every
  call — the private key may only be read at SSH time. A live value serving it
  is therefore `source: "external"` with `changes: { snapshot }`: the remote
  answer has no change signal here, and a `db` arm would label it fresh. The
  read is undeclared: `no-db-backed-notify` follows the loader into it, so each
  serving plugin sanctions it in its own `exempt/index.ts`.

### Stand-in box (demos)

`markServerBoxIsThisInstance(serverId)` (table `deploy_host_stand_ins`, one row
per server, cascades with it) marks a server whose box is THIS instance: a
demo's server, whose host-only data (analytics, messages) the demo wrote into
its own database. `hostOnlyQueryOverSsh` then fetches the route through this
instance's own gateway (`namespaceUrl(runtimeNamespace(), path)`, owner
principal, one hop, the same 10 s deadline) instead of SSH, and maps it onto
the same failures: network error -> `request-failed` 7, 404 -> `route-missing`,
any other HTTP >= 400 -> `request-failed` 22. No SSH key or pinned host key is needed. Used by
`deploy/fixtures` (`box: "this-instance"`).

`server/internal/query-over-ssh.ts` holds the argv, the mapping and the query
with its two effects injected, tested without a box.

## Web

- `HostQueryFailureState({ failure, subject })` — each failure as a sentence
  naming what failed and what to do, with the raw stderr under it.
  `HostQueryErrorState` is the same alert shape for a consumer's own refusals.
- `useDeploymentShips(deploymentId, pluginId)` — `pending | failed | yes | no`:
  does the deployment's composition closure include the plugin? A section gate
  (`useAvailable`) is `useShipsGate(deploymentId, pluginId)` — `kind !== "no"`,
  so the card shows while loading and on a failed read; every tab gated on one
  plugin spells it through that hook.

Consumers: `analytics/dashboard`, `analytics/sessions`, `site-messages/inbox`.

Run the tests with `./equin test plugins/apps/plugins/deploy/plugins/host-query`.

## Plugin reference

- Description: The deploy app's shared pieces for a section that reads its deployment's box over SSH: HostQueryFailureState renders every way the read can fail (no SSH key, unverified host, SSH failure, failed request, unreadable answer) in one vocabulary, and useDeploymentShips(deploymentId, pluginId) answers whether the deployment's composition closure includes a plugin (useShipsGate: the tab gate over it — shown unless the answer is no). hostOnlyQueryOverSsh(deploymentId, path, schema, { maxAnswerBytes? }): resolves a deployment's server and pinned SSH target, curls one host-only route of the install through its own gateway on the loopback port (two SSH sessions at most), refuses an answer over maxAnswerBytes unread (curl --max-filesize on the box, re-checked here), and answers the parsed answer, which of SSH, the request or the answer failed, or not-found. markServerBoxIsThisInstance(serverId) marks a demo's server whose box is this instance: its host-only routes are answered through this instance's own gateway, no SSH (the same answer cap applies).
