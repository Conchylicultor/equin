# demo

The Agent Manager's demo scenario: `agentManagerDemo` (`core`) — the app, the
route it opens at (`/c/conv-demo-dark-mode`) and its pack, the recorded answers to
everything the route reads on mount, telling one story (an agent fixing a dark
mode bug in a small notes app, three more at work in the queue, two done). The
app owns its scenario, so the demo plugins (`framework/browser-server/demo`)
never name it. Rendered by `<DemoScope scenario><AppEmbed app route/></DemoScope>`
— the website's Live demo band and this plugin's exhibit
(`agent-manager/demo`). Design:
`research/2026-10-15-global-app-embed-and-agent-manager-demo.md` §5.

- **Every id carries `demo`** (`conv-demo-…`, `task-demo-…`, `att-demo-…`), so a
  request that leaked past the scope to the real server is findable in its logs.
- **Keys answered the same for any scenario** (no in-flight ops, no
  notifications, config defaults…) are their owning plugin's `Demo.Resource`,
  not this pack's.
- **Growing it**: a read the pack does not record fails loudly
  (`DemoMissingError`, `loader-failed` naming the key). Record the tuple here
  when it is part of the story, or contribute a neutral answer from the owner.
