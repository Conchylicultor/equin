# single-flight

Cross-process single-flight: N processes asking for the same keyed work at the
same time run it **once**. The cross-process twin of `packages/inflight` (which
collapses overlapping calls inside one process).

```ts
import { singleFlight } from "@plugins/packages/plugins/single-flight/core";

const flight = await singleFlight(
  {
    dir,                         // every coalescing process names the same dir
    key,                         // everything that changes the answer is IN it
    id: opId,                    // recorded as the leader if this caller leads
    schema: VerdictSchema,       // ZodParser<V>: a published verdict is parsed before adoption
    adoptable: (v) => v.outcome !== "interrupted",
    onJoin: (leader) => console.log(`waiting on ${leader?.id ?? "a starting run"}`),
    signal,                      // optional: abandon a pending JOIN wait
  },
  async (publish) => {
    const outcome = await doTheWork();
    publish({ outcome });        // what joiners adopt; omit it and they run themselves
    return outcome;
  },
);
if (flight.role === "joined") use(flight.verdict, flight.leader);
else use(flight.result);
```

Design and the first consumer (`withDirectOp`'s `flight` option, for `check` and
`test`): [`research/2026-10-09-global-direct-op-single-flight.md`](../../../../research/2026-10-09-global-direct-op-single-flight.md).

## How it works

Per key, three files in `dir`, named by `sha256(key)`: `.lock` (a kernel flock),
`.leader.json` (who holds it, for display), `.verdict.json` (the last published
verdict, wrapped with a per-publish `nonce` and the publishing leader).

- **Lead.** `flockTry` on the lock wins → write `.leader.json` → `lead(publish)`
  → remove `.leader.json` → release. The lock is released only after `lead`
  settles, so a published verdict is on disk before any joiner wakes, and the
  kernel releases it if the leader dies (SIGKILL included).
- **Join.** `flockTry` fails → note the verdict file's current `nonce` → `onJoin`
  → `waitForFlock` (`packages/flock`: a child blocked on the flock, woken by the
  kernel; no polling) → **holding the lock**, re-read the verdict. A different
  nonce that parses and is `adoptable` → release and return `joined`. Anything
  else → keep the lock and lead.

`tryLead(opts, lead)` is the never-wait variant: lead if the key is free (others
can still join this run), else return `{ role: "busy" }` at once. For a caller
that holds something an in-flight leader may itself be queued for — a nested op
holds its parent's host grant, and a leader still queued for a grant may be
waiting on exactly those units, so joining it would deadlock.

## Rules that look wrong and are not

- **Staleness is the nonce, not the file.** The verdict file is never deleted.
  A joiner adopts only a verdict published after it saw the lock held — by the
  leader it found, or by one that took the lock after it (whose run therefore
  started later, on the same key). A leader that dies between taking the lock
  and touching any file leaves the old verdict in place with the old nonce, and
  it is not adopted. (The design doc had the leader delete the old verdict and
  joiners match `leaderOpId`; both left a window — a leader dying before the
  delete, a joiner reading the previous holder's `leader.json` — in which a stale
  verdict could be adopted. The nonce has none.)
- **A joiner that could not adopt keeps the lock and leads.** It already holds
  it, so releasing to "retry" would only open a window for a third process to
  barge in between "I could not adopt" and "I run".
- **`leader.json` is display only.** It can be missing (the holder has not
  recorded itself yet) or name a dead pid (a holder that died) — `onJoin` then
  gets `null`. `joined.leader` is read from the verdict envelope, so it always
  names the run actually adopted.
- **A verdict this code cannot parse is not adoptable**, never a throw: a
  flight directory may be shared by checkouts running different code, and the
  safe answer to "a verdict I do not understand" is to run the work.
- **Joiners are woken one at a time** (an exclusive flock is granted to one
  waiter), each holding the lock only for a file read — a few ms per joiner.

## Cost and bounds

One `bun --smol` wait child (~37 MB) per pending joiner, for the length of the
wait. One lock/leader/verdict triple per distinct key, ever: a caller whose keys
are unbounded (they embed a content hash) owns reclaiming its `dir` — a
per-worktree dir goes with the worktree's data dir.

Tests (`core/internal/single-flight.test.ts`) drive real child processes: one
body for a leader plus joiners, a SIGKILLed leader re-led, a non-adoptable
verdict re-run, a stale verdict never adopted, different keys in parallel.
