# socket-buffer

A connected socket's kernel buffers, read and raised through `bun:ffi`
(`machine/` barrel — host processes only):

```ts
import { raiseSocketSendBuffer, socketBufferSizes } from "@plugins/packages/plugins/socket-buffer/machine";

raiseSocketSendBuffer(socket, 1024 * 1024); // { before, after } — never lowers
socketBufferSizes(socket);                  // { send, receive }
```

Why: on a macOS Unix stream socket the **sender's** `SO_SNDBUF` bounds how much
of a write is in flight (`net.local.stream.sendspace`, 8 KB by default; the
receiver's `SO_RCVBUF` changes nothing), and Bun writes once per event-loop
turn — so a 768 KB write leaves the process in ~96 turns, 15 s on a loop whose
turns take 150 ms. A process may raise its own sockets up to
`kern.ipc.maxsockbuf` (8 MB by default) without root; past it `setsockopt`
fails and so does the call. Linux reports twice the value it keeps and caps an
unprivileged raise at `net.core.wmem_max`; its Unix-socket default (~208 KB)
is already larger.

The descriptor is read from the socket's native handle (`_handle.fd`, Bun and
Node alike); a socket with none (not connected yet) throws.

User: the app's database lane pools (`database#machine`), raised to
`LOCAL_SOCKET_BUFFER_BYTES` on connect.
