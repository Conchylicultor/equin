# error-subject

What an error is ABOUT, carried by the error itself, so a crash report filed
from it can tell one cause from another whichever filer catches it.

## Why

A crash report's identity (`reports/crash`'s `crashFingerprint`) is its top
stack frames. When the throw site is shared code acting for many subjects —
the migration runner applying one file of hundreds, the trigger installer one
table of many, Postgres' protocol parser raising every server error — those
frames are the same for all of them, so every failure of that code landed on
ONE report row whatever its cause. On main, report-1793851409-s559e6 held every
"backend crashed during boot" migration failure since 2026-11-05 (a `column
"first" … already exists` and an unrelated `column "stale_origin" does not
exist` alike). A fix to one could not be named with `./equin push
--fixes-report` without the row "regressing" on the next unrelated failure.

## The API (`core`)

- **`SubjectError(message, { subject, cause })`** — thrown by a SHARED throw
  site for the one subject it failed for. `subject` is a stable name (a
  migration's slug and phase, a table) — never a run id, a timestamp or a
  worktree, so one cause stays one row.
- **`errorSubject(err)`** — every `SubjectError` subject along the `cause`
  chain, outermost first, then the class `code` of the innermost error carrying
  one (`ENOENT`, a SQLSTATE such as `42701`): `migration page_links_first_edge
  (expand) › code 42701`. Null when nothing names one.
- **`crashFieldsOf(err, scope?)`** — the `{ errorType, stack, scope }` every
  crash filer derives from a caught error. `scope` joins what the caller knows
  (a job's name, a plugin hook) with `errorSubject(err)`; it becomes the crash
  payload's `scope`, part of the fingerprint. An error with neither keeps
  `scope: null`, so its fingerprint did not move.

## Enforced: `error-subject/crash-fields-of`

An object literal with an `errorType` whose `stack` reads a `.stack` (or is a
shorthand `stack`) is a hand copy that drops the subject — use
`...crashFieldsOf(err)` (then override `errorType` if the caller declares its
own identity). A relay of fields recorded earlier (`errorType: r.errorType`)
must relay `scope` too; better, it carries one `CrashFields` value spread whole
(the jobs attempt event's `crash`). Out of scope in tests.

## What changed for existing rows

Nothing: rows keep their fingerprints. A NEW occurrence of an error that now
names a subject (a migration, a trigger table, a rollup, a coded error such as
a Postgres or Node one) lands on a new row keyed by that cause.
