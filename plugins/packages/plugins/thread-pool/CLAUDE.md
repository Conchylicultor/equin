# thread-pool

`createThreadPool({ url, size, name })` / `serveThreadPool(handle)` — a bounded
pool of worker threads, each answering one request at a time, for CPU-bound JS a
host process would otherwise run on its single thread. The first user is the
build's artifact compiles (`framework/tooling/web-artifacts`): Babel and the
React Compiler are JS, so every concurrent vite run of one process shared one
thread, and a cold frontend build used ~1.7 of 6 cores.

- **Lazy and warm:** no worker until the first request, at most `size`; a worker
  lives as long as the pool, so its JIT stays warm across requests (a cold one
  pays seconds of warm-up — measure before sizing a pool for small batches).
- **One request per worker at a time;** the rest queue in arrival order.
- **Loud, contained failure:** a throwing handler rejects that request with the
  worker's message and stack; a dying worker rejects the request it held and is
  replaced on the next one. Never retried.
- **Never keeps its process alive:** idle workers are `unref`-ed; `close()`
  terminates them and rejects what is still queued.
- **Admission is the caller's:** the pool bounds threads, not host CPU. A build
  wraps each `run` in its host grant (`grant.run`), so the pool never runs more
  than the grant holds.

Lives in `cli/` because its users are host processes (a CLI op and the `bin/`
worker entries it starts), and `cli` is the barrel both rows may import; the
barrel is loaded by every `./equin` call, so it stays a small module with no
top-level work.
