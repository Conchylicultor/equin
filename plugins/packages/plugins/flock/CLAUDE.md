# flock

`flockTry(fd)` / `flockRelease(fd)` over libc's `flock(2)`, dlopen'd lazily.

Exported from `core/` (runtime-neutral Node/Bun, like `infra/spawn/core` — never
`web/`) so a plugin's `shared/` code, which may not import a `server` barrel,
can lock too (the prototype version store). The `server` barrel re-exports the
same binding for its existing consumers.

**Why this is its own plugin.** The binding was hand-rolled in two places
(`packages/host-semaphore`, `infra/worktree`'s push-lock probe) before a third
consumer — the CLI's `.build.lock` — needed it. Three copies of a `dlopen` is a
smell, so the syscall lives here once and the consumers import it.

**What the kernel buys you, and why it matters here.** An flock is owned by the
open file description, so it is released when the fd closes *or when the process
dies* — SIGKILL, OOM and power loss included — and no pid is ever consulted, so
PID reuse cannot confuse it. That is the property `infra/worktree` calls "the
ONLY crash-safe, PID-reuse-proof truth for 'is a push running'", and it is why
`cli/plugins/bootstrap/cli/checkout-lock.ts` was migrated onto it: a build killed by a caller timeout can
no longer leave a lock nobody holds. A userland scheme has to *emulate* this with
a pid probe plus a heartbeat, and both of those emulations have holes.

**Two acquires: `flockTry` in-process, `waitForFlock` in a child.** A
synchronous FFI `flock(LOCK_EX)` has no yield point — the thread it runs on is
frozen until the lock frees, which is never acceptable on an event loop. So the
only in-process acquire is the non-blocking `flockTry(fd)`. A caller that must
*wait* calls `waitForFlock(path, { signal })`, which spawns one `flock-wait`
child (`scripts/flock-wait.ts`, `bun --smol`) that parks the blocking flock on a
worker thread of its own (`scripts/flock-block.ts`), relays `granted`, and then
HOLDS the lock until the returned `HeldFlock` is released — or until we die, when
its stdin hits EOF and it exits. Push-based (the kernel wakes it, including when
a SIGKILLed holder's lock drops), cancellable (an abort kills the child and
throws `signal.reason`), and loud (a child that exits without granting throws).
The pair moved here from `packages/host-semaphore`, which now consumes it, so
`single-flight` could wait on a lock without a second copy. The two scripts
import nothing cross-plugin (only `node:*` + `bun:ffi`): they are loaded by path
and stay independently runnable. The one lock file arrives via
`FLOCK_WAIT_FILE`.

**Why the blocking flock sits on a worker thread, not the child's main
thread.** A child blocked on its *main* thread could not observe stdin EOF or
signals while parked; if its parent were SIGKILLed nobody would be left to
SIGTERM it and it would hold the lock forever (the orphan hole). The worker keeps
the main thread free to see EOF and exit, and process exit closes the fd.

**The parent lifeline (`holdParentLifeline` / `exitWithParent`).** The one
place this plugin opens a file in-process. `infra/spawn` holds an exclusive lock
on a per-spawn `lifeline` file for as long as it waits on a child, and passes
the path in `SINGULARITY_PARENT_LIFELINE`. A child that calls `exitWithParent()`
parks a worker thread (`scripts/lifeline-block.ts`) on a *shared* lock on that
file. The lock is granted only once the parent's lock is gone, meaning the
parent died by any means, and the thread then SIGKILLs its own process. The kill
comes from the thread, not via a message, because the child's main thread may be
stuck in minutes of synchronous work. A child that arms it must end with an
explicit `process.exit()`: the parked FFI call must not be what an empty event
loop waits on. See
`research/2026-10-09-infra-spawn-children-die-with-parent.md`.

**Not a lock manager.** No path convention, no release-on-exit hook — callers own
their fd's (or `HeldFlock`'s) lifetime. `packages/host-semaphore` builds bounded
N-slot pools on top; `packages/single-flight` builds cross-process run
coalescing; `checkout-lock.ts` builds a size-1 mutex.
