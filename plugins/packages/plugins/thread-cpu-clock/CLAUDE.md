# thread-cpu-clock

How long did THIS thread actually run?

```ts
const r = readThreadCpu();
// { supported: true, ms } | { supported: false }
```

Two reads on the same thread differ by the CPU time that thread consumed
between them (`CLOCK_THREAD_CPUTIME_ID`) — not the time it was runnable but
unscheduled, waiting in a syscall, or the machine was asleep.

**Why it exists.** A timer that fires late cannot say whether code held the
thread or the OS did not schedule it. A `./equin check` pass inside a
build runs at macOS background priority; on a busy host its 50 ms tick fired
seconds late while its thread ran a fifth of that time, and every such stall
was filed as a code problem. `process.cpuUsage()` cannot settle it: it is
process-wide, so worker threads count, and Bun has no per-thread CPU clock.
The check runner's thread watch reads this on its tick to split each stall into
**held** (the thread's own time) and **starved**.

darwin (`clock_gettime_nsec_np`) and Linux (`clock_gettime`), read through
`bun:ffi`, lazily, like `packages/sleep-clock`. Elsewhere `{ supported: false }`
— never read that as "the thread did not run".
