# zod-introspect

**The one owner of zod internals.** Everything else in the repo reads a zod
schema through this plugin's `SchemaNode`, never through `_def` / `_zod` /
`typeName` / `instanceof Zod*` — so a zod upgrade is a change to this plugin,
and a kind zod adds is a `never`-switch error here, not a silent miss in a
consumer. Plan: `research/2026-10-28-global-zod-4-migration.md` (Phase 1).

```ts
const node = inspect(schema);          // ONE level, in zod 4's model
switch (node.kind) { case "object": node.shape; node.unknownKeys; … }
childrenOf(node);                      // [{ edge, schema }] — walk them with inspect
peel(schema);                          // { node, peeled: ["optional", "default", …] }
valueSide(pipeNode);                   // in for .transform(fn), else out
isUncheckedBase(schema);               // a bare z.string() / z.number() / … — no check at all
describeSchema(schema);                // { description, opaque } — repo-owned, survives a zod upgrade
const tag = defineSchemaTag<T>("my-tag");
tag.set(schema, value);                // a NEW schema, stamped by clone
tag.get(schema);                       // T | undefined
```

- **Shallow nodes.** A node's children are raw schemas; recursion,
  memoisation and cycle cutting (a `lazy`) are the walker's, keyed on schema
  identity (`node.schema` is the schema handed to `inspect`).
- **One model, one backend.** `backend-v4.ts` reads zod 4 (`_zod.def.type`,
  caps from its size checks) into the repo's nodes: a refinement is a
  `refine` check, a transform `pipe(inner, transform)`, a preprocess
  `pipe(transform, inner)`, a brand nothing, a `z.custom` an `any` with a
  `refine` check, an `unknown` / `any` catchall (`.passthrough()`)
  `unknownKeys: "opaque"`, a codec (`z.codec`, `z.stringbool()`) a `pipe`
  with `codec: true`. Every def field that changes what a schema accepts or
  produces is on the node — a record's `mode` / `partial`, a union's
  `inclusive` / `unionFallback`, a template literal's `parts`, a function's
  `input` / `output`, a map's `max`, a format's `pattern` (and `url`'s
  `normalize`, with `rewrites: true` — it trims) — so `describeSchema` sees
  it. A kind zod adds is a `never`-switch error there.
  Anything that is not a zod 4 schema throws, and a zod 3 one
  (`_def.typeName`) is named as such.
- **Tags ride the def, stamped by clone.** zod 4's `.describe()` / `.meta()`
  clone over the SAME def object, so a mutation would tag the source too
  (the clone copies the def by descriptor, as zod's `mergeDefs` does — a
  default's `defaultValue` getter stays a fresh fill per parse); and
  registries are per module instance and follow no wrapper. A tag survives
  `.max()` / `.describe()` / `.meta()` / `.check()` / `.refine()` / `.brand()`;
  a wrapper's tag is read off its inner schema.
- **Describable function steps.** `describeSchema` blinds every function
  body, except the two this plugin mints with a fixed body and its
  parameters recorded (a module WeakMap, so nothing else can claim to be
  one): `retype<T>` — an identity brand cast,
  `z.string().transform(retype<Id<P>>)`, described `fn: "retype"` — and
  `fallbackTo(scalar, onFailure?)` — a catch answering one JSON scalar
  (`onFailure` only reports; its return is ignored), described
  `{ fallback }`. A literal `Date` default (`.default(new Date(0))`, handed
  out as the same object on every fill) is described by its instant
  (`date: iso`); a computed one stays blind. Use these instead of an inline
  cast or normalizer wherever a schema feeds a definition (row schemas: the
  epoch handoff's point definition, L2 `all` definitions).
- **`no-zod-subpath`** (this plugin's `lint/`, on in tests too) bans every
  `zod/…` specifier: the repo runs one zod, imported as `"zod"`.
- **`no-zod-internals`** (on in tests too) bans `_def` / `_zod` reads,
  `instanceof Zod*` (but `ZodError`) and zod 3 kind-name literals outside this
  plugin.
