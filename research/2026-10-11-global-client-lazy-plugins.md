# Cold start: client lazy plugins (plan)

Track: Cold start performance (page block-31faa75d-f93e-469e-99dd-cdc706059377, instructions
block-361815ed-5750-413a-b5ab-31c5dc855144). Scope of this doc: this session. The shared
web + server lazy-plugin design will go on a wiki sub-page of the track, because it takes more than one session.

## Context

The server is ready at about 0.75 s, so the browser is now the critical path. On /agents with an empty cache, the median is:

- First screen with data at 2.28 s.
- Main screen at 4.17 s.
- Download is about 0.45 s. Running the code costs about 1.0 s: 821 of 988 plugins, 12.9 MB.
- The main screen then waits about 1.9 s behind a 0.8 to 1.0 s burst of main-thread work after the first render.

**Why 821 are eager.** The tier is a function of the plugin's path, generated by
`tooling/codegen/core/eager-tier-gen.ts`. Only *app content* (`apps/plugins/<app>/plugins/<x>`,
outside `shell`) can be deferred, and that is 167 plugins. Everything else is structurally eager, whether or not the first screen
reads it: primitives, conversations (155), page (69), fields (90), debug (57) and the rest. The deferred tier then loads right
after the first render (`web-core/web/App.tsx`), in batches of 24. That is the likely source of the post-render burst; the CPU profile will
confirm or refute it.

**Already found while planning: 1.46 MB of the 13.3 MB eager bytes is one CSS bug, not the plugin count.**

- `page/math/render` already loads KaTeX on demand (`lazyComponent`). Its eager `index.js` is still 1.46 MB.
- The cause is in `web-artifacts/core/internal/vite-builder.ts:425-458`. It folds *every* extracted `.css` of the build into
  the entry `index.js`, including the CSS of the dynamic chunk.
- That CSS is katex.min.css, with 60 fonts inlined as `data:` URIs (lib mode inlines `url()` assets).
- 13 eager files carry injected CSS, 1.50 MB in total, almost all of it this one.

## Approach (phased, in this session)

### Phase 0: Measure (before any fix)

1. **CPU profile in `cold-start.ts`.** Add `--cpu-profile` (CDP `Profiler.start` on the existing session at line ~285, stop at the main
   screen). The tool attributes self time to an artifact URL and so to a plugin, and to a function. It does this for two windows: the
   `load-plugins` span and the window from first render to main screen. It prints the top 15 of each and writes the `.cpuprofile` next to `--out`.
   This answers the open [CPU profile] task.
2. **First-screen slot trace.**
   - The boot-trace marks each distinct slot the first time it is read (`useContributions` / `.Render` / `.Mount`, in
     `web-sdk/core/slots.ts`), up to the route-content mark and up to the main screen.
   - cold-start.ts then reports what would load if a plugin loaded only when something needed it: the import closure of the read
     slots' owners and contributors, plus side-effect plugins. It gives this as a count and in bytes, against today's 821.
   - This number decides the design (slot granularity versus key granularity, below) before we build it.

### Phase 1: Structural fixes already identified

1. **A dynamic chunk's CSS travels with the chunk** (`vite-builder.ts`).
   - Build with `cssCodeSplit` per chunk, and inject each chunk's CSS from the chunk that owns it.
   - Font `url()` assets become emitted files next to the artifact (content-addressed, served from `/artifacts/`), not `data:` URIs.
   - Guard: the build throws when a file statically reached from `index.js` carries CSS that came from a dynamic chunk. This is the
     same pattern as `assertCoEntriesOffHostPath`.
   - Expected effect: the eager bytes drop by about 1.45 MB, and parsing the 1.4 MB string literal leaves the boot.
2. **[Immutable code files]** `gateway/proxy.go` `handleStatic` adds `Cache-Control: public, max-age=31536000, immutable` to
   `/artifacts/*`, since the URLs are content-addressed. A test goes in `gateway/proxy_test.go`. This does not change the cold
   headline; it stops real browsers from revalidating.

### Phase 2: Lazy plugins design (wiki sub-page, shared with the server)

**The rule: a plugin's code loads when something needs it.** That is one of:

- (a) an eager module imports it (the existing `dependsOn` closure);
- (b) a slot it contributes to is first read;
- (c) it has boot side effects, so it stays eager. Side effects are a `register` array, `Core.Root` / `Core.Boot`, a `preload:` resource, or a side-effect
  import in the barrel. The generator detects these, with today's `WATCHED_SLOTS` / preload scanners generalised.

This replaces the path-based eager/deferred split with one mechanism. "App content" stops being special.

- **Manifest (build time).**
  - The codegen already imports every barrel, with `SlotNaming`, for the `contributions` facet.
  - It emits `web-contributions.generated.ts` next to `web.generated.ts`. This file maps a slot id to the plugin paths that contribute to it.
  - A sync check fails on drift, like `eager-tier-in-sync`.
- **Runtime (`web-sdk/core/context.tsx` + `slots.ts`).**
  - `PluginProvider` knows each slot's not-yet-loaded contributors.
  - Reading a slot that has some starts their `import()` (deduplicated) and suspends: it throws the promise, React Suspense handles it, and the
    nearest boundary renders `primitives/loading`.
  - Pending is a state, never a partial list (the not-known-yet rule). All 445 slot read sites keep their API.
- **Two granularities.**
  - Level 1 is per slot.
  - Level 2 is per key, for dispatch slots whose reader picks one contribution: panes by route id, page blocks by type,
    fields by token, active-data tags, id kinds. There the slot declares a data key evaluated at build time into the manifest, and only the matching
    contributor loads.
  - Phase 0's slot trace says whether Level 1 alone gets /agents near the 2 plugins its main pane needs, or whether the
    first screen reads broad dispatch slots that need Level 2.
- **After the main screen**, the remaining plugins prefetch at idle priority, so a later navigation is not cold. They never load
  inside the window before the main screen.
- **Server.** It uses the same manifest generator and the same load-on-first-need contract (routes / RPC prefixes and slots map to plugins, and
  `register` stays eager). The design is recorded on the wiki page, and the server implementation remains the [Lazy plugins] task.

### Phase 3: Implement Level 1 (then Level 2 for the dispatch slots the trace names), this session if sizing supports it

The rollout runs behind the generator: a plugin with any unknown side effect stays eager, and the eager set shrinks as the scanners prove plugins safe.
Critical files:

- `web-sdk/core/{context.tsx,slots.ts,load-tiers.ts,deferred-load-store.ts}`
- `web-core/web/App.tsx` (the boot flow and the priority / deferred batches)
- `tooling/codegen/core/{eager-tier-gen.ts,plugin-registry-gen.ts}`
- `web-artifacts/core/internal/compose.ts` (`computePreloadClosure` seeds only the eager set)
- `layouts/route-fallback`: deferred-tier settle, which becomes "the matching pane plugin is loaded"

Reuse `lazyComponent` (`primitives/lazy-component`), `traceBootPluginLoad` (boot-trace), the contributions facet's
barrel-import pass, and `topoSortPlugins` for the register order of late plugins.

## Findings (2026-10-12)

- **CPU profile** (`--cpu-profile`, /agents, 3 cold starts):
  - Load-plugins, about 0.9 s: 0.46 s of it is native parse and compile, and 0.29 s is module linking (V8 charges this to boot-trace's `import()` wrapper). Plugin top-level code is about 0.1 s. The cost scales with bytes and modules.
  - First data → route content, about 2 s: 100% busy rendering the first screen and applying live updates. No dominant plugin.
  - This is not a plugin-loading cost. It moves to the [Main screen] task.
- **Sizing** (`slot-read:` marks):
  - The first screen reads 41 slots by route content, and 34 of them by first data.
  - Level 1 (owners plus contributors of the read slots, plus their `dependsOn` closure): 428 of 989 plugins, 5.9 MB, against 822 plugins and 10.2 MB today.
  - Level 2 (panes keyed by route): 343 plugins, 4.1 MB.
  - The floor is set by import fan-out: a single seed often closes over about 190 plugins.
- **Lazy-chunk CSS** (shipped in the branch): the eager bytes drop by 1.4 MB. The time change is within noise, because V8 parses an unused string literal lazily.
- **A footgun found on the way:** reading `slot.id` before the slot's owner is declared throws. A plugin that reads a slot owned by a not-yet-loaded plugin is a real case: it happened on every cold load of /agents. How many slots do this was not counted. A lazy loader must key on the slot object, not on its id.

## Findings: the main-thread burst after first data (2026-10-12, React render profile)

Tools: `cold-start.ts --react-profile` on a `--no-minify` build (2 cold runs, host load ~25, so read
counts and fiber totals, not times), plus R rows (commits) and the unminified CPU profile.

- **Correction.** The priority (route-content) plugins are fetched in ~3 ms, but their `import()`
  only resolves ~2.7 s later: it waits for the main thread. Route content = the end of the burst.
- **~110 commits** between profiler install and route content, but the cost is in **5 commits**:
  56 000 fibers rendered in all, of which ~52 000 in five commits of 12–14 k fibers each. The other
  ~105 commits render 1–380 fibers (57 of them are `OverflowPanel`, below).
- The 12–14 k-fiber subtree is **the conversations sidebar** (Queue DataView): ~57 rows × ~200
  fibers. It is mounted at first data, then re-rendered whole four more times:

  | # | Initiator (hook) | Fibers | Trigger (to confirm) |
  |---|---|---|---|
  | 1 | `Region` (sidebar-framing variant region) / `MergedDataView` — `useSyncExternalStore` | 14 100 | a config store update during boot (`useConfig` in the region / the DataView's view config) |
  | 2 | `DndContext` under `ListView > RankReorderProvider` — `useReducer #0` | 11 600 | dnd-kit's droppable registration dispatch after mount (every sortable row registers) |
  | 3 | `QueueSource` — `useState` ×3 + 33 contexts | 13 500 | the queue's live reads landing one after another (active → ranks of the live id set → gone pages / count) |
  | 4 | `App` — `useState #0` | 12 800 | web-core appending the priority plugin batch: `PluginProvider` rebuilds the runtime, every contribution object is re-spread, every slot reader re-renders. This IS the route-content commit |
  | – | `DataViewBodyInner` (facet options) | 760 | |

- **Amplifier, not cause:** no row is a memo boundary. `ListView` builds each row's element inline
  (`renderRow` → `ManualOrderRow` → `Row` → `SidebarConversationItem`) and `classifyQueue` builds new
  row objects, so any list-level render re-renders all 57 rows.
- **57 `OverflowPanel` commits** (3 fibers each, cheap in React but each runs floating-ui's
  `computePosition`): `useFloating({ whileElementsMounted: autoUpdate })` keeps positioning the closed
  (always-mounted, `display:none`) panel on every layout shift during boot.

Fix candidates, by altitude (none applied yet):

1. **Registry append re-renders only what changed** (web-sdk, origin of #4 and of every deferred
   batch after it): stamp contributions once per plugin (stable identity), keep a slot's array
   identity unless its contributor set changed, and let slot readers subscribe per slot instead of
   to one runtime context. Also what lazy plugins (load-on-first-read) needs anyway.
2. **Rows are memo boundaries in the list view** (data-view/list): a row re-renders only when its
   row object or the props it reads change; `useQueueRows` keeps row identity for unchanged rows.
   Turns #1–#3 from whole-list renders into renders of the rows that changed.
3. **Origins of #1–#3**: which config update lands after first data (should be boot-hydrated:
   `preload: "boot-and-keep"`), whether dnd-kit registration needs a context-wide re-render, and the
   queue's read cascade (ranks keyed on the live id set = one extra round trip and one extra whole render).
4. **OverflowPanel positions only while open** (adaptive-bar).
