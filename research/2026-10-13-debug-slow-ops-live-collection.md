# Slow Ops plan: a live, paged collection with ring merges done in SQL inside one upsert per batch

## Context

Debug → Slow Events → Aggregates reads `slow-ops.list`, an external snapshot value (`plugins/debug/plugins/slow-ops/core/resources.ts`, `server/internal/slow-ops-served.ts`). Each read is `SELECT * FROM slow_ops ORDER BY total_ms DESC` with no limit. On main today that is 7,080 rows, about 21 MB of JSON. It never updates on its own.

The cause is the write shape in `upsertSlowOpIn` (`record-slow-op.ts:369-453`). Every occurrence does an upsert with `RETURNING *`, merges five jsonb rings in JS, then runs a second UPDATE that rewrites all five. All of this sits inside one transaction per batch, under the row lock. Measured: `n_tup_upd` is 384k against 6.8k inserts.

When the table was on the change feed, this produced 2 trigger runs and 2 NOTIFYs per occurrence. Each NOTIFY made every open reader reload the whole table. Those reloads ran profiled, so they tripped slow ops themselves, which wrote more rows. The table was therefore marked `ExcludeFromChangeFeed`. The read-modify-write transaction also rules out `defineChangeProducer`, which only accepts one autocommit statement on the pool.

Research doc B3 (`research/2026-10-11-global-endpoint-reads-onto-live.md:567-584`) deferred option (a): move the merges into SQL. This plan is option (a).

Payload breakdown: about 80% of the wire payload is `recent_samples` and about 20% is `callers`. The scalar columns alone are about 50 KB for a 200-row window. `callers` has no cap today: the largest row holds 457 entries (16 KB).

## Decision

Keep one row per op in `slow_ops` and keep all five jsonb rings on it, so no column is dropped or renamed. Make the table a volatile change producer with a 2 s coalesce window, replacing the exclusion. Each batch becomes:

1. A pure JS pre-fold per (kind, op), with caps applied.
2. One sorted, multi-row `INSERT … ON CONFLICT DO UPDATE` through `slowOpsProducer.mutate`. Every ring merge is a SQL expression in the SET clause, evaluated against the locked row.

Reads use two collections over the same table:
- A slim scroll window, `slow-ops.ops`, paged by `liveDataSource` in a DataView.
- A lookup-only fat row, `slow-ops.op`, read with `useLiveRow` in a new detail pane.

This follows the reports hot-counter producer and the traces slim-list plus lookup-detail pattern.

**Why not the alternatives.**
- **Split by temperature** (a slim produced table plus an excluded detail table): it keeps the JS read-modify-write under `FOR UPDATE`, only moved to the detail table. It needs two non-atomic commits per batch, makes the detail a non-live snapshot (the pattern this task is retiring), and drops columns that the cross-fork readers select.
- **Append-only occurrence log** with rings computed when a row is opened: it changes the breakdowns from all-time to 7 days. It needs a uuid filter (`liveText` over uuid fails at runtime, per the filter CLAUDE.md), a breakdown value that is fully recomputed on every flush, and a timeline rewrite with a silent `LIMIT` truncation.
- **`defineRollup`**: it re-aggregates the whole key history inside the write and needs a triggered source. A3p and A2′ forbid it for a produced table.

Both alternatives also need schema-skew probes in both cross-fork readers. The chosen design needs none.

**Fixes to the chosen design, from review.**
- **Caps on first insert.** On the first insert of a key, Postgres stores the VALUES row as given, so a cap applied only on conflict would never run. The pre-fold therefore applies the same caps as SQL: variants top 10 + "(other)", samples newest 10, and callers top 50 + "(other)".
- **No stored `wait_ms` / `last_trace_id`.** Stored copies would drift during a hot swap, because the old backend's writes would not update them. Both are `expr` fields instead: `waitMs` sums the jsonb `waits`, and `lastTraceId` is `recent_samples->0->>'traceId'`. They cannot drift, need no backfill, and the cluster contract is untouched.
- **Lock order.** VALUES rows are sorted by (kind, op) so concurrent batches on the two backends during a hot swap cannot deadlock.

## Schema & migration

- `slow_ops` keeps all of its columns.
- Two new indexes in `server/internal/tables.ts`. The migration is expand-only, generated by `./singularity build`:
  - `slow_ops_total_ms_idx (total_ms DESC, id)`: the default order and keyset paging.
  - `slow_ops_last_seen_at_idx (last_seen_at DESC, id)`: the "Last seen" sort and the 30-day retention sweep, which is a sequential scan today.
- No new columns, no backfill and no contract phase. The old fat columns remain the detail data.
- `core/schema.ts`:
  - New `SlowOpListRowSchema = SlowOpSchema.pick({id, worktree, operationKind, operation, count, totalMs, maxMs, lastMs, thresholdMs, firstSeenAt, lastSeenAt}).extend({ waitMs: z.number(), lastTraceId: z.string().nullable() })`.
  - `SlowOpSchema` stays as the full detail row.
  - `CALLER_CAP = 50` and `OTHER_CALLER = {kind:"other", label:"(other)"}`, mirroring `VARIANT_CAP` / `OTHER_VARIANT`.
- Cost of the indexes: `total_ms` changes on every write, so updates go from 64% HOT to about 0%, each inserting into 4 btrees. That is accepted on a 7k-row table and is still fewer tuple versions than today's 2 per occurrence.

## Write path

- **New `server/internal/producer.ts`:**
  ```ts
  export const slowOpsProducer = defineChangeProducer({
    table: _slowOps, durability: "volatile",
    reason: "Written exactly while the app is slow; a per-statement trigger+changelog+NOTIFY rebuilt the self-amplifying loop. All writers run in the serving backend.",
    coalesce: { ms: 2000, reason: "One scoped refill per reading tuple per 2 s however many occurrences land." },
  });
  ```
- **`server/index.ts`:** replace `ExcludeFromChangeFeed({table:_slowOps})` with `slowOpsProducer.declare`; A2′ forbids having both. Keep `ExcludeFromFork`. `retention.ts` is unchanged, because `defineRetention` already deletes through `changeProducerFor` (`define-retention.ts:114`).
- **`recordSlowOpBatch`** (`record-slow-op.ts`). These parts are unchanged:
  - per-item `occurredAt` stamping and the per-item `slowOpShed.admit` gate;
  - `runInBackgroundLane(() => runWithoutProfiling(async () => …))`, with the mutate awaited inside both scopes;
  - one `getContentionSnapshot()` per batch;
  - the per-item `markerChannel.publish` and `void recordReport(...)` after the write.

  The body inside the scopes becomes:
  1. **`foldSlowOpBatch(items, snapshot)`**, a new pure function in `server/internal/fold-batch.ts`.
     - Group by (operationKind, operation); worktree is always `runtimeNamespace()`. Each group produces:
       - `count = n`, `totalMs = Σ`, `maxMs = max`
       - `firstSeenAt = min(occurredAt)`, `lastSeenAt = max(occurredAt)`
       - `lastMs` and `thresholdMs` from the newest item; on a tie, the later item in the batch wins
       - `callers` with `mergeCaller` (capped at `CALLER_CAP`), `waits` with `mergeWaits`, `recentSamples` with `mergeSample` capped at 10, `variants` with the capped `mergeVariant`, `measures` with `mergeMeasures` in arrival order
     - Move `mergeCaller` / `mergeWaits` / `mergeSample` into `merge-detail.ts`.
     - Sort the rows by (kind, op).
     - This merges items and drops none. It is required because Postgres refuses `ON CONFLICT` touching one row twice in a statement.
  2. **Exactly one statement:**
     `await slowOpsProducer.mutate(db, (q, t) => buildBatchUpsert(q, t, rows), { latency: "background" })`

     `buildBatchUpsert` returns `q.insert(t).values(rows).onConflictDoUpdate({ target: [t.operationKind, t.operation, t.worktree], set })`. The `EXCLUDED.*` spelling follows the precedent in `latency-ledger/server/internal/store.ts:63-74`. The SET expressions live in the new `server/internal/merge-sql.ts`:
     - **Counters:** `count + EXCLUDED.count`, `total_ms + EXCLUDED.total_ms`, `greatest(max_ms, …)`, `least(first_seen_at, …)`, `greatest(last_seen_at, …)`.
     - **`last_ms` / `threshold_ms`:** `CASE WHEN EXCLUDED.last_seen_at >= slow_ops.last_seen_at THEN EXCLUDED.x ELSE slow_ops.x END`, the same guard as today.
     - **`waits`:** a per-key sum over `jsonb_each_text` of the union of old and new.
     - **`recent_samples`:** the union of both arrays `WITH ORDINALITY`, ordered by `(atTime DESC, src /*EXCLUDED first*/, ord)`, `LIMIT 10`, re-aggregated with `jsonb_agg`. This matches `mergeSample`'s stable sort with the new sample prepended.
     - **`callers`:** group the union by (kind, label) and sum count/total, max of max. Keep first-appearance order with `min(src*1e6+ord)`. With the cap: rank named entries by `totalMs DESC`, keep the top `CALLER_CAP`, and fold the rest plus any existing "(other)" into one "(other)" entry.
     - **`variants`:** the same shape with `VARIANT_CAP`.
     - **`measures`:** per key, `{max: greatest(old.max, new.max), last: coalesce(new.last, old.last)}`.

     Caps are bound as parameters from the core constants. Column names go through a small `excludedCol(t.col)` helper so renames stay type-checked.
- **Removed:** `upsertSlowOpIn`, `SlowOpTx`, and the second UPDATE. The test seam becomes `writeSlowOpRows(rows, executor: ProducerExecutor = db)`, following reports' `writeReport`. The `change-feed:producer-writes` check (A11) will then find no write to `_slowOps` outside a mutate builder.
- **Transaction shape:** one batch is one autocommit statement, so one commit, one snapshot and one round trip. Today it is one transaction of 2N statements. Each row lock is held only for that one statement, and no JS runs under a lock, which removes the `Lock:transactionid` queue. Safety across backends during a hot swap comes from ON CONFLICT locking the row and evaluating SET against the current version.
- **Duress replay:** each re-driven `recordSlowOp` is still one statement and one commit, the same commit count as today.
- **Every writer is in the serving backend, so A13 holds:**
  - the `onSlowSpan` hook, installed in `onReady`;
  - the POST `/api/slow-ops/client` handler;
  - the boot-monitor job (`schedule.perWorktree: true`, verified at `monitor-job.ts:37`);
  - in-process replay;
  - retention.

## Why the churn loop cannot recur

Each part of the old loop is removed:

- **I3, no feed work inside the write.** A produced table gets no trigger, no transition table, no changelog row and no NOTIFY. A2′ checks the catalog after the rebuild to confirm.
- **I2, rate cap independent of write rate.** The coalesce window is fixed: armed on the first change and never re-armed (`producer.ts`). That allows at most 0.5 flushes per second for `slow_ops`, whether 1 or 10,000 occurrences arrive per second. Above 1,000 distinct ids a flush routes `ids:null`, which recomputes only the bounded window query.
- **I1, read cost per flush is bounded.**
  - The list tuple refills only the changed ids it holds, at about 200 B per row, plus one top-N membership query on `slow_ops_total_ms_idx`. A full 100-row page is about 20 KB; today one load is about 21 MB.
  - Some tuples are O(table) per flush, but capped at 0.5 Hz and only while the pane is open: the `operationKind` `:groups` facet, a search tuple (ILIKE), and sorts with no index. Each scans roughly 7k rows.
  - A detail tuple refills one row, and only when its own id changed.
- **I4, writer shape.** One autocommit statement per batch with no JS read-modify-write. Per 200-item beacon, statements go from ≤400 to 1, and row versions from 2 per occurrence to 1 per distinct key.
- **I5.** The write stays inside `runWithoutProfiling` and the background lane.
- **Residual cycle.** The producer flush runs profiled in the root context, so a slow refill can record a slow op, which feeds the next flush. That cycle's period is at least 2 s and its cost is bounded by (open tuples × window rows). The gain is therefore ≤ 1 and does not grow with load. It can sustain itself at up to 0.5 Hz while the pane is open; it cannot amplify.
- **Example at a burst of 100 occurrences/s with one list open:**
  - Old: about 200 NOTIFY/s, each followed by a 19 MB reload, for roughly 3.8 GB/s of attempted recompute.
  - New: ≤ 0.5 flushes/s, each about 20 KB plus one index top-100, about 10 KB/s. That is a reduction of about 10⁵.
- **What remains** is the rewrite of the fat row, the TOAST and the WAL, once per key per batch. That is plain database I/O in the background lane, with no feedback edge. The callers cap bounds it.

## Semantics preserved

- **Cold-start attribution:** `transportWaitMs` still becomes the `notifications-transport` wait layer (it now also shows in `waitMs`). `transportColdStart` / `transportWaitMs` / `traceId` still go into the per-item report data, which is built from the input.
- **Nothing filtered:** every admitted item is still counted (the fold sums), still writes a marker line, and still files its own `recordReport`. The shed gate stays per item, before the write.
- **Replay is order-insensitive:** first/last seen use least/greatest, the newest-wins guard uses `EXCLUDED.last_seen_at`, samples are the top 10 of the union by `atTime`, and callers/waits sums and the max are exact. The variants fold was path-dependent before and still is; totals stay exact.
- **Batched client beacon:** `slow-op-queue.ts` (250 ms debounce, chunks of 200, pagehide flush, cap of 1,000 with a dropped count) is unchanged. One batch is still one snapshot and now one statement, which is literally one transaction.
- **Job work-time thresholds:** `resolve-threshold.ts` and the evidence-first `captureTrace` in `install-slow-span.ts` are untouched. Rows still record wall-clock `durationMs`.
- **Reports and markers:** kind, fingerprint, payload and the `slow-op-markers` sink are unchanged.
- **Retention:** still 30 days on `lastSeenAt`, per worktree. Deletes now go through the producer, and the new index serves the sweep.
- **Fork exclusion:** `ExcludeFromFork` stays.

## Decisions (user, 2026-10-13)

1. **Cap `callers` at 50:** the top 50 by total time stay named, and the rest fold into one `(other)` entry, like `variants`. `CALLER_CAP = 50`, applied both in the JS pre-fold and in the SQL SET. Counts and totals stay exact, and no occurrence or report is dropped. Only the per-route label past the 50th caller of one op is merged.
2. **Trim the Cluster SELECT:** done in this change. `handle-cluster.ts` and `ClusterSlowOpSchema` select only what `aggregate.ts` uses, dropping `callers`, `waits`, `last_ms`, `threshold_ms` and `first_seen_at`.
