## 2. Runs ledgers as entity refs

### Why not `defineEntity` for `build_runs`

It does not fit, for three independent reasons:

1. **Boundary (hard blocker).** `defineEntity` is server-only.
   - `entities/server` side-effect-imports `fields/server-capabilities-loader` (the `fieldsEager` pre-barrel manifest), and `define-entity.ts` pulls `derived-updated-at/server` (`pg`, `node:crypto`).
   - The detached `./singularity build` CLI imports `run-ledger/server` (`framework/cli/plugins/build/cli/run.ts:101`).
   - `cli:codegen-manifests-not-frozen` forbids a regenerating CLI from loading that manifest. The leaf's own CLAUDE.md also forbids the import graph.
2. **DDL.** `targets` is `text[]`, and no field storage produces `text[]`: `string-list` has no storage plugin, and `tags` is jsonb. Fitting it would mean a migration plus a change to the hand-written INSERT, which violates "derived DDL unchanged".
3. **Branded id.** `idColumn(buildRunIdKind)` (a branded parsedText key that tolerates legacy `<commit>-<ms>` ids) has no `defineEntity` spelling.

What does fit: the partial unique index `build_runs_inflight_uniq`, which `meta.indexes` passes through raw. The hand-written INSERT is unaffected either way.

So we use the fallback: an **`entityRef` beside the raw table**, the `pagesEntityRef` / `_blocks` pattern. `entityRef` lives in `entities/core`, imports only `fields/core` types and field config cores, and is CLI-safe. The table, its INSERT and its DDL do not change.

### Design

**a. Ref per ledger, in the ledger's own core.**

- `build/run-ledger/core`: `buildRunsEntityRef = entityRef("build_runs", buildRunFields)`.
  - Fields, the stored wire columns: `id`, `trigger`, `commitHash` ("Commit"), `namespace`, `targets` (`stringListField`, "Targets"), `startedAt`, `finishedAt`, `exitCode` ("Exit code").
  - `pid` is left out (internal; stripped from the payload today).
  - Labels move here from `runs-arm/core`.
- Release (`release/core`, table `release/server/internal/tables.ts:23`): the stored arm fields `kind`, `composition`, `target`, `platform`, `commitSha`, `commitDirty`, `artifactPath`, …, labelled.
- Deploy (`deploy/deployments/core`, table `…/deployments/server/internal/tables.ts:102`): `verb`, `phaseFailed`, `serverId`, `deploymentId`, `compositionId`, `commitSha`, `releaseRunId`, `exitCode`, `message`.
- Backup is skipped: its arm fields are computed from the manifest jsonb, and only `archiveSize` is stored.

**b. Drift guard at tsc (rung 2).** Nothing ties a ref's field keys to its raw table today; `page_blocks` has the same gap.

- Add a type-only `RefMatchesTable<Ref, Row>` to `entities/core`. It resolves to `never` / an error tuple naming the ref fields that are not keys of `Row`.
- Each ledger's `server/internal/tables.ts` asserts it against `typeof _table.$inferSelect`.
- Apply the same assertion to `pagesEntityRef` / `_blocks`.
- This is type-only, so it adds no runtime import to the lean leaf.

**c. Arms pick their stored fields.** Example for build (`runs-arm/core/internal/fields.ts`):

```ts
liveArm(runs, BUILD_RUN_KIND, {
  label: "Build", order: 10,
  from: buildRunsEntityRef,
  pick: ["targets", "commitHash", "exitCode"],
  fields: { status: enumTextField(BUILD_STATUSES, { label: "Build status", options: … }) },
  sortable: ["status", "exitCode"],
});
```

- Picked fields bind by name, through serve-arm's `extra` fold.
- `targets` stays overridden in `extra` (`to_jsonb(targets)`). serve-arm skips the by-name bind of a picked name the arm binds itself, because the column is `text[]` and the field domain is a jsonb string array.
- `commitHash` and `exitCode` drop out of `extra`.
- Only computed fields stay hand-written: `status`, and the base `label` / `outcome` / `message`.
- Release and deploy follow the same split: picks are the stored columns; label, outcome and the deploy server join stay in `base` / `extra`.
- Wire ids stay `build.commitHash` etc., so the runs golden should not change. If it does, the diff must be explained.
- Each arm now `reaches` its ledger entity. A future `defineExtension(buildRunsEntityRef, …)` exposure then lands in the Build band with no runs code.
  - One entity per arm holds: each ledger is reached by exactly one arm.

**d. Constraints re-checked in implementation:**

- `import-closure` of `framework/cli/plugins/build/cli/run.ts` reaches no `fields/server-*` / `entities/server` module.
- `cli:codegen-manifests-not-frozen` passes.
- `migrations-in-sync`: build generates no migration for the ledgers (only the two index DROPs from part 1).

## As landed (2026-10-17)

Deviations from the plan above:

- **The drift guard sits at the binding, not beside the ref.** There is no
  `RefMatchesTable` type. `served.arm`'s `extra` now *requires* a binding for
  a picked field when `from` has no column of that name whose value is the
  field's type (`ByName` in `network/live/server/internal/serve-arm.ts`).
  That is where the by-name bind happens, so the boot-time throw ("picks X
  … bind it in `extra`") became a tsc error for every entity arm, not only
  the ledgers. Non-picked ref fields are not checked against the table.
- **An arm field is never primary.** Picking a release's `target` (the release
  entity's title, `primary: true`) would have made it a second row title in the
  runs list. `liveArm`'s listed descriptors are now `primary: false`, and the
  union's base `label` is the title.
- **One record per ledger, not two.** `build.history` (`BUILD_RUN_FIELDS`) and
  `release.history` / `release.runs` each had their own field record. They now
  use the ledger's record (`buildRunFields`, `releaseRunFields`,
  `deployRunFields` for `deploy.run-history`).
- **Labels and types unified where the records disagreed:**
  - release `kind` is an enum with "Release kind" and the staged/candidate
    options, moved from the arm into the record;
  - release `commitSha` / `commitDirty` / `artifactPath` are labelled in the
    record;
  - deploy `releaseRunId` reads "Release run" in the deploy history too (it
    was "Release" there);
  - deploy `verb` / `phaseFailed` options are capitalised in the runs list too
    (they read as the raw values there).
- **Deploy `verb` / `phase_failed` became `parsedText` columns** over their
  enum schemas. DDL is unchanged (`text`), and the schemas moved to a zod-only
  `deployments/core/verbs.ts` so the table module stays light. An `expr` that
  is exactly one column is refused at bind, so typing the column was the only
  way to bind them by name as enums.
- **Build band order changed:** picks come first (`targets`, `commitHash`,
  `exitCode`), then `status`. Field ids are unchanged, so saved views still
  resolve. Release and deploy keep their order.
- Migration: `20261017_191424_40569893__drop_activity_updated_indexes.sql`, two
  `DROP INDEX` statements only.
- Tests: bun 116 files pass. vitest has two failures unrelated to this change:
  - `build/web/__tests__/build-button.test.tsx`: its `network/live/web` mock
    lacks `FieldPresentation`, which `runs/web` has used since Phase 3
    (b19d3ee896);
  - `data-view/table nested-row-key`: a 5 s timeout under host load.

  The `runs` e2e scripts `open-run` and `runs-live` pass.
