# Resume conversations stopped by a usage limit

## Context

When a Claude account runs out of quota, every agent on it stops with
"You've hit your session limit · resets 5:30pm". The user then switches account
(or auto-switch does), but the stopped conversations stay stopped:

- an SDK agent picks its account **once, at process start**
  (`runtime-sdk/machine/internal/agent-process.ts` `chooseLaunchAccount`) and
  keeps it until it restarts — so typing "continue" into a stopped conversation
  sends it to the same exhausted account, and it stops again;
- nothing lists which conversations stopped at the limit, so finding and
  restarting them is manual, one by one.

Outcome: (1) a conversation knows it stopped at a usage limit and which account
it ran on; (2) any turn sent to such a conversation transparently restarts its
agent on the account a launch would pick now; (3) a "Resume all on <account>"
action in the health report, and a Resume button on the transcript's
usage-limit line.

Out of scope (follow-ups): auto-resume on account switch, scheduled resume at
the limit's reset, naming interrupted sub-agents in the resume prompt.

## Evidence

A limit hit is already in the agent's own `events.jsonl` (seen in
`state/sdk-agents/singularity/conv-1792668571-ochl7d/events.jsonl` seq 4917):
an `sdk` line whose payload is a `type:"assistant"`, `model:"<synthetic>"`
message with top-level `error:"rate_limit"`, followed by the turn's `result`.
So detection lives in the runtime's existing reducer — no transcript parsing.

## Design

### 1. Record the account and the limit hit (runtime-sdk, server + bin)

- `bin/agent.ts`: add `account` to the `started` agent event payload (it
  already has `--account`). Extend the `started` schema in `core/protocol.ts`
  (bump `PROTOCOL_VERSION` only if the reader requires it; the field is
  additive — make it optional so old events still parse).
- `server/internal/tables.ts`: two new side-table fields on
  `conversations_ext_sdk_agent`: `account: nullable(textField())`,
  `limitHitAt: nullable(dateField())`. Migration generated by
  `./singularity build`.
- `server/internal/reducer.ts` (`AgentProjection`):
  - `started` → `s.account = p.account ?? null`, `s.limitHitAt = null`;
  - `sdk` assistant with `error === "rate_limit"` → `s.limitHitAt = at`;
  - `turn_started` → `s.limitHitAt = null` (a new turn ran past it).
  - Unit tests in the existing reducer test file.

"Stopped at the limit" = `limitHitAt !== null` and the conversation is active
(`isActiveStatus`). The account is the authority for "is a restart useful".

### 2. A turn to a limited agent restarts it on a runnable account (runtime-sdk, machine)

In `machine/internal/sdk-runtime.ts` `sendTurn` (the one path every turn takes —
`submitTurn` → `deliverLocked` → `runtime.send`, under the per-conversation
mutex):

```
row = readAgentRow(id)
if (row.limitHitAt && row.sessionId) {
  next = launchAccount({...readClaudeAccounts(), byAccount: readClaudeUsage().byAccount, now})   // pure, no select
  if (next !== row.account) await relaunchOnAccount(id, row.sessionId)
}
commandAgent(turn)
```

`relaunchOnAccount` reuses the Stop-path rewind relaunch steps already in
that file (`stopAgent` → `writeOptions({...readOptions(id), resume: sessionId,
resumeAt: null, prompt: null})` → `recordLaunchSession` → `startAgentProcess`
→ `waitForProjection(agentPid !== null)`). `startAgentProcess` calls
`chooseLaunchAccount`, so the new process lands on the new account (and
auto-switch selection stays where it is today).

This makes the wrong thing inexpressible: typing into a stopped conversation,
the Resume button and Resume all are all just "send a turn". When no account
has room (`next === row.account`), the turn goes to the agent as today and the
CLI answers with the limit line again — loud, not swallowed.

### 3. The set of stopped conversations (runtime-sdk, core + server)

- `core`: `liveCollection` `runtime-sdk.limit-stopped` — rows
  `{ conversationId, account, limitHitAt }`.
- `server`: `serveCollection` over `conversations_ext_sdk_agent` joined to
  `_conversations` where `limit_hit_at is not null` and status active, ordered
  by `limitHitAt desc`, default `limit` 50 / `maxLimit` 200. Kept fresh by the
  change feed (the side table is DB-backed).

### 4. Resume endpoint (runtime-sdk, core + server)

`POST /api/runtime-sdk/resume-limited` body `{ ids?: string[] }` (omitted =
every stopped conversation): for each, `submitTurn(id, { kind: "text", text:
"Continue from where you left off." })` (the CLI's own resume wording, see
`transcript-source/core/protocol.ts` meta-prompt). Returns per-id
`SubmitOutcome` so the UI can show failures. `submitTurn` already runs
`ensureResumed` for hibernated rows and holds turns for `starting` ones.

### 5. UI (runtime-sdk, web)

- **Health report**: in the Claude Code row (`web/components/claude-accounts.tsx`,
  beside `LimitBanner`), a `StoppedBanner` when `runtime-sdk.limit-stopped` is
  non-empty: "N conversations stopped at a usage limit" + Button
  "Resume all on <launch account> · X% left" (account from `launchAccount`, room
  from `weekRoom`). Disabled with "No account has room until <reset>" when
  `limitReached` on every account. A disclosure lists them as a `DataView`
  (`views={["list"]}`, ConversationItem rows) so single ones can be opened. The
  row's status goes `attention` while the set is non-empty
  (`useClaudeCodeRowHealth`).
- **Transcript**: a `JsonlRowActions.Item` on `api-error` events with
  `error === "rate_limit"`: "Resume on <account>" — visible only when
  `useJsonlConversationId()` is in the stopped set (so old limit lines in a
  resumed conversation don't show it). Calls the endpoint with `{ ids: [id] }`.
  Button auto-pends on the promise.

## Verification

1. `./singularity test plugins/conversations/plugins/runtime-sdk` — reducer
   cases (limit hit sets, `turn_started`/`started` clear, account recorded) and
   a pure test of the "relaunch?" decision.
2. `./singularity build`, then `query_db` on the worktree DB:
   `select conversation_id, account, limit_hit_at from conversations_ext_sdk_agent where limit_hit_at is not null`.
3. Replay check: a backend reading an existing events.jsonl with a limit line
   (e.g. a copy of conv-1792668571-ochl7d's) projects `limitHitAt` (old
   `started` events have no account → `null` → treated as "restart useful").
4. Manual end-to-end on the worktree build with two accounts: let a test
   conversation hit the limit (or switch accounts with one already stopped),
   confirm the health banner lists it, click Resume all, confirm in
   `agent.log` the new process's `--account` and the turn continuing.
   Screenshot the banner and the transcript button with `screenshot.ts`.
